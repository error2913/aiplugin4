## 0. 判定原则（先读这段，否则会误判）

### 0.1 单测已覆盖什么，手工只需验证什么

### 0.2 五条最容易误判的语义（**先接受，再测**）

| 现象 | 真相 |
|---|---|
| 「启用用量限制」= `false` 时，`.ai tk quota` 依然显示 `已用 X / 2,000,000（≈200万，P%）` 和「剩余」 | **正常**。`status()` 不按开关折算，永远渲染"如果开起来预算会是多少"（`manager.ts:467`）。首行写「仅统计，不拦截」才是开关状态的唯一权威 |
| 用量为 **0** 时，`.ai tk quota` / `.ai tk me` 的「已用」列显示 **`不限`** | **已知文案缺陷**，见 §14.1。不是你的操作错了，记录为 `PASS（含已知缺陷 D-1）` 即可 |
| 会话档、本人档两行**只有 5 小时窗口**，看不到周/月 | **设计如此**：`status().session/user` 只取 `hourKey`（`manager.ts:490-501`）。本人周/月用 `.ai tk me`；会话周/月**没有查看入口**（只能 `.ai tk rank week` 间接看） |
| 把「5小时限制」改成 `1` 后 `.ai tk quota` **首行没写「当前超限」**，但对话照样被拒 | **正常，两道闸**：粗闸条件是 `已用 >= 上限`（`token.ts:65`），`已用=0` 时不成立；但细闸条件是 `已用 + 估算 >= 上限`，估算恒 > 0 ⇒ **细闸拒**。看 §3 开头 |
| 被拒了但日志里**找不到** `quota denied:` | **正常**：细闸（`admitChat`）不打日志，只有粗闸（`session.chat`）打。见 §3 开头与 B2.2 |

### 0.3 配置生效的三个时间常数（这是本清单最常见的假失败）

| 常数 | 值 | 影响 |
|---|---|---|
| `CONFIG_CACHE_TTL` | **60 000 ms** | 面板点「点我保存」后，插件最长 **1 分钟**后才读到新值（`config/static_config/meta.ts:6`） |
| `SAVE_MIN_INTERVAL_MS`（启用时） | **5 000 ms** | 开启总闸时，一次对话的记账最多 5s 后落盘 |
| `SAVE_MIN_INTERVAL_DISABLED_MS`（关闭时） | **60 000 ms** | **关闭总闸时是 60s**！做重载持久化测试时必须**等满 60 秒**再重载，否则计数丢失是正常的（`quota/store.ts:22-23`） |

> **规则：所有改配置的用例，"保存 → 等 ≥ 65 秒 → 再测" 写进操作步骤里，不要凭感觉。**

## 3. B 组：总闸 + 拒绝与节流（**核心**）

> **先理解两道闸，否则本节全做错**：
> - **粗闸** `session.chat` 最前面 `checkChat`：`已用 + 在飞 >= 上限` 即拒。**有日志** `quota denied: …`，返回 `'quota'`。
> - **细闸** `requestModel` 里 `admitChat`：`已用 + 在飞 + 本次估算 >= 上限` 才拒。**无日志**，抛 `QuotaExceededError`，由 `agent.ts:425` 兜住并回复。
>
> 含义：**上限 ≤ 单次请求估算（≈ prompt + 4096）时，任何请求都在细闸被拒，`used` 永远是 0**。所以「粗闸」场景必须先把 `used` 堆上去再把上限调低。

### B1 粗闸：先堆用量，再压低上限

| 步骤 | 操作 |
|---|---|
| 1 | 「启用用量限制」= `true`、「5小时限制」= `2000000`、「限制时段及百分比」**清空**（避免峰时系数干扰） |
| 2 | 保存 → **等 ≥ 65 秒** |
| 3 | 骰主 `.ai tk quota clear`（从 0 开始，便于辨认） |
| 4 | 群聊正常 @ 对话 **1–2 轮**，`.ai tk quota` 确认「5小时 已用」是一个**几千以上**的数字 |
| 5 | 把「5小时限制」改成 **`1`** → 保存 → **等 ≥ 65 秒** |

| ID | 操作 | 期望 | AC | 依据 |
|---|---|---|---|---|

## 4. C 组：峰时百分比（预算系数）

> 语义：命中片段 ⇒ `有效预算 E = max(1, floor(总限制 × 百分比/100))`。**百分比是预算系数，不是消费折扣。**

## 6. E 组：静默闸（定时器 / 事件 / 唤醒）

> 共同要求：**配额耗尽时不产生 AI 回复、不往上下文写 system 提示**。
> **但"是否给用户发提示"分两类，这是本组最容易判错的地方：**

| 路径 | 是否给用户发配额提示 | 是否有日志 | 次数/条目是否被消耗 |
|---|---|---|---|
| **手动定时器**（`set_timer`：`target`/`interval`，无 `ruleId`） | **完全静默** | **无日志** | `target` **保留**（下 tick 重试）；`interval` **不消耗** |
| **规则/模式定时器**（`timer` 模式、链 `timer` 门、M4 `active_time`） | **会发一次**（`notifyOnce`） | **无日志** | `interval` **不消耗**；`target` **会被丢弃、不补发** |
| **旧存档 `activeTime` 定时器** | **完全静默** | **无日志** | 重排已完成，只跳过本次 |
| **事件触发**（`event` 模式） | **完全静默** | `事件触发跳过（用量限制）：…` | 事件已去重，**不补发** |

## 7. F 组：用途降级（四种辅助用途）

> 四种用途（摘要 / 判定 / 识图 / 嵌入）各有独立软上限 `E_h × 用途百分比%`，另有 `Σ用途 ≤ E_h` 的合计兜底。
> **用途被拒不改变用户可见回复的"成功/失败"，只改变质量**。所以判定标准是「**功能降级但不报错不崩**」。

### 7.1 怎么快速把某个用途压到必然被拒

用途预算是 `E_h × p%`，而 `p` 最小只能填 `1`。所以**唯一手段是把 `E_h`（= 5小时限制 × 时段系数）压小**。

|---|---|---|---|---|
| 识图 | `100000` | `1` | 1 000 | 一次识图请求估 ≈1024+ token ⇒ **第一张图就可能被拒** |
| 嵌入 | `3000` | `1` | 30 | 一次嵌入 query ≈ 20–40 token ⇒ 几次检索即被拒 |
| 摘要 | `100000` | `1` | 1 000 | 摘要请求 prompt 远超 1000 ⇒ **第一次归档必被拒** |
| 判定 | `100000` | `1` | 1 000 | 判定请求 prompt 远超 1000 ⇒ **第一次评分必被拒** |

## 14. 编制本清单时核对代码发现的问题（**不是功能缺陷**，但会让验收误判）

### 14.1 「已用」为 0 时渲染成「不限」（**文案缺陷，建议修**）

- **代码**：`src/cmd/sub_cmd/token.ts:23-24`
  ```ts
  const unlimited = (l: number): boolean => !Number.isFinite(l) || l <= 0;
  const fmtTokens = (n: number): string => (unlimited(n) ? '不限' : comma(n));
  ```
  `fmtTokens` 本意是**渲染上限**（`0`/`∞` = 不限），但它同时被用于渲染**已用量**：
  `token.ts:74`（三窗口）、`:83-84`（会话/本人）、`:87`（用途）、`:109`（`.ai tk me`）。
  ⇒ 已用量为 `0` 时 `unlimited(0) === true`，于是输出 `已用 不限`。
- **实测影响**：全新会话/刚清空后执行 `.ai tk quota`，会看到
  `5小时  已用 不限 / 2,000,000（≈200万，0%）  剩余 2,000,000  窗口 …`
  （`.ai tk me` 三条窗口行同理，`.ai tk quota` 的会话/本人/用途行同理）
- **验收处理**：看到「已用 不限」**不要判 FAIL**，按 `PASS（含已知缺陷 D-1）` 记录。
- **建议修法**：已用量改用 `comma(n)`（新加 `fmtUsed`），`fmtTokens` 只保留给上限位。一行改动，可另开 PR。
