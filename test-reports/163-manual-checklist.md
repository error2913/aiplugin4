## 0. 判定原则（先读这段，否则会误判）

### 0.1 证据强弱与**两个不同的东西**

先分清两个机制，否则会互相误判：

| 机制 | 何时运行 | 结果去哪里看 |
|---|---|---|
| **冻结守卫**（`compile.ts:726-748` 的 `stats.prefixDrift`，**有快照就跑**） | 每轮：把本轮渲染结果与「上轮快照」逐字节比；**只要发现差异就记 `prefix-drift-freeze`**（差异若在冻结区内，还会用快照覆盖回去） | **「前缀：」行的 reason** |
| **漂移探针**（`runPrefixProbe`，`src/utils/message.ts:685`，**默认关闭**，`.ai ctx debug` 开） | 每轮：比对消息哈希，报**首个差异位置**；不做任何修正 | **「前缀守卫：」行** |

关键推论有两条：
1. **「前缀守卫」行只在探针开启时才有意义**。探针关着时，`commands.ts:190` 取到的 `drift` 恒为 `null` ⇒ 恒显示「上次校验通过」，**这不代表校验过**，只是没测量。
2. **冻结守卫需要「上一轮快照」**。重载后第一次编译没有快照 ⇒ 守卫空转一轮（这也是为什么重载后的首编译用 `reload`/`upgrade`/`tools` 归因，而不是漂移）。

| 等级 | 证据 | 说明 |
|---|---|---|
| **强** | `.ai ctx` 的「缓存：命中率 N%」逐轮上升 | 厂商回传的真实 `cache_read_tokens`，唯一能证明"钱省到了"的指标 |
| **强** | 「前缀：」行恒 `稳定` / 只有白名单 reason | 内部记账，能证明没有非白名单 rebase |
| **强** | 从未出现 `prefix-drift-freeze` | 始终运行的冻结守卫一次都没被触发 ⇒ 无渲染路径漏纯度 |
| **中** | `.ai ctx debug` 开启后「前缀守卫：上次校验通过」 | 探针的逐消息哈希比对，能证明连续轮次字节一致 |
| **无效** | 探针关闭时的「前缀守卫：上次校验通过」 | 没测量，别当证据 |
| **弱** | 问模型"你看到的历史带不带时间戳" | 模型转述，可能幻觉，只能当辅助 |

### 0.2 本版**没有**「dump 请求体」的命令

历史渲染出来的字节，人无法直接看到。要验证"历史不带 `[msg_id]`/`[time]`"这类内容级断言，只能靠：
- 探针/守卫（强：能发现漂移）
- 让模型原样转述（弱）
- 真接厂商看命中率（强，间接）

**不要**因为"看不到请求体"就判 FAIL —— 按下面各用例指定的证据判。

### 0.3 几条正常但反直觉的现象（别报成 bug）

| 现象 | 原因 |
|---|---|
| **新会话（还没说过话）** 显示 `前缀：稳定` | 正常。引导期归因的条件是 `contextV2.head().nextSeq > 1`，空会话不记 rebase |
| **老会话重载后第一条消息** 显示 `前缀：已重建 1 次（最近原因：reload）` | `prefixSnapshot` 是运行时字段，重启必为空 ⇒ 本次启动首编译必然换前缀。这是**白名单内**的 rebase，按 `upgrade`/`tools`/`reload` 三选一归因 |
| 重载后「缓存：命中率 -（本会话暂无数据）」 | 命中率窗口也是运行时字段，重启清零，重新累积 |
| 重载后「前缀守卫：-」 | `service.lastCompile()` 为空（重载后还没编译过）。这行刻意不谎报"通过" |
| 重载后「前缀守卫：上次校验通过」但探针没开 | 见 §15.2：探针关闭时 `drift` 恒为 null ⇒ 恒显示这句。**这不是校验证据** |
| 「注入：跳过 0」永远是 0 | 设计如此：预算不足时**先归档腾位**，绝不跳注；`skipped` 是硬约束自检位 |
| DeepSeek 命中率不是 100% | 厂商按块命中，末尾新消息必然 miss；看**趋势**不看绝对值 |
| 后端不回传缓存字段时「命中率 0.0%」 | 无数据 ≠ 没命中。若你用的是不返回 `prompt_cache_hit_tokens` / `cached_tokens` / `cache_read_input_tokens` 的后端，这一行不可用（记 `SKIP(env)`） |
| 探针开启后**第一轮**不报差异 | 开启时把上轮哈希清零了（`hashes: []`），第一轮没有可比基线，从第二轮起才有效 |

## 4. C 组：缓存命中率趋势（唯一的"钱"证据）

> **命中率的算法（先看懂再判）**：`cacheWindow` 是**近 100 轮的滚动窗口**（`CACHE_WINDOW_TURNS=100`），
> 显示值 = `Σ read / Σ prompt × 100%`，是**累计平均，不是单轮值**。
> ⇒ 所以它会**平滑上升**，不会像单轮那样跳变；也**不会因为某一轮 miss 就掉很多**。
> 另外 `prompt_tokens` 用的是归一化后的值（Anthropic 方言会把 `cache_read`/`cache_creation` 补回 prompt），
> 所以不同厂商的命中率**可比**，但绝对值仍受厂商块大小影响（见 §0.3）。

### C1 命中率逐轮上升

```
1) 全新会话（或 .ai ctx purge --yes 后）先连发 3 轮暖场
2) 之后每发 1 轮，记一次 .ai ctx status 的「缓存：」行
共记录 8 轮
```

- [ ] 第 1–2 轮：「缓存：命中率 -（本会话暂无数据）」或很低（<20%）
- [ ] 第 3 轮起：命中率**明显上升**（通常 40%+，随历史增长可达 70–90%）
- [ ] 第 5–8 轮：命中率**不回落**（因为是累计平均，允许极小波动，若明显回落说明前缀被反复重建）

**判定**：若命中率**恒为 0%**：
1. 先确认后端是否回传缓存字段（见 §0.3 最后一行），不回传 ⇒ `SKIP(env)`；
2. 回传但为 0 ⇒ **FAIL**，保存该轮 `.ai ctx status` 截图 + 海豹日志，按 §14 上报。

> 注意「缓存：命中率 **-**（本会话暂无数据）」和「**0.0%**」是两件事：
> 前者是**窗口里没有有效轮次**（还没请求过，或所有请求 `prompt_tokens<=0` 被跳过）；
> 后者是**有数据但读到的缓存为 0**。前者不能判 FAIL。

### C2 消息停顿不破坏命中率

```
连发 3 轮 → 停 3 分钟（< 1 小时）→ 再发 3 轮，每轮后 .ai ctx status
```

- [ ] 停 3 分钟后的第 1 轮命中率**不归零**（前缀还在，厂商缓存未过期）
- [ ] 前缀行保持稳定

> 这是"停顿但没到时间注入阈值"的场景，最容易被误认为"缓存丢了"。
> 停顿 < 1 小时 ⇒ 不注入 time 块 ⇒ 前缀不变 ⇒ 缓存应继续命中。

## 5. D 组：前缀漂移探针

> **探针的语义（必须先读懂，否则全组都会误判）**：
> 探针是**逐字节**比对（`runPrefixProbe`，`src/utils/message.ts:685`），它**不认识 rebase 白名单**。
> 它只比较「上一轮编译产物的消息哈希」与「本轮」，一旦不同就记 `firstDiffIndex`。
> 因此：**任何合法的 rebase（归档/编辑/隐藏/改配置…）都会让探针报一次首差异位置**，而且是**只报一轮**
> （下一轮 `prev.hashes` 已更新成本轮的，自动回到"上次校验通过"）。
>
> 所以探针的正确用法是 **配合前缀行一起看**：
> - 有首差异位置 **且** 前缀行 count 增加了（reason 是白名单项）⇒ 正常 rebase，**PASS**
> - 有首差异位置 **但** 前缀行没变（reason 未更新）⇒ **这才是 bug**，即"非白名单漂移"
> - 没首差异位置 ⇒ 最理想，说明连续轮次逐字节一致

### D1 稳态（无 rebase）时探针恒通过

```
1) .ai ctx debug          # 开启（此时会把上轮哈希清零，所以第一轮不比对）
2) 连发 5 轮纯对话，每轮后 .ai ctx status
```

- [ ] 第 2 轮起「前缀守卫：」行**始终**为 `上次校验通过`
- [ ] 前缀行始终 `前缀：稳定`（没触发归档的前提下）
- [ ] 5 轮内**没有**出现 `首差异位置`

**判定**：稳态下出现首差异位置 ⇒ FAIL（这是真正的非白名单漂移）。

### D2 合法 rebase 时探针报一次差异（这是**预期**，不是 bug）

> **关键时序**：探针只在**编译时**跑（`runPrefixProbe` 由 `compileV2Request` 调用），
> 而 `.ai ctx archive` / `.ai ctx hide` 这类**指令本身不编译**。
> ⇒ 所以「rebase 发生」和「探针报差异」**不在同一轮**：rebase 当轮只改「前缀：」行，
> 探针要等**下一次对话**才比对到差异。

```
1) .ai ctx debug          # 开启
2) 连发 3 轮对话（让探针进入稳定态，守卫行 = 上次校验通过）
3) .ai ctx archive        # 合法 rebase（指令，不编译）
4) .ai ctx status         # ← A 点
5) 发 1 轮对话             # 编译 → 探针比对
6) .ai ctx status         # ← B 点
7) 再发 1 轮对话
8) .ai ctx status         # ← C 点
```

- [ ] **A 点**：前缀行 reason=`archive`；守卫行仍是 `上次校验通过`（本轮没编译，探针没跑）
- [ ] **B 点**：守卫行显示 `首差异位置 N`（**预期**，字节确实变了）
- [ ] **C 点**：守卫行回到 `上次校验通过`（自愈，只报一轮）
- [ ] 全程前缀行 count **只 +1**（归档一次）

**判定**：
- **A 点**报差异 ⇒ 几乎不可能（该轮没有任何编译）。若真出现，说明你在第 3–4 步之间发过消息，重跑本用例
- **B 点**没报差异 ⇒ **不算 FAIL**。归档把最旧的消息换成了摘要块，前缀开头就变了 ⇒ 正常应在 `首差异位置 0`（或很小的位置）；
  若没报，多半是本次归档释放的块恰好没落进共同长度区间（见下面的已知局限），记 `SKIP(探针未覆盖)` 即可
- **C 点**仍然报差异，或前缀行 count **持续增长** ⇒ **FAIL**

> ⚠️ 这是本组最容易误报成 bug 的地方。**判据永远是"前缀行 count 有没有增加 + reason 是不是白名单项"**，
> 不是"探针有没有报差异"。探针只是辅助定位，它不认识白名单。
> 12 个白名单 reason 见 H 组表。
>
> 探针的已知局限（`src/utils/message.ts:690`）：`comparable = min(prev.hashes.length, hashes.length)`，
> 所以**只比两者共同长度**那段。归档通常让消息变少，于是"被截掉的那段"不会被比到 ——
> 这是"宁可漏报不误报"的取舍，不是 bug。

### D3 关闭探针后不再显示

```
.ai ctx debug    # 关闭（同时清空上轮哈希）
.ai ctx status
连发 2 轮，每轮后 .ai ctx status
```

- [ ] 指令回「前缀探针已关闭」
- [ ] 守卫行显示 `上次校验通过`（因为 `firstDiffIndex` 被置 null）
- [ ] 但**注意**：这里的「上次校验通过」**不代表校验过** —— 探针已关，`drift` 恒为 null（见 §15.2）
- [ ] 探针是纯观测：开关不影响任何对话行为、不影响前缀行、不影响命中率

> 关闭逻辑见 `src/context/commands.ts:334-342`：关闭时把 `prefixProbe` 整个重置为

## 6. E 组：历史层内容（弱证据为主，配合探针）

> 本组评级为**中**：先用 `.ai ctx debug` 保证没漂移，再让模型转述内容。
> 让模型"逐字贴原文"本身不可靠（它会改写、会省略），所以**只用来验证"某标记不存在"**，不用来验证"某标记存在"（后者用 E2 的系统事件，那类文本短且模型会照抄）。

- [ ] **没有** `[msg_id:` 前缀

### E2 系统事件**保留** `[time]`

```
1) 让 AI 设一个 1–2 分钟后触发的定时器，例如跟它说：
   「用 set_timer 设一个定时器，1 分钟后触发一次，prompts 写『测试唤醒』」
   （模型会用 types=interval + minutes=1 + count=1；或 types=target + 明确的年月日时分）
2) 等它触发（会写一条 [system:wake] 系统事件）
3) 问：「刚才那条系统唤醒消息的原文是什么？」
4) 用 .ai trg timer lst 确认条目已消耗；残留的用 .ai trg timer clr 清
```

- [ ] 系统事件形如 `[system:wake][time:<时间>] [wake] ... [/system]`（**有** `[time]`，且紧跟在 `[system:wake]` 后面、没有空格）

> 渲染实现见 `src/context/view/compile.ts` 的 `renderSystemEvent`：
> `` `[system:${name}]${time}${text ? ' ' + text : ''} [/system]` `` —— `time` 与 `[system:...]` 之间**无分隔符**。
>
> 定时器正文渲染见 `src/timer.ts` 的 `renderTimerText()`：只用 `set`（设定时刻）与 `target`/`intervalSec`（目标/间隔），
> **不输出"现在几点"** —— 否则同一事件每轮渲染字节不同，直接破坏 R1。这也是 v4.32 顺手修掉的 1970 年 bug
> （旧实现用 `fmtDate(interval)` 把秒数当时间戳格式化）。
>
> 参数约束（`src/utils/timer_spec.ts`）：`target` 型**必须**显式给 `years/months/days`（1~12 月、1~31 日、0~23 时、0~59 分），
> 早于当前时间或超过 1 年被拒；`interval` 型间隔必须 > 0 且 ≤ 1 年，`count` 为 -1 或 1~30（-1 要求间隔 ≥ 12 小时）。
> `prompts` **1~10 条**是必填项，触发时随机取一条。

| **H11** | 摘要区间被编辑污染（难构造，可跳） | `summary-stale` | `utils/message.ts:668-670` 的 false→true 跳变 |
| **H12** | 注入总量超硬上限（极难构造，可跳） | `inject-overflow` | `injection_writer.ts:390` |
| — | *（测试专用，用户不可触发）* | `epoch` | 仅单测使用，手工验收不会出现 |

**判定要点**：每个用例只验证「reason 字符串是否匹配」。`prefix-drift-freeze` **不应**在任何用例中出现 —— 出现即 FAIL（那说明有正常路径漏了纯度，代码出处 `utils/message.ts:672-674`）。

> **H2/H3 的坑（很重要）**：配置是**带 60 秒缓存**的（`CONFIG_CACHE_TTL = 60000`），且指纹比对只在**下次读该分区**时发生。
> 所以改完配置**立刻**看 `.ai ctx status` 很可能还是旧值 —— 必须**等缓存过期或发一轮对话**触发读取。
> 若等 60 秒 + 一轮对话后仍无 `config:*` 归因，才是真 bug。
> 另外 `observeConfigFingerprint` 的**首次观测只建基线、从不通知**（`config/hooks.ts`）——所以"改配置 → 重启 → 首轮"时
> 可能先报 `reload`/`upgrade` 而把 `config:*` 吞掉，这是设计（避免启动时一波假 rebase）。
>
> **H9/H10 的坑**：引导期归因是**一次性**的（`takeBootRebaseCause()` 取走即清空，见 `src/core/prefix_boot.ts:51`）。
> 因此：
> - **第一个**在本次启动后编译的会话 → 显示真实归因（`upgrade` / `tools` / `reload`）
> - **之后**编译的其他会话 → 回落成 `reload`（`takeBootRebaseCause() ?? 'reload'`）
>
> ⇒ 只在**同一个测试群**里验收 H9/H10。如果你想在多个群都看到 `upgrade`，那是**做不到的**，不是 bug。
> 另外 `upgrade` 优先级高于 `tools`（版本变了就不再看工具指纹），所以"改版本号 + 改工具"只会报 `upgrade`。
>
> **白名单只有 7 个分区**（`src/session/persistence.ts` 的 `CONFIG_REBASE_KEYS`）：
> `context` / `tool` / `role` / `image` / `model` / `subagent` / `knowledgeBase`。
> 改**其他**分区（`memory` / `mcp` / `skills` / `base` / `quota` / `error` 等）**不会**产生 `config:*` rebase —— 这是设计（它们不进 system 渲染字节）。别把这些报成 FAIL。
>
> H8 会清空会话上下文，**放最后做**，做完 `.ai ctx status` 应显示 `已重建（最近原因：purge）` 且上下文条数归零。

## 15. 本清单编制时核对代码发现的瑕疵（**不是功能缺陷**，但会让验收误判）

编制本清单时逐项对照了实现，发现 4 处"文案/展示/时序"层面的不严谨。它们**不影响 R1/R2/R3 的正确性**，但在手工验收时会导致误判，先列在这里：

### 15.1 提示词里的时间块标记与实际渲染不一致

- **写的**：`src/prompt/texts/en.ts:71` 说 `A time injection block ([system:time] Current time: …) appears only after a gap longer than 1 hour`
- **实际渲染**：`src/context/view/compile.ts` 的 `renderInjectionBlockText()` 对所有 kind 统一输出
  `[system:inject-<kind>] <正文> [/system]` ⇒ time 块的真实字节是
  `[system:inject-time] Current time: <时间> [/system]`
- **全仓搜索**：`[system:time]` 只在 `en.ts:71` 这一句提示词里出现，没有任何代码产出这个标记
- **影响**：模型可能按提示词去找 `[system:time]`，实际看到的是 `[system:inject-time]`。因为块正文本身带
  `Current time:` 语义，模型通常不会认错，但这是**提示词与实现不一致**，建议后续修
- **验收影响**：G1 里如果模型说"没看到 `[system:time]`"**不是 bug**。按实际 `[system:inject-time]` 判

### 15.2 探针关闭时「前缀守卫」行仍显示「上次校验通过」

- **代码**：`src/context/commands.ts:190-193` —— `drift` 只在 `prefixProbeEnabled` 时取，否则恒为 `null`；
  而 `null` 走的是「上次校验通过」分支
- **语义问题**：「没测量」被显示成「通过」，与同一函数里 `if (!compiled) lines.push('前缀守卫：-')`（"无统计 ≠ 校验通过"）的初衷相反
- **验收影响**：**探针关闭时不要把「前缀守卫：上次校验通过」当证据**。要看守卫效果必须先 `.ai ctx debug`
- 冻结守卫（有快照就跑）的结果在**「前缀：」行的 reason** 里，不在守卫行

### 15.3 `prefix-drift-freeze` 只报"发生了"，不报"哪一条"

- 冻结守卫触发时，`stats.prefixDrift` 有差异位置（消息下标），但 `notePrefixRebase('prefix-drift-freeze', 0)` 传的
  `throughSeq` 是 **0**，`.ai ctx` 只能显示"最近原因：prefix-drift-freeze"，看不到位置
- 差异位置只在**探针**的「前缀守卫：首差异位置 N」里可见 —— 而探针默认关闭
- **验收影响**：一旦真的看到 `prefix-drift-freeze`，**先 `.ai ctx debug` 开启探针**再复现，否则拿不到定位信息
- 另外这个位置是**编译产物的消息下标**（不是 seq），只能用来人工定位"从第几条消息开始不一样"

### 15.4 探针/守卫只在**真实请求编译**时跑，指令不触发

- `runPrefixProbe` 与冻结守卫都在 `compileV2Request` 里（`src/utils/message.ts:842-851`），
  **只有发模型请求时才会走**。
- `.ai ctx status` / `.ai ctx archive` / `.ai ctx hide` / 改配置 —— 这些**指令本身不编译**。
- **验收影响**：
  - 改完配置后看 status，前缀行可能已经变了（配置 hook 直接记账），但**守卫行还是上一轮的结果**
  - 归档/隐藏后，探针要等**下一次对话**才比对到差异（D2 用例已按这个时序写）
  - `.ai ctx debug` 刚开启时，守卫行显示的是**上一次真实请求**的结果，不是"刚校验过"

> 这 4 条都在本清单各用例里就地标注了"别误判"。是否要修由你决定 —— 15.1 是纯文案（改 `en.ts` 一行即可），
> 15.2 是观测口径（改 `commands.ts` 一行），15.3/15.4 是能力边界（要修得把 diff 位置一路传到 status，
> 收益不大），都不涉及 #163 的核心不变量。
