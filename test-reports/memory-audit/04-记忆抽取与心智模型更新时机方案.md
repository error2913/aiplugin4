## 0. 结论先行（对齐 Hindsight 的默认时机）

| 操作 | Hindsight 的语义/默认 | 本插件默认 |
|---|---|---|
| **L1 事实抽取**（retain） | 每个 retain（内容块）抽事实；不阻塞后续读取 | 在**上下文结算边界/轮末**（AI 已触发）入队；**不设时间去抖**；队列合批；无 AI 触发不抽取 |
| **L2 观察巩固**（事实→观察） | retain/delete/update 后**自动触发**，后台 job；批量加载默认 50；LLM 重试默认 3 次、退避 1s→60s | 抽取完成后**自动入队**；后台执行；单批最多 50 条事实；重试 3 次/退避 1s→60s；无 AI 触发不调度 |
| **L2' 观察更新** | 新事实与现有观察在一次 LLM 内解决（冗余/矛盾/状态更新），保留 history | 写时 `update/delete` 立即失效旧事实；后台定向巩固（同 L2 队列） |
| **L3 心智模型刷新** | `trigger.mode` 默认 **full**；`refresh_after_consolidation` 默认 **false**；最小自动刷新间隔默认 **0**；每模型最多 1 个 pending；空内容保护；delta 有定期 full | **完全对齐**：默认 full、默认不随巩固自动刷新、最小间隔 0、单 pending、空内容保护；delta 需显式开启，开启后定期 full 默认 48h |
| **L3' 定期重建** | delta 模型建议每 48h `clear+refresh`；新增 scheduled full | 仅在 delta + 自动刷新开启时生效，默认 48h |
| **L4 反思**（reflect） | 按需；心智模型优先、读时 0 LLM；stale 才下探 | 按需；快路径 0 LLM；不做后台 reflect |
| **新鲜度分级** | observation pending 0 / <10 / ≥10 → `up_to_date/slightly_stale/stale`；MM stale = 自上次刷新有新 in-scope 记忆 | 完全对齐 |
| **原始事实** | append-only，不做后台去重 | 完全对齐 |
| **在线请求优先级** | 在线请求优先于后台 job 的 LLM 槽位 | 用户 reflect/手动命令 > 抽取 > 巩固 > MM 刷新 |

**插件额外的安全阀**（Hindsight 服务端没有、但本插件必须有）：
- 后台 LLM **并发 1**（本地单连接/限流）；
- 后台 LLM **每小时 20 次**上限（可配，超限只跑用户可见任务）；
- **无 AI 触发不自动调度**（SealDice 有会话待机/未触发 AI 的场景）；
- 连续 3 次失败 **熔断 30min**；
- 调度器 tick 只扫元数据（0 LLM），队列空即停止。

## 1. Hindsight 的具体案例（主要依据）

### 1.1 写入 → 观察：retain 后自动触发，后台执行

- `retain()` 后 consolidation **自动运行**（官方 Blog：*After every `retain()` call, Hindsight's consolidation engine runs automatically*），执行形态是**后台 job**（*runs as a background job after new memories are retained*）。
- 可配置：`HINDSIGHT_API_ENABLE_AUTO_CONSOLIDATION`（retain/delete/update 后自动触发）、`HINDSIGHT_API_CONSOLIDATION_BATCH_SIZE`（批量加载，默认 **50**）、`HINDSIGHT_API_CONSOLIDATION_LLM_BATCH_SIZE`（单次 LLM 事实数）、`HINDSIGHT_API_CONSOLIDATION_MAX_ATTEMPTS`、`HINDSIGHT_API_CONSOLIDATION_RECONCILE_INTERVAL_SECONDS`（后台 sweep 补漏）。
- 底层 LLM 重试默认：`LLM_MAX_RETRIES=3`、初始退避 `1.0s`、上限 `60.0s`；consolidation 的 LLM 重试/退避/超时默认继承全局。
- 原始事实 **没有** 后台去重 sweep：合并只发生在 consolidation 队列里。
- 观察新鲜度用**未巩固积压**分级：0 / <10 / ≥10 → `up_to_date / slightly_stale / stale`。

**含义**：抽取完成后自动入队巩固，但不阻塞回复；批量和重试用 Hindsight 默认；失败不反复烧 token。

### 1.2 观察更新：在 consolidation 内一次性解决

- 新事实到达 → 用 recall 找相关观察（语义 + token 预算 + `tags_match="all_strict"` 边界）→ 一次 LLM 决策：
  - 冗余：改写现有观察；
  - 直接矛盾：保留两种状态并写时间叙事（不覆盖旧信息）；
  - 状态更新：写 “used to / now / changed from X to Y”。
- 写 `history`（previous_text/changed_at/reason/source_memory_id）与 temporal metadata；新观察继承源事实 tags，更新时 tags 并集，consolidation 只在同一安全 scope 内。
- 没有“定期重写所有观察”的定时任务。

**含义**：观察更新不是独立调度器，而是 L2 job 的一部分；纠错由写时失效 + 下一次定向巩固完成。

### 1.3 心智模型：巩固后按 tag 重叠、异步、限频、单飞

- `trigger` 默认：`mode="full"`、`refresh_after_consolidation=false`；另有 `fact_types/tags_match` 等。
- `refresh_after_consolidation=true` 时，consolidation 后**只刷新 tags 与本次触及记忆重叠的模型**；刷新异步提交，consolidation 不等待。
- `HINDSIGHT_API_MENTAL_MODEL_MIN_REFRESH_INTERVAL_SECONDS`：同一模型两次**自动**刷新最小间隔，**默认 0**（官方建议在大导入时设置 floor）。
- 同一 `(bank, mental_model)` **最多一个 pending refresh**（issue #3487：慢 bank 曾堆积 ~45 个重复刷新）；在线请求优先于后台 LLM 槽位（PR #5928）。
- delta 模型有**定期 full 重建**（PR #5674）；官方建议长期 delta 模型每 48h `clear + refresh`。
- 创建时跑一次 reflect 生成 content；此后读取是**直接查库、0 LLM**。
- 刷新有 staleness gating（scope 内没有新记忆→不调 LLM）、空内容保护（空输出保留旧 content、记录 `refresh_skipped`）、watermark 不推进。

**含义**：默认不要“每次巩固都刷新所有模型”；默认甚至不随巩固刷新。只有用户显式打开自动刷新，才按 tag 重叠 + 最小间隔 + 单 pending 执行。

### 1.4 异步操作与优先级

- retain / consolidation / refresh_mental_model 都是 async operation（状态 `pending/processing/completed/failed`），可查询、可 webhook 通知。
- `LLM_MAX_CONCURRENT` 满时，**在线 API 请求优先拿槽位**，后台 async retain/consolidation 排队。

**含义**：后台任务必须低优先级、可观测、可让路；插件里对应调度器 P0–P3 与 `.ai memo status`。

## 2. 主流机制对照（只用于取舍，不照搬）

| 系统 | 抽取/写入 | 巩固/更新 | 反思/合成 | 我们采用的点 |
|---|---|---|---|---|
| **Hindsight** | 每个 retain 抽事实 | retain 后自动、后台 job；批量 50；重试 3/1s→60s | MM 默认 full + 巩固后不自动刷新；异步限频；读时 0 LLM | **默认对齐** |
| **Mem0** | `add()` 抽取并决策 ADD/UPDATE/DELETE/NOOP；`async_mode` 默认 true 后台排队 | 写时更新，无独立观察层 | 无独立调度 | 写路径异步化、写时更新决策 |
| **Letta** | Agent 学到时更新；`/remember` | dreaming 后台子代理：每 N 个完成步骤/上下文压缩时 | dreaming 即合成 | 用“事件/完成步”触发，不用纯 cron |
| **LangMem** | 热路径或后台 | ReflectionExecutor：活动静默后延迟（示例 30–60min），新消息取消重排 | 提取即管理 | **可选**去抖；QQ 场景默认不用 30–60min |
| **Zep/Graphiti** | `add_episode` 抽实体/边 | **写时双时态失效** | 无独立 reflect | 写时失效旧事实 |
| **Generative Agents** | 事件流写入 | 无独立巩固 | importance 累计过阈值（≈150）触发层级反思 | 可用“积压/重要性”升级巩固优先级 |
| **A-Mem** | 新笔记写入 | 写时演化相关笔记 | 无定时 | 仅小规模可借鉴，不采用 |

**结论**：默认行为按 Hindsight；只在“没有常驻 worker”这一点上用事件 + 持久化队列 + 轻量 tick 替代。**不引入 30–60min 去抖作为默认**，因为 QQ 用户期望“刚说过就记得”，且 Hindsight 本身没有这层延迟。

## 3. 本插件的时机设计

### 3.1 分层职责

```
AI 触发的一轮对话（唯一自动记忆入口）
  │  run 结束 / 上下文结算
  ▼
L1 事实抽取 ── 入队 ──→ L2 观察巩固 ──完成──→ L3 心智模型刷新（仅在显式开启时）
  ▲                        ▲                        │
归档/裁剪（同样来自 AI 触发）                      ├─ 定期 full（delta 且开启自动刷新）
                                                    └─ 手动/创建
L4 reflect = 按需，不参与后台队列
```

原则：
1. **自动记忆 = AI 触发的副产物**；没有 AI 触发就没有自动 L1/L2/L3。
2. **抽取跟着结算边界走**，不按每条消息、不按固定时间。
3. **巩固跟着抽取走**（Hindsight：retain 后自动），后台队列合批。
4. **心智模型默认不自动刷新**（Hindsight `refresh_after_consolidation=false`、`mode=full`）。
5. **所有自动 LLM 都不在回复路径上**。

### 3.2 L1：事实抽取时机（对齐 Hindsight retain）

**触发点**：
1. **上下文结算边界**：`context_bridge` 的 `consumeContextV2` 达到记忆水位时（现有触发，只在 AI run 前/后执行），把待抽取原文作为一个 retain 单元入队；
2. **归档/裁剪**：写入 `raw:` 分片后入队（不阻塞归档）；
3. **轮末**：`agent.run` 的 `finally` 阶段检查是否有“已读未抽”的 pending，若有则入队；
4. **手动**：`.ai memo obs` / 工具；
5. **兜底**：下一轮请求前若 pending > 2×有效水位（上限 12k tokens），有界抽取一次，防止积压无界。

**默认没有时间去抖**：
- Hindsight 的 retain 由调用方按内容块触发，没有“等 90s”这层；
- 本插件的“内容块”就是 `mem_cursor` + 水位（`MEMORY_WATERMARK_TOKENS` 上限 6000，实际取 `min(结算水位, 6000)`），已经是自然批；
- 多个 extract job 在队列里时**合并 payload**（一次抽取处理多块），不需要时间窗口；
- 如果以后需要进一步省 token，可加可选 `抽取静默窗口`（默认 0，非 0 才启用 LangMem 式取消重排）。

**硬门控**：
- 只有 **AI 已触发** 的会话才产生 extract job；待机/未触发 AI 的会话不自动抽取（见 3.6）。
- 空文本/空 chunk 不入队。
- 同一会话同一时刻最多 1 个 extract job；新 pending 合并进去。

**成本**：每次抽取 1 次 LLM（Hindsight retain 同样抽一次）；输入受现有 `maxItems:200/maxChars:12000` 限制。

### 3.3 L2：观察巩固/更新时机（对齐 Hindsight 自动巩固）

**触发**：
1. **extract 完成即入队**（Hindsight：retain/delete/update 后自动触发）；
2. **写时 update/delete**：旧事实 `state='invalidated'`，立即把受影响 scope 入队 **targeted consolidate**；
3. **reconcile**：调度器 tick 每 60s 扫元数据（0 LLM），发现“有 pending 但无 job / 失败退避已过”则补入队；
4. **手动**：`.ai memo consolidate` / 工具；
5. **不设“pending ≥ N 才巩固”的默认阈值**：Hindsight 是每次 retain 后自动；队列本身负责合批。

**批量与限频**：
- 单次 LLM 最多 **50 条事实**（Hindsight `CONSOLIDATION_BATCH_SIZE` 默认 50；`CONSOLIDATION_LLM_BATCH_SIZE` 可按模型再调低）；
- 队列 dispatch 间隔 30s：同一 bank 在 30s 内到达的多份 pending 合并为一次 job；
- 同一 bank 同时最多 1 个 consolidate（单飞）；
- **每 bank 最小间隔默认 0**（对齐 Hindsight；没有这个配置就靠队列+批处理）；可选配置用于极端高频群；
- 后台并发 1；每小时 20 次上限（插件安全阀）。

**重试/失败**（对齐 Hindsight LLM 默认）：
- 最多 3 次；退避 1s → 2s → 4s……上限 60s（`LLM_MAX_RETRIES=3 / INITIAL=1.0 / MAX=60.0`，consolidation 默认继承）；
- 连续 3 个 job 失败 → 熔断 30min，避免持续烧 token；
- 空输出/格式错 → 回退简单拼接，标记 degraded，不无限重试；
- pending 事实永不丢；job 状态持久化。

**观察更新语义**：
- 只在 consolidate 内更新观察；`proof_count` = distinct live source facts（重算而非自增）；
- 矛盾保留旧状态 + 时间叙事；`history` 记录 reason/source；
- 失效事实不参与 proof_count，但保留审计；
- 观察 freshness：pending 0 / <10 / ≥10 → `up_to_date / slightly_stale / stale`（Hindsight 口径），只用于 reflect/status，不删除观察。

**token 门控**：没有 pending 事实 → 不调度；只处理本 bank；不跨 bank 全量扫。

### 3.4 L3：心智模型刷新时机（默认完全对齐 Hindsight）

**默认触发**：
| 触发 | 默认 | 说明 |
|---|---|---|
| 创建模型 | ✅ 立即一次 full | 对齐 Hindsight：创建时跑一次 reflect 生成 content；pending 占位 |
| 模板播种 | ✅ 一次 seed full | 播种后立即排 `mm_refresh(full, source='seed')`，否则 pending 永不 ready（见 05 §7） |
| 巩固后自动刷新 | ❌ **默认关闭**（`refresh_after_consolidation=false`） | 对齐 Hindsight 默认；开启后仅 tag 重叠 + stale + 最小间隔 |
| 手动 refresh / add（无答案） | ✅ | 用户显式请求；force 仍单飞 |
| 定期 full（delta 模型） | ❌ 默认关闭；开启 delta 自动刷新后默认 **48h** | 对齐 Hindsight 建议与 PR #5674 |
| sourceQuery 变化 | ✅ 下次刷新强制 full | delta baseline 失效 |
| 失败冷却结束 | ✅ 下一次 consolidate/reconcile 重试 | 冷却 30min（现有逻辑） |
| 启动/读取 | ❌ 不刷新 | 只读 ready content（0 LLM） |

**开启自动刷新后的规则**（对齐 Hindsight）：
- 只刷新 `refresh_after_consolidation=true` 且 `tags` 与本次 `touchedTags` 有交集的模型（tags 为空=全局模型也参与）；
- 同一模型同时最多 1 个 pending refresh；running 时新请求合并为标记（完成后仍 stale 再跑一次）；
- 最小自动刷新间隔默认 **0**（Hindsight 默认；UI 提示：开启自动刷新建议设 floor，尤其导入/大批量时）；
- per-model 输出上限 `maxTokens=2048`（Hindsight 默认）；
- 空内容保护：空输出/LLM 失败 → 保留旧 content，水位不推进，记录 `refresh_skipped`；
- delta：只读 `createdAfterSeq` 之后的新证据；无 baseline/sourceQuery 变化/失败 → full；
- 定期 full：**先合成后替换**，失败保留旧 content（比 Hindsight 的 clear+refresh 更安全，但同样防止空内容回写）。

**成本**：默认 `mode=full` + 巩固后不自动刷新 + 最小间隔 0，意味着**自动刷新完全不发生**，除非用户打开开关；打开后受 tag 重叠/单 pending/48h 限制。读注入不产生 LLM。

### 3.5 L4：reflect 与读取

- **按需**：`.ai memo reflect`、`memory_reflect`、MM 创建/刷新内部调用；不做后台 reflect。
- **快路径**：相关内容的新鲜心智模型命中 → 直接返回 content（0 次合成 LLM），带 `basedOn`；对应 Hindsight 的“心智模型优先、读时 0 LLM”。
- **stale 路由**：模型 stale 或无相关模型 → observations（带 backlog 分级）→ raw facts；prompt 明确“stale 时以原始事实为准”。
- **不做自动写回**：用户 reflect 结果不自动落库；只有 L3 刷新写 `reflect_response/content`。
- **可选短期缓存**：同 query 60s 内复用，避免连续命令重复烧 LLM。

### 3.6 不烧 token 的六道门（关键）

| 门 | 规则 | 目的 |
|---|---|---|
| **1. AI 触发门** | 只有 `agent.run` 实际触发过的会话，才产生自动 L1；待机/未触发 AI 的群消息只留在上下文，不抽记忆 | 解决“不触发 AI 也烧 token” |
| **2. 空工作门** | 无 pending 事实不巩固；无 in-scope 新记忆不刷新；无 query 不 reflect | 消除空转 LLM |
| **3. 合批门** | 同 bank 同 key 只保留 1 个 pending job；30s dispatch 窗口合并；单次最多 50 事实；队列空即停 tick | 减少调用次数 |
| **4. 限频门** | 后台并发 1；每小时 20 次；每模型单 pending；MM 自动刷新默认关 | 控制最坏成本 |
| **5. 熔断门** | 连续 3 次失败暂停 30min；空输出不重试；超时/配额错误不立即重试 | 故障时不烧 token |
| **6. 暂停门** | 插件停止/无模型可用时暂停；待机**不**立刻杀已有 job：自动 job 只在 AI 活动后 30min 窗口内运行，超窗等下一次 AI；恢复后只处理仍 pending 的工作 | 空闲不烧 token，且不把“AI 后转待机”卡死 |

补充：
- **调度器 tick 只读元数据**，不读上下文事件全文、不调 LLM；
- **不新增后台定时抽取**；定时器只做 reconcile/重试扫描；
- 每个 job 带 `source: ai-triggered | archive | manual`，非 `ai-triggered` 的自动 job 默认不创建（manual 除外）。

## 4. 调度器实现设计（插件内）

### 4.1 结构与生命周期

新增 `src/agent/memory_scheduler.ts`（L3；约 250 行）——**放在 agent 层而不是 memory 层**，避免 `memory/*`（L2）反向 import `session/*`（L3）新增跨层依赖；它向下调用 memory（L2），与 `agent/context_bridge.ts` 同级。

```ts
type JobKind = 'extract' | 'consolidate' | 'consolidate_targeted'
             | 'mm_refresh' | 'mm_full';
type JobSource = 'ai' | 'archive' | 'manual';

interface MemoryJob {
  id: string;
  kind: JobKind;
  bankId: string;
  source: JobSource;
  priority: 0 | 1 | 2 | 3;          // P0 manual/reflect; P1 extract; P2 consolidate; P3 mm
  notBefore: number;
  attempts: number;
  payload: { sessionId?; texts?; factIds?; scopeTags?; modelId? };
}

interface SchedulerState {
  version: 1;
  jobs: MemoryJob[];
  running: string | null;
  lastTickAt: number;
  lastAiActivityAt: number;        // 本进程；启动 0；无此标记时自动任务不跑
  hourly: { windowStart: number; llmCalls: number };
  failureStreak: number;
  pausedUntil: number;
}
```

- 持久化到 `mem_sched_v1`（或按 agent 分 key），写穿（仿 `TimerManager`）。
- tick：`setTimeout` 每 30–60s；**队列空即停止**，有任务再启动；不常驻空转。
- 启动：`index.ts` 初始化时加载队列，有任务则启动；重载后 reconcile 恢复。
- 单进程：`running` 保证后台 LLM 并发 1；同 bank/模型另有 in-memory 锁。

### 4.2 优先级与在线优先

| 优先级 | 任务 | 说明 |
|---|---|---|
| P0 | 用户 reflect / 手动 mm refresh / 手动 consolidate | 立即执行；后台让路 |
| P1 | extract | 事实尽快落库 |
| P2 | consolidate | 观察层 |
| P3 | mm_refresh / mm_full | 最贵，默认很少触发 |

- 后台 job 开始前**不调用** `requestLimiter.acquire`（FIFO 会让后台插到用户前），只探测 `requestLimiter.getQueueInfo().active === 0 && queued === 0`；否则延后 5s，累计最多 10min 后强制。对齐 Hindsight“在线请求优先占 LLM 槽位”。
- 用户命令/工具 `runNow`，不进后台队列。

### 4.3 去重、幂等、背压

- Job key：`kind + bankId + target`；同 key 只保留 1 个 pending，新触发合并 payload（Hindsight #3487 单 pending 原则）。
- `extract` 用会话 cursor 幂等；`consolidate` 用事实 `consolidationState`；`mm_refresh` 用 `lastMemorySeenSeq/lastRefreshedAt`。
- 队列上限 200；超限丢弃 P3、合并 P2；P0/P1 保留。
- 重载中断：job 保持 pending/attempts，启动 reconcile 重入；已写事实/观察不回滚。

### 4.4 触发点接线（现有代码）

| 时机 | 现有位置 | 新增动作 |
|---|---|---|
| 上下文结算 | `agent/context_bridge.ts`（`consumeContextV2`） | 抽取完成后 `scheduler.enqueueConsolidate(bank, facts, 'ai')`；本文件是 agent 层，直接调 memory 合法 |
| 轮末 | `agent.ts:189-203` / `500-514` 的 `finally` | `scheduler.onRunEnd(session)`：若存在已读未抽 pending 则排 extract；只对 AI 触发的会话生效 |
| 归档/裁剪 | `context/archiver.ts`（旧回退） | **删除** 3 处 memory 调用；legacy v1 归档不再写记忆，见 4.6 |
| 周期 reconcile | scheduler tick | 60s 扫元数据；补 job/重试/暂停判断；0 LLM |
| 空闲 flush | scheduler tick | 会话静默 5min 且有 pending → 排 consolidate（`source=ai`，来自先前 AI 触发） |
| 命令/工具 | `cmd/sub_cmd/memory.ts`、`tool_memory.ts` | `runNow` / force |
| 插件启动 | `index.ts` | 加载队列、reconcile、启动 tick |

> 不复用 `TimerManager`：它的队列面向用户可见的聊天定时器（`.ai timer`），混入后台记忆会污染展示；但复用其“写穿持久化 + 队列空停止”的模式。

### 4.5 状态与观测

- `.ai memo status`：
  - `pending 抽取 / pending 巩固事实数 / 新鲜度分级`；
  - `后台队列：extract N / consolidate N / mm N`；
  - `下次允许刷新时间 / 最近失败原因 / 本小时后台 LLM 次数 / 是否熔断`；
  - `自动记忆：开/关；MM 自动刷新：开/关`。
- 日志标签 `[memory]`：job 触发原因/跳过原因/耗时/token。
- 可选 `.ai memo ops`（骰主）看最近 job 状态（对齐 Hindsight operations API 的 pending/processing/completed/failed）。

### 4.6 上下文模块耦合审计与解耦（最终：删除而非端口）

**现状问题**：
| 位置 | 问题 |
|---|---|
| `src/context/archiver.ts:6` | 直接 `import { MemoryManager }`；95/377/414 调用 `summarizeChunkWithRetry`。与 docs“上下文不写记忆”冲突 |
| `src/context/roster.ts:98` | `host.session.memory.findImage(id)`：穿透会话记忆门面；新引擎恒 null（死调用） |
| `src/agent/context_bridge.ts` | 正确方向：agent 层消费 `context/recall` 后调 memory；唯一记忆桥 |

**最终处理**（三份 review 结论：v2 下 archiver 被 `context.ts:684,694` 短路，为 legacy v1 上新端口收益≈0）：
1. `context/archiver.ts`：删除 `import MemoryManager` 与 3 处 `summarizeChunkWithRetry`；legacy v1 降级路径**不再写记忆**（记录一次日志）。保留归档分片/窗口逻辑。
2. `context/roster.ts`：删除 `return host.session.memory.findImage(id)`，返回 `null`（`Image.resolveRef` 已覆盖图片解析）。
3. `context/**` 静态守卫：禁止 import memory、禁止 `.memory.`；不新增端口、不改 `prompt/memory_source`。
4. 调度器/桥都在 agent 层；context 不 import scheduler。
5. `context_too_long` 在 v2 下 `archiveByTokenIfNeeded` 返回 `'converged'` 被当成功是**非记忆**既有缺陷，另立工单。

**为什么值得做**：上下文是高频核心链路，记忆是可选功能；删掉直接依赖比新增端口更少代码、更少语义坑（端口布尔成功会掩盖失败/丢 pending）。

## 5. 场景时序

### A. 群里 10 条消息（AI 被触发多次）
1. 每次 AI run 结束 → `onRunEnd` 检查上下文结算是否达到记忆水位；达到则排 `extract`（`source=ai`）。
2. 若多个 extract 在队列中 → 合并成一个 job（一次抽取多块）。
3. extract 完成 → 自动排 `consolidate`；30s dispatch 窗口内到达的更多 pending 合并。
4. consolidate 一次 LLM 处理 ≤50 事实；完成后 `touchedTags`。
5. 默认 `refresh_after_consolidation=false` → 不刷新 MM；只把模型标 stale（0 LLM）。
6. 下一轮注入：新事实/观察可用；MM 注入仍是旧 content，若用户手动 reflect 则按 stale 下探原始事实。

### B. 用户纠正“不是猫，是狗”
1. 抽取输出 `op=update` → 旧事实 `invalidated`，新事实 `supersedes`；
2. 立即排 `consolidate_targeted`（30s 内）→ 观察改写为时间叙事；
3. 受影响模型标 stale；默认不自动刷新（除非用户开启 `refresh_after_consolidation`）。

### C. 第一次创建心智模型
1. `.ai memo mm add` → pending + 立即排 `mm_refresh`（full）；
2. 后台 reflect（strict）→ 成功 ready 并写 `reflect_response`；失败 failed + 冷却 30min；
3. 读取注入 0 LLM。

### D. 用户开启“巩固后自动刷新”（显式选择）
1. 默认 full 模式；每次 consolidate 后 tag 重叠且 stale 的模型排 refresh；
2. 同模型最多 1 pending；最小间隔默认 0（建议 UI 提示设 floor）；空内容保护；
3. 若用户把某模型改为 delta → 每 48h 定期 full 重建（先合成后替换）。

### E. 不触发 AI 的群（待机/无触发）
1. 消息只进上下文事件账本，**不产生 extract/consolidate/refresh job**；
2. 调度器 tick 发现队列空即停；0 LLM；
3. 下次该会话真正触发 AI 时，才按结算水位抽取（此时属于 AI 触发）。

### F. 重载 / 失败 / 忙
- 重载：队列持久化，启动 reconcile；已提交事实/观察不重复。
- 失败：重试 3 次/退避 1s→60s；连续 3 次熔断 30min；状态可见。
- 忙：后台延后，用户 reflect 插队。

## 7. 验收与测试

### 验收
1. **不阻塞**：后台 job 不改变回复 P95；用户 reflect P95 不因后台队列变慢。
2. **不干烧**：无 AI 触发的会话连续 100 条消息 → 后台 LLM 调用数 = 0；空队列时 tick 停止；连续失败熔断生效。
3. **默认对齐**：默认配置下不自动刷新 MM（0 次）；巩固按抽取自动触发；批量/重试/退避与上表一致。
4. **不丢**：重载后 pending 最终处理；无重复 proof_count 虚增。
5. **可观测**：status 显示 pending/队列/预算/熔断/下次刷新。

### 测试（假时钟 + InMemory storage）
- 无 AI 触发不产生 job；AI 触发后抽取/巩固自动；
- 队列合批（多块 → 1 次 extract；多 pending → 1 次 consolidate）；
- 默认 `refresh_after_consolidation=false` 时 0 次 MM LLM；开启后只 tag 重叠 + stale + 单 pending；
- delta 定期 full（48h）先合成后替换，失败保留；sourceQuery 变化强制 full；
- 重试/退避/熔断；重载恢复；暂停/待机门；
- 后台让路；refresh 单 pending；
- 上下文解耦静态守卫（`src/context/**` 不 import memory / 不访问 `.memory.`）；
- `npm run deps:check` 无新增违规。

## 8. 与 Hindsight 的对应关系

| 我们的设计 | Hindsight 依据 |
|---|---|
| 抽取完成自动入队巩固、后台执行 | retain 后自动 consolidation + 后台 job |

| MM 最小间隔默认 0 | `MENTAL_MODEL_MIN_REFRESH_INTERVAL_SECONDS` 默认 0 |

| delta 定期 full 48h | 官方 48h clear+refresh 建议 + PR #5674 |
| 空内容保护/watermark/失败冷却 | 心智模型 refresh 文档 |
| 读模型 0 LLM / reflect 优先模型 | 心智模型“saved reflect responses” |
| 在线优先 | MR #5928 |
| 后台状态可查询 | Operations API |
| 原始事实不去重 | Thirty Agents, One Memory |
| 无 AI 触发不抽取 / 后台并发 1 / 小时上限 | **插件安全阀**（Hindsight 无对应概念） |
