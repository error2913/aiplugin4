## 1. 问题陈述（修正后的因果链）

用户观察到的现象是「待机群聊上下文 token 频繁超出 → 疯狂压缩 → 白耗 token」。核对代码后，因果链需要修正为两条**互相独立**的链路：

| 链路 | 真实触发条件 | 代价形态 |
| --- | --- | --- |
| **A. 入库压缩链**（主因） | **字符阈值**（默认 2000 字）在**每一条新消息**到达时被重新评估；待机群里所有消息都追加进同一个 `user` 消息块，块一超阈值就调一次压缩智能体 | LLM 调用数 ∝ **消息条数**，与 token 是否超限无关 |
| **B. 归档链** | **token 超限**（默认 1e6 本地预算，实际多由模型报 `context_too_long` 触发） | 单次可达数十万 token 输入；且存在「不归档、直接整段硬删」的缺陷路径 |

也就是说：**"疯狂压缩"不是 token 超限造成的，而是入库路径上的按消息压缩造成的**；token 超限走的是另一条更贵、并且有数据丢失缺陷的路径。两者叠加才是完整的"白耗"。

## 2. 现状机制清单（证据见 §14）

| # | 机制 | 事实 | 代价 |
| --- | --- | --- | --- |
| M1 | 每消息重压整块 | 块内累计文本超阈值即调 `compress_agent`；N 条消息的同一个 user 块**最多 2N−1 次**压缩调用（单条压缩 + 合并压缩各 ≤1 次/条） | O(N)~O(N²) 调用 |
| M2 | 压缩输出无约束 | 压缩智能体只有一句 instruction，无目标字数/压缩比校验；`compression` 用途默认 `max_tokens=8192`（输出上限，不是目标）。输出只要仍接近阈值，下一条消息立刻再压一次 | 把 M1 从偶发变常态 |
| M3 | 压缩失败无退避 | 压缩返回等值文本或抛错 → `changed=false`、块不变 → 下一条消息用同一段 joined **再次重试**，无冷却、无退避、无硬上限 | 同段文本反复送审 |
| M4 | 摘要的摘要（不可逆） | 块被压缩后 `contentItems` 只剩一条**无 `rawText`** 的块条目；再次压缩时 `joined` 取 `it.rawText ?? it.text` = **上一轮摘要**；新 `rawItems` 存的是摘要，旧原始全文被覆盖丢弃（`RawUserItem` 无嵌套字段，落盘后不可恢复） | 信息丢失，且 `rawText/rawItems` **不计 token**，丢它并不省 token |
| M5 | 入库无并发锁 | `addUserMessage` 在 await 压缩期间可被下一条消息穿插；两者都用各自快照写 `contentItems`，后返回者可覆盖前者 | 可能丢消息（推断，未复现） |
| M6 | 归档是重链路 | 每块 50000 token 交给 `summarize_agent`，**最多重试 3 次**（即单块最高 15 万输入 token）；每条 fact 一次 embedding 调用；`consolidate` 对每个簇 1 次观察合成 LLM（「用LLM合成观察记忆」默认开） | 单次归档可达百万级输入 token |
| M7 | 归档语义缺陷（数据丢失） | 真实 user 轮数 **≤ 对话保存轮数（默认 5）** 时，`getKeepStart` 返回 0 → 待归档列表为空 → 直接 `forceFitContext` **按轮硬删**：不调 summarize、不写记忆。待机群里所有消息折进 1 轮，必然命中 | 白花 + 丢历史 |
| M8 | 归档静默跳过 + 假成功 | `addAssistantMessage` 里是 fire-and-forget；`archiveByTokenIfNeeded` 遇 `archiving` 锁直接 `return false`；而 `handleModelError` **不检查返回值**，先置 `handled.archived=true` 再打"已归档删除至 X tokens"并重试 → 重试再失败即 `giveup` | 反复被拒 + 日志误导排查 |
| M9 | 默认配置放大 | `上下文最大token=1000000`（与真实窗口无关）、`对话保存轮数=5`（待机群语义失真）、`上下文超长自动归档重试`默认开（"先被拒→再归档→重发"成为默认路径）、`消息压缩阈值=2000` | 放大 M1/M6/M7 |
| M10 | 请求体无上界 | 本地预算 1e6、校准系数无样本默认 1（clamp 0.5~2.0 → 最坏仍 ≈50 万），`applyTokenBudget` 实际不裁剪；`checkRequestBudget` 只告警 | 一次触发可能把整个待机上下文发出去 |
| M11 | 每消息全量落盘 | `session.save()` 把**含事件 raw、rawText、rawItems 的整个会话** JSON 化，每条消息一次（事件每条再各一次）；`flushGroupUserMemories` 每次遍历全部消息建发言者集合 | O(n²) 序列化/写盘 |
| M12 | 无按用途可观测 | 用量只按**模型名**聚合；compression/summarization/judge 常解析到同一个 chat 模型 → `.ai tk` 拆不出"压缩烧了多少" | 无法定位与调参 |
| M13 | 事件与消息同块 | 事件条目与普通消息进入**同一个 user 块**，事件文本会进入下一次 `joined`，帮忙把块推过阈值 → 触发压缩 | 放大 M1 |
| M14 | 其他触发路径（有上限，次要） | judge 评分每会话每小时 ≤20 次 gate 通过 → ≤80 次 LLM 调用（单次最多 4 次尝试）；计数器/概率/计时器命中各起一整轮完整 chat（全上下文 + tools JSON），受令牌桶限制（默认 3 个 / 3 秒补 1） | 有界，但每次都很贵 |
| M15 | **缓存字段未采集** | `extractUsage` 只取 `prompt/completion/total`，不读缓存字段；Anthropic 方言下 `usage.input_tokens` **不含** cache read/creation → `prompt_tokens` 少算。`TokenCalibration.record` 用该值算比值，缓存命中时比值偏小 → 系数向 clamp 下限 0.5 漂移 → `applyTokenBudget` 的 `budget = maxTokens / factor` **被放大到约 2 倍**、`checkRequestBudget` 的预测减半 → 更容易超限、更容易走"被拒→归档→重发" | 预算失真、白耗 |
| M16 | **judge 路径直接渲染整块** | `JudgeManager.buildHistory` 从 `session.context.messages` 取最近 N 条**消息**并用 `buildContent` 整条渲染（`src/judge/judge_manager.ts:386-408`）；待机群里所有消息是**同一条**消息 → judge 的 prompt 可能包含**整个待机块**。gate 只限制调用次数（≤20 次/小时），不限制单次体积 | 单次 prompt 可达数万 token |

1. `docs/03` 称事件 raw「单条 4000 字符」上限，代码中无此实现（只有读取侧 20 条上限）。

## 3. 根因归纳

1. **成本与消息量耦合**：入库路径直接调用 LLM，导致"群越热闹，机器人越贵"，与机器人是否参与对话无关。
2. **上下文只有一种形态**：`context.messages` 同时承担"要发给模型的内容"与"历史存档"两个职责，于是必须靠压缩/归档来腾空间——而压缩本身又要花钱。
3. **降级顺序颠倒**：超预算时先尝试最贵的动作（LLM 压缩/总结），纯代码截断只作为最后的兜底；而项目在工具回调、事件文本上已经确立了"纯代码优先 + 原文保留"的取向（见 `src/context/context.ts:383-409`、`src/pipeline.ts:568-570`），用户消息路径没有跟上。
4. **没有状态概念**：`standby` 只是一个布尔量，没有"当前是否正在对话"的状态，因此无法按状态切换预算、窗口与是否允许 LLM 工作。

## 4. 设计目标与不变量

**目标**

- **G1 成本与消息量解耦**：冷态（机器人未参与对话）入库路径 LLM 调用数 = **0**；记忆沉淀按"积压批量"结算，与消息条数无关。
- **G2 请求体有上界**：发给模型的内容由「真实模型窗口 × 安全系数」决定，而不是 1e6 的默认值。
- **G3 原文不丢**：原文 append-only，只增不覆盖；摘要只是"视图"，不是"替代"。
- **G4 可观测**：按用途（chat/compression/summarization/judge/embedding）与按会话记账，能回答"谁烧的、烧了多少"。
- **G5 兼容**：旧 `session_*` 数据可直接加载；配置语义变更必须有迁移说明与开关。
- **G6 与既有取向一致**：默认"纯代码优先、LLM 只在必要时用"。
- **G7 缓存友好（前缀稳定）**：任何"作废前缀缓存"的操作（改写历史、切模型、改 system/工具集）都必须**批量、稀少、可解释**；能"只追加"就绝不"重写"。

**不变量（不得破坏）**

- `tool_calls` ↔ `tool` 消息配对结构（`src/utils/message.ts:362-406`）；
- `[system:…]`/`[tool_result]` 防注入边界与内部标签剥离；
- thinking mode 下 `reasoning_content` 必须原样回传；
- 事件去重"后到覆盖先到"语义；
- 子代理 notice / 媒体任务送达的"用户请求结果必达"口径（免令牌桶）。

## 5. 核心设计：会话冷热态（Hot / Cold）

### 5.1 为什么需要状态，而不是又一个开关

现有代码里已经有**半个**冷热态雏形：judge 的 WAIT 轮（`src/judge/judge_manager.ts:113-139`）、触发令牌桶（`src/session/session.ts:456-467`）、待机"只记录不发言"。但它们只约束"要不要发言"，**没有同时约束"窗口多大、要不要 LLM、什么时候结算"**——所以才会出现"冷态也在疯狂压缩"。

把"是否正在对话"显式建模成状态后，成本、窗口、结算三件事可以一起跟着状态走：**冷态零 LLM、窗口极小；热态才付费、窗口给足**。这比"降低阈值/关掉压缩"更彻底：后者仍保留 O(N) 的调用结构，且会牺牲上下文保真度。

### 5.2 状态与转移

```
                触发命中（@/关键词/AI设定条件/计数器/概率/计时器/活跃时间/
   COLD ────────► judge SPEAK/媒体与子代理结果送达/.ai 指令要求对话）      HOT
     ▲                                                                    │
     │                                                     无相关活动 ≥ 热态保持秒数
     │                                                                    ▼
     └─────────── 无相关活动 ≥ 冷态回落秒数（转冷时结算一次） ───────── COOLING
```

- **COLD（冷态）**：待机中且机器人未参与对话。
- **HOT（热态）**：一轮真实对话进行中（含工具链、子代理等待期间）。
- **COOLING（余温）**：热态结束后的一段观察期，窗口冻结、不再装回新消息，等待结算后回冷。

**滞回（防抖动）**：`热态保持秒数`（180s）、`冷态回落秒数`（60s）、`窗口重建冷却`（30s），关系为 `重建冷却 < 冷态回落 < 热态保持`。
两个要点（技术细节见 §5.6）：① **"相关活动"≠"群里有人说话"**——只有与机器人有关的交互才重置热态计时，否则活跃群会永远停在 HOT；② 防抖的真正对象是**窗口重建**（它作废前缀缓存），不是"禁止转热"。

### 5.3 每个状态的行为与预算

| 维度 | COLD | HOT | COOLING |
| --- | --- | --- | --- |
| 消息入库 | 纯代码写入**原文库**（append-only，零 LLM）；单条超 `待机单条截断字数` 时 head/tail 截断，原文仍进原文库 | 原文库 + 窗口全文 | 同 HOT |
| 模型窗口 | **按字数界定**：累计超过 `冷态窗口字数`（默认 **5000 字**）就把更早内容折叠为**纯代码摘要**（零 LLM），模型只看到最近约 5000 字 | 按 token 预算 `min(上下文最大token, 模型窗口 × 0.7)` 渲染全文；单条/合并超 `消息压缩阈值`（2000 字）时用 **LLM 压缩**（带门禁与熔断） | 冻结，不再装回 |
| LLM 压缩 | **禁止** | 允许，但需过门禁（§6.2）+ 每会话冷却 + 每轮最多 1 次 | 禁止 |
| 记忆结算 | 进入 COLD 时标记 `needSettle`，用 **watermark 补算**（下次活动时执行）；积压 ≥ `结算水位` 时也可提前结算；单次调用数有上限（§5.6.4/§6.8） | 对话结束时结算一次 | 转冷时结算一次 |
| 事件条目 | 只计数 + 进原文库（默认**不进窗口**，避免 M13） | 进窗口作为背景 | 同 HOT |
| 是否发言 | 否（除非触发命中 → 转热） | 是 | 否 |
| LLM 花费 | ≈0：入库**零 LLM**；例外是 judge 评分（独立小请求，≤20 次/小时/会话，单次体积见 §6.12）与批量结算 | ∝ 交互轮次 | 0 |
| `.ai ctx` 展示 | `COLD` + 窗口预算 + 待结算积压 | `HOT` + 本轮预算 + 本轮调用数 | `COOLING` + 待结算量 |

### 5.4 转热装回（rehydrate）

转热时不使用压缩摘要，而是按**字数预算**（`min(上下文最大token, 模型窗口 × 0.7)`，通常远大于冷态折叠线）从原文库把最近的原文装回窗口；装不下的部分继续以纯代码折叠摘要占位。这比"压缩摘要"更准，也让 M4 的"摘要的摘要"彻底消失。
装回量还有一道天然上界：**原文库上限**（默认 2000 条 ≈ 数万 token）。因此即便 `上下文最大token` 保持 100 万（Q2=B），转热装回也不会失控。

> **可见窗口只按字数界定，不按轮数/条数**：成本由 token（中文 ≈1 token/字）决定，而单条消息长度差异极大（"哈哈哈"3 字 vs 一篇 500 字的转贴），按条数/轮数都会失真；轮数在待机群里更是失效（全部消息只有 1 轮）。
> 主流实现同理：LlamaIndex `token_limit` + `chat_history_token_ratio`、LangChain `trigger=tokens/fraction`（`keep=20 messages` 只是**次要保护**）、Claude Code `autoCompactWindow`（token 水位线）、Aider `--map-tokens`、Codex `model_auto_compact_token_limit`。
> **两个字数参数各管一件事**：`冷态窗口字数`（默认 5000）管"冷态下模型能看到多少历史"，超线用**纯代码折叠**（零 LLM）；`消息压缩阈值`（默认 2000）管"热态下单条/合并消息太长时要不要 **LLM 压缩**"。二者数值独立可调。`对话保存轮数` 保留原义（超限后"归档保留量"的次要保护），不再承担"可见窗口"的职责。

### 5.5 边界情况

| 情况 | 处理 |
| --- | --- |
| 热态期间消息洪水 | 窗口**只追加**，达到预算后**整体折叠一次**（不是每条消息滑动窗口，否则每轮都作废前缀缓存） |
| 长工具链 / 子代理等待 | 保持 HOT（`HOT` 的保持计时在"有新交互或有在途任务"时重置） |
| `.ai stop` / 模型报错放弃 | → COOLING（不再装回新消息） |
| 重载 JS | 冷热态**不持久化**（恢复为 COLD，安全默认）；原文库与记忆持久 |
| 全局待机开启 | 所有会话初始 COLD |
| 媒体任务 / 子代理结果送达 | 免令牌桶直接转 HOT 投递（保持既有"用户请求结果必达"口径） |
| **冷热态切换本身** | **不得改动 system prompt / 工具集**（否则每次切换都击穿前缀缓存）；状态只通过**消息层**（`[system:…]` 提示）或工具调用表达。依据：Anthropic 官方博客的 plan-mode 案例——状态切换用工具实现而非换工具集 |

### 5.6 状态推进与滞回的技术细节

#### 5.6.1 运行时变量（不持久化）

```
state: 'COLD' | 'HOT' | 'COOLING'
stateSince: number        // 进入当前状态的 Date.now()（ms）
lastRelevantAt: number    // 最近一次"相关活动"（ms）
lastRebuildAt: number     // 最近一次窗口重建（rehydrate/折叠）的 ms
settleWatermark: number   // 已结算到的位置（结算幂等用）
needSettle: boolean       // 需要结算的标记
```

放在 `Session` 上并加入 `SESSION_RUNTIME_KEYS`（`src/session/session.ts:30`）→ 重载后自动回 COLD（安全默认）。

#### 5.6.2 "相关活动"的口径（滞回的前提）

| 类别 | 事件 | 重置 `lastRelevantAt` |
| --- | --- | --- |
| **相关活动** | @机器人、触发正则命中、计数器/概率/计时器/活跃时间触发、judge SPEAK、机器人自己发出回复、工具链或子代理在途、媒体/子代理结果送达、`.ai` 指令要求对话 | **是** |
| **无关活动** | 群里其他人的普通消息（待机入库）、系统事件（撤回/禁言/上传等） | **否** |

若普通群消息也重置，20 条/分钟的活跃群会**永远停在 HOT**，本方案直接失效。

#### 5.6.3 状态推进用惰性求值，不挂定时器

在三个点调用 `tick(now)`：①入站消息时 ②`session.chat` 入口（触发命中）③构建请求前（保证渲染用最新状态）。

```
tick(now):
  if busy: lastRelevantAt = now                    // 在途任务冻结衰减（见 5.6.5）
  if state == HOT     and now - lastRelevantAt >= T_hot:   → COOLING (stateSince = now)
  if state == COOLING and now - stateSince    >= T_cool:   → COLD    (stateSince = now; needSettle = true)
```

好处：不必为每个会话挂定时器（避免定时器泄漏与持久化开销）；天然抗重载；状态只在"有事件"时被观察，而所有决策（渲染/是否 LLM/是否结算）都发生在"有事件"时。
代价：**纯静默的群不会自己"转冷"**——但静默时也没有请求；下次消息到达时 `tick` 会一次性把状态推到位（可能 HOT→COLD 连跳），并在那一刻补做结算。

#### 5.6.4 结算为什么不用 `TimerManager`（读 `src/timer.ts` 后的结论）

`TimerManager` 是持久化轮询队列，有三个硬约束：

1. **5 秒轮询**（`src/timer.ts:410`）+ 每个定时器执行后 `await 2000ms` 间隔（`src/timer.ts:391`）→ 精度秒级，够用但不能当精确计时。
2. **到点超过 1 小时的定时器被直接丢弃**（`src/timer.ts:369-373`）→ 机器人离线超 1 小时，定时器就没了。
3. 新增类型要改 5 处机械代码：`TimerInfo.type` 联合、`validKeys`、`task()` 的 switch、`getTimerListText`、以及三处 `types` 参数类型标注（`src/timer.ts:170`、`:201`）。

**结论：用普通 `setTimeout` + watermark 补算，不新增 `TimerManager` 类型。** 约束 2 说明"及时性"本来就保不住，既然必须有补算兜底，持久化定时器的额外价值只剩及时性，不值得改 5 处代码。做法：`needSettle` 标记 + `settleWatermark`，在"下次任何活动"时补算；结算只处理 watermark 之后的原文，天然幂等。

#### 5.6.5 在途任务期间冻结衰减

HOT 期间若工具链/子代理在跑（`session.running` / `activeRuns > 0`）或压缩/归档在飞，`tick` 不得推进状态到 COOLING，否则会出现"任务还在跑、状态已经冷了"的交叉（结算与新工具回调同时改上下文）。规则：`busy` 时持续刷新 `lastRelevantAt`。

#### 5.6.6 防抖对象是"窗口重建"，不是"禁止转热"

COLD→HOT 要 rehydrate（读原文、重建窗口），HOT→COLD 要折叠窗口，两者都会**作废前缀缓存**（DeepSeek 命中/未命中价差约 1/50）。因此 `窗口重建冷却`（T_rebuild，默认 30s）限制的是**重建频率**，不是转热：

```
toHot(now):
  state = HOT; lastRelevantAt = now
  if now - lastRebuildAt >= T_rebuild:  rehydrate(); lastRebuildAt = now
  else:                                 不重建，直接用当前（冷态）窗口回答这一轮
```

代价明确：30s 内被触发两次时，第二次用冷态窗口（5000 字骨架）而非全文——信息略少，但省掉一次前缀重建。

#### 5.6.7 边界与竞态

| 情形 | 处理 |
| --- | --- |
| await 期间定时器/新消息到达 | 状态字段只在**同步段**修改；`tick` 幂等（只比时间戳，不依赖调用次数） |
| 时钟回拨 / 时间跳变 | 时间差一律 `Math.max(0, now - t)`，负数按 0（不推进） |
| 重载 JS | 状态回 COLD（不持久化）；结算靠 watermark 补算；内存定时器自然消失 |
| `.ai stop` | 直接 → COOLING（不等 T_hot），这是明确的停止意图 |
| `.ai off` / 会话清理 | 清运行时字段 + 取消内存定时器（照 `JudgeManager.clearSession`，`src/judge/judge_manager.ts:107-110`） |
| 多会话并发 | 状态 per session，互不影响 |

#### 5.6.8 与 judge 的 WAIT 轮的关系

judge 已有 WAIT 轮（`waitUntil` + `judgeWait` 定时器，`src/judge/judge_manager.ts:163-187`），但它只管"评分冷却"，语义是"轮内消息挂起、轮末重过 gate"。冷热态要覆盖**所有**触发路径并驱动窗口与结算，因此不能复用，只能并存——**WAIT 轮可视为热态内部的一个更细子状态**。

#### 5.6.9 参数取值与伪代码

- `T_hot = 180s`：群聊一次对话的自然间隔通常 1–3 分钟，180s 覆盖大部分连续对话，不会中途转冷。
- `T_cool = 60s`：再观察一分钟，确认不是短暂停顿。
- `T_rebuild = 30s`：窗口重建是秒级操作，30s 足够吸收抖动。

```ts
// src/session/state.ts（纯函数，显式传 now，便于假时钟单测）
export function tick(s: StateVars, now: number, cfg: StateCfg, busy: boolean): StateVars {
    const v = { ...s };
    if (busy) v.lastRelevantAt = now;                     // 在途任务冻结衰减
    const dt = (t: number) => Math.max(0, now - t);       // 防时钟回拨
    if (v.state === 'HOT' && dt(v.lastRelevantAt) >= cfg.hotHoldMs) {
        v.state = 'COOLING'; v.stateSince = now;
    } else if (v.state === 'COOLING' && dt(v.stateSince) >= cfg.coolDownMs) {
        v.state = 'COLD'; v.stateSince = now; v.needSettle = true;
    }
    return v;
}

export function toHot(s: StateVars, now: number, cfg: StateCfg) {
    const rehydrate = Math.max(0, now - s.lastRebuildAt) >= cfg.rebuildCooldownMs;
    return { vars: { ...s, state: 'HOT', stateSince: now, lastRelevantAt: now,
                     lastRebuildAt: rehydrate ? now : s.lastRebuildAt }, rehydrate };
}
```

## 6. 详细设计（模块级）

### 6.1 状态机落地

- 新增 `src/session/state.ts`：`SessionState`（`COLD`/`HOT`/`COOLING`）+ 纯函数 `tick` / `toHot`（显式传 `now`，便于假时钟单测，见 §5.6.9）。
- 运行时字段（`state`/`stateSince`/`lastRelevantAt`/`lastRebuildAt`/`settleWatermark`/`needSettle`）放在 `Session` 上并加入 `SESSION_RUNTIME_KEYS`（`src/session/session.ts:30`）→ **不持久化**，符合 §5.5 的重载语义。
- `tick(now)` 的调用点（§5.6.3）：①`src/pipeline.ts` 待机分支入站（`745-784`）②`src/session/session.ts:448` 的 `chat` 入口（覆盖所有触发路径，含媒体/子代理送达）③构建请求前（`src/agent/agent.ts:196` 一带），保证渲染用的是最新状态。
- 触发命中：`state.toHot()` → 若返回 `rehydrate=true` 才重建窗口，否则用当前窗口回答（§5.6.6）。

### 6.2 压缩门禁、熔断与缓存安全分叉（仅 HOT）

- `Context.compressPreserveIfLong`（`src/context/context.ts:206-218`）增加**门禁**：
  - 接受条件：`outLen ≤ max(压缩最小收益比 × inLen, 压缩输出上限)`；
  - 否则丢弃压缩结果、保留原文（与"工具回调不再压缩"同取向）。
- **输出硬上限 + 结构化 schema**：摘要必须限长（参考量级：Cursor 自总结平均 ≈1000 token、基线 >5000；Claude Code 摘要块 ≈ 被摘要量的 12%），并固定小节（目标 / 已完成 / 错误与修复 / 待办 / 涉及的人与话题）。当前"输出无任何长度约束"是明确的反模式（修 M2）。
- **熔断（修 M3）**：连续 N 次压缩后窗口水位**没有实质下降**（注意 Claude Code 的 thrashing 判据是"压缩成功但立刻回满"，不只是失败）→ 停止自动压缩、降级为纯代码裁剪，并记录 `[ctx-cost] 压缩熔断`。把"已压缩次数"作为状态保留（Cursor 的做法），用于熔断计数。
- **缓存安全分叉**：压缩调用必须**复用当前对话完全相同的前缀**（system + 工具 + 历史），把"请压缩上面这段"作为**尾部追加的 user 消息**，只让指令本身成为新 token；另起一个独立 prompt 的压缩调用会"在前缀第一个 token 就分叉"，整段按未命中价重算（Anthropic 官方博客的对照结论）。
- 压缩输入只含**新增条目**，历史块成员不再进入下一次压缩输入；`rawItems` **只追加不覆盖**（修 M4）。
- 限流：每会话压缩冷却（默认 60s）+ 每轮模型请求最多 1 次压缩 + 失败指数退避（5/15/60 分钟）。
- 入库串行化：HOT 下 `addUserMessage` 的压缩段加每会话锁（修 M5）。
- **两级降级顺序（先无损、后有损）**：先做纯代码裁剪（丢/折叠最旧的原始消息、清理旧工具结果），仍超预算才做 LLM 摘要。依据：Claude Code 原文"**clears older tool outputs first, then summarizes the conversation if needed**"；Anthropic 把 tool result clearing 称作"最安全、最轻的压缩形式"；Cline 在不支持的模型上**回退到规则式截断**。

### 6.3 请求前有界结算

- 在 `src/agent/agent.ts` 的 run 循环里、`handleMessages`（`:196`）之前 `await` 一次**有界**结算：单轮最多 `单次结算调用上限` 次 LLM 调用 + 墙钟预算（默认 10s）。
- 取代"先发超长请求 → 被拒 → 归档 → 重发"：预算在**发送前**就已收敛。
- 结算未完成时，本轮以纯代码折叠摘要占位，保证请求体永不超限。
- `handleModelError`（`:342-350`）必须**检查 `archiveByTokenIfNeeded` 返回值**：为 false 时不得打"已归档"日志、不得置 `handled.archived=true`，改为记 `[ctx-cost] 归档未完成` 并直接给出可读提示（修 M8）。

### 6.4 归档语义修复（修 M7）

- `archiveByTokenIfNeeded`（`src/context/context.ts:419-449`）：当 `keepStart === 0` 且仍超预算时，**不得**走 `forceFitContext` 整段删除；改为：
  1. 先把**最旧 contentItem** 移出窗口（粒度下沉到条目，`dropOldestRound` 增加 item 级裁剪），移出内容进原文库；
  2. 仍超预算才考虑硬删，且必须保留"最近 `地板 token / 地板条数`"，并写一条 `[system:归档降级]` 提示 + 账本计数。
- 归档真正的 LLM 总结只在"待归档消息量 ≥ 阈值"时触发，且按 §6.3 的预算与退避执行。

### 6.5 预算与窗口信息（修 M10，采用 B 方案）

- **不做"默认自动"**：已核实插件拿不到窗口信息——`/models` 只解析 `data[].id`（`src/model/list.ts:2-3`），能力分类不含窗口（`src/model/catalog.ts`），唯一来源是被拒时报错里的数字（`parseMaxContextTokens`，`src/model/api_error.ts:214-233`）。
- 采用 **B**：`上下文最大token` 默认保持 `1000000`；当 `TokenCalibration.predict` 预测超过"已知窗口 × 0.8"时**打警告日志**，提示用户手填合理值。
- 仍把从报错学到的窗口**按模型名持久化缓存**（供告警与 `.ai ctx` 显示"已知窗口：128k（来源：报错探测）"），但**不据此改默认值、不静默裁剪**。
- 请求体的实际有界性由 §5.4/§6.7 的**字数折叠线**保证，因此"一次发出几十万 token"不依赖本项解决。
- 可选增强（P2，需另行确认）：读 `/models` 返回里若存在的 `context_length` 类字段；或提供 `模型上下文窗口` 手填项。

### 6.6 原文库（Layer A，修 M4/M11）

- 新增 `src/context/raw_store.ts`：存储键 `session_<id>:raw:<分片号>`（按天或按 ~2MB 分片），条目 `{ id, time, userId?, systemName?, kind: 'user'|'event', text }`；上限 `原文库上限`（条数/字节）+ 保留天数，超限按最旧优先淘汰。
- `src/tool/tools/raw/tool_raw.ts` 的采集器（`collectUserRawEntries` / 事件采集）扩展为"先查消息内 `rawText/rawItems`，再查原文库"，`read_raw` / `grep_raw` 的**工具接口不变**。
- 收益：`context.messages` 体积有上界 → M11 的 O(n²) 落盘消失；原文永久可查。
- **写入批量化（否则等于把 M11 的写放大搬到另一个键）**：原文库**不**每条消息一次 `storageSet`，改为内存缓冲 + 批量 flush——每 N 条（默认 50）或每 T 秒（默认 5s）或随 `session.save()` 一起落盘。进程被杀最多丢最后一次缓冲，可接受（原文库是"尽力保留"，不是强一致）。

### 6.7 窗口渲染（Layer B）：**只追加，到阈值才整体折叠一次**

> 这一节在调研后做了修正：原稿写的是"滑动窗口"，但滑动窗口**每来一条消息都会改变前缀**，等于每轮都作废一次缓存。LlamaIndex 的 `Memory` 用的是"追加到比例上限 → 批量冲刷"，Claude Code 用的是"只追加、偶尔压缩一次"，两者一致（见 §17.3/§17.4）。

- `src/utils/message.ts` 的 `buildContextMessages` 按状态选择渲染：
  - COLD：`冷态窗口字数`（默认 5000 字）以内的条目以**骨架**渲染（每条 head 截断）+ 折叠块（**追加式**：只往里追加新行，不回写已有行）；
  - HOT/COOLING：最近 X token 全文 + 同一折叠块。
- **窗口策略（按字数，只追加）**：窗口**只追加**；当累计字数超过 `冷态窗口字数`（冷态，默认 5000 字）或 token 预算（热态，`min(上下文最大token, 模型窗口 × 0.7)`）时，触发**一次**整体折叠——把最旧的一批移出窗口并**追加**一条纯代码折叠记录（条数/时间范围/发言者/每条 head）。也就是说"破坏缓存的操作"从"每条消息一次"变成"每攒够一批一次"。
- 折叠块/摘要条目一律 **append-only + 挂原文锚点（原文库 id）**，永不就地重写；需要更正时新增一条并让旧条目标记失效（先例：SillyTavern 摘要挂消息 metadata 且可回滚、Mem0 的 ADD-only、Graphiti 的"时序失效而非删除"）。
- `context.messages` 只保留"窗口内 + 折叠块"，移出部分进原文库 → 每消息 `session.save()` 体积恒定。
- **检索注入位置**：若启用"按需检索历史"，注入点必须是**稳定段（system 之后的固定位置）或尾部（工具结果/新消息）**，绝不插进历史中间——SillyTavern 明确警告：动态提示源会重构前缀，"与缓存一起使用时向量化往往是反效果的，你必须二选一"。
- **折叠记录的格式**（追加式、纯代码生成，示例）：

  ```
  [折叠 12:03-12:41 · 7 位发言者 · 38 条 · 原文 read_raw kind=user blk:xxx]
  - 12:05 张三：今天几点开团，我先去吃饭…（head 40 字）
  - 12:09 李四：@bot 上次那个规则再说一遍（head 120 字，命中"@机器人"）
  ```
- **选择性保留**：折叠时对"@机器人 / 直接问句（以 ？吗 呢 结尾）/ 超过 200 字的长消息"保留更长的 head（如 120 字）或保留全文——先例：SillyTavern 保留最近 5 条不参与洗牌、Aider 按图/热度排序决定保留什么。
- **骨架渲染参数**：COLD 每条骨架的 head 截断为常量（默认 60 字）；折叠行 head 默认 40 字（命中上一条规则的放宽到 120 字）。

### 6.8 结算（Layer C）：水位 + 门槛 + 空闲三条件，两阶段，带上限

调研后本节从"按积压批量"细化为**三条件触发 + 两阶段 + 多类上限**（先例：Codex `memories` 的 `min_rollout_idle_hours`（建议 >12h）/`max_rollout_age_days`/`max_unused_days`/`max_rollouts_per_startup` 与 `phase_1_model`/`phase_2_model` 分工；LlamaIndex 的 `token_flush_size`；LangChain `SummarizationMiddleware` 的 `trigger`+`keep`+`trim_tokens_to_summarize`）。

- **触发条件（三者同时成立才结算）**：①待结算积压 ≥ `结算水位`（token，参考 LlamaIndex flush 3000）；②总上下文 ≥ `结算最小门槛`（token，低于门槛根本不动手——Claude Code 的地板是 10 万 token，我们按群聊体量下调）；③距上次交互 ≥ `结算空闲门槛`（秒/小时）。
- **两阶段**：阶段一用**便宜模型**做批次摘要，阶段二做合并/巩固（`use=summarization` 已支持按用途绑定不同模型）。
- **多类上限**：单次结算的 `单次结算调用上限`、单轮处理的候选批次数上限、积压条目 `保留天数`/`未使用天数`（超期直接淘汰，不再结算）。
- **时机选择（成本相关）**：①**缓存还热时做**——热缓存下摘要请求能复用前缀，"成本只是上下文大小暗示的一小部分"；冷缓存下摘要请求要把完整历史按未命中价重算（官方原话："This is why `/compact` costs the most when you resume an old session"）。因此**若已闲置超过缓存 TTL，就不要为了省 token 去结算**。②可选：把结算安排在**低峰时段或批量接口**（DeepSeek off-peak 为 peak 半价；Anthropic Batch = 0.5×）。
- 扩展 `MemoryManager.summarizeChunkWithRetry`（`src/memory/manager.ts:399-408`）实现上述预算与退避；失败按会话 + bank 指数退避（5/15/60 分钟），连续无实质进展则**熔断**（同 §6.2）。
- 保持现有 `consolidate` → 观察合成（每簇 1 次 LLM）语义不变；**注意：归档路径本就不含心智模型刷新**（刷新只在 `.ai memo` 指令与记忆工具入口，见 §14 证据 E7），本文不改这一点。
- **与状态机的一致性**：结算由 `needSettle` + `settleWatermark` 驱动（§5.6.4）——进入 COLD 时标记，在下次任何活动时补算；`冷态结算间隔` 只作为"提前结算"的可选加速，不是唯一触发。
- **摘要 prompt 的调法**：先最大化**召回**（不漏信息），再迭代**精确率**（压长度）；官方警告"过度压缩会丢掉重要性后来才显现的细节"。结算 prompt 还应加入一条群聊特化约束（借自 Amp 的 `read_thread`）：**"不要停在第一个相关命中，要检查后续消息是否修订/推翻/更正了前面的说法"**。

### 6.9 账本与命令（修 M12/M15）

- **先修用量采集**（M15）：`src/model/adapter.ts:50-60` 的 `extractUsage` 补缓存字段——OpenAI 的 `prompt_tokens_details.cached_tokens`、DeepSeek 的 `prompt_cache_hit_tokens`/`prompt_cache_miss_tokens`、Anthropic 的 `cache_read_input_tokens`/`cache_creation_input_tokens`；并让 Anthropic 方言的 `prompt_tokens = input + cache_read + cache_creation`（现在少算缓存读取，导致 `TokenCalibration` 系数向 0.5 漂移、本地预算被放大到约 2 倍）。

- 日志：压缩被门禁拒绝、**压缩熔断**、结算降级、超长被拒、归档未完成，各打一条可 grep 的 `[ctx-cost]` 标记。

### 6.10 缓存友好性：为什么"批量改写历史"是最贵的操作

这条是本次调研最重要的补充（依据见 §17.1/§17.5）：

1. **前缀缓存的匹配是精确匹配**：请求开头（前缀）中任何位置的改动，都会让它**之后的全部内容**重新计算；没有按段/按文件的缓存。
2. 本项目现状恰好违反这一条：合并压缩把同一个 `user` 消息块的**内容整体重写**（`src/context/context.ts:267-273`），而这个块在待机群里常常是历史里**最早、也是唯一**的块。于是每次重压不仅花一次压缩调用的钱，还会让**其后所有历史在下一轮请求里全部失去缓存**（按未命中价重算）——**"白耗"的真实量级远大于压缩调用本身**。
3. 由此得到三条工程规则（也是本方案的设计约束）：
   - **只追加，不改写**：历史一旦写入不再修改；窗口只做"移出"，原文进原文库，绝不做"就地重写"。
   - **破坏缓存的操作要批量做**：压缩/结算合并为一次（先例：Claude Code 移除最旧图片时按批处理，避免每张图一次未命中）——对应本项目就是"按积压批量结算"，而不是每条消息一次。
   - **在自然边界结算**：Claude Code 的 idle compaction 在 1 小时缓存 TTL 的第 ~54 分钟（缓存过期前）执行，理由是"缓存还热时，压缩请求自身能命中缓存；缓存已冷再做，摘要请求要把完整历史按未命中价重算"。本项目的对应边界是：**转冷时**（对话结束、窗口即将冻结）与**积压够多时**。
4. **摘要本身是一次大请求**：Claude Code 成本文档明确"压缩大上下文本身就是一次大请求"，而"想要干净重来"时清空（`/clear`）不花钱。这支持本方案的降级顺序——**COLD 下优先纯代码折叠/丢弃，只有在确实需要连续性时才付 LLM 摘要**。

### 6.11 固定开销分解（写进账本）

请求体的固定部分（system prompt、预设上下文、tools JSON）每轮都要重发，属于"必然成本"：本项目已经用「工具按需加载」把它压过一轮（核心 8 个工具常驻 + `search_tools`/`call_tool` 调度，system prompt 从约 2 万字符降到约 2800 字符，见 `src/changelog.ts:461`、`src/tool/tool.ts:25-37`）。因此 `.ai ctx` 应把账本拆成：

```
固定：system=<n> + 预设上下文=<n> + tools JSON=<n>
窗口：COLD 骨架（≤ `冷态窗口字数` 5000 字）/ HOT 全文（≤ token 预算）
折叠：窗口外摘要=<n>
其他：记忆注入=<n> + 知识库=<n>
缓存：本轮 cache 命中=<n> / 未命中=<n>（API usage 提供）
```

对应先例：Claude Code 的 `/context` 提供按类别的实时分解与优化建议，`/usage` 的 `Prompt cache (main)` 行给出"请求数 · 命中占比 · 未命中次数 · expected rebuild · warm/cold + TTL"。本项目可直接读 API 返回的缓存 token 字段（DeepSeek 的 cache hit/miss、OpenAI 的 `prompt_tokens_details.cached_tokens`）填最后一行。

### 6.12 judge 路径的上下文同样必须走窗口渲染（修 M16）

- 现状：`buildHistory`（`src/judge/judge_manager.ts:386-408`）按"最近 N 条消息"收集并用 `buildContent` **整条**渲染；待机群里所有消息是同一条消息，因此 judge 的 prompt 可能带上整个待机块。gate 只限次数（默认 ≤20 次/小时，`src/config/configs/trigger.ts:41`），**不限单次体积**。
- 修复：judge 的历史收集改为**复用 §6.7 的窗口渲染**（COLD 骨架 / 折叠块），或对渲染结果加字数上限（复用 `冷态窗口字数`）。
- 账本：`.ai ctx` 与 `.ai tk` 的用途维度要能显示 `judge` 的调用次数与累计 token（用途维度已含 `judge`）。
- **"COLD 零 LLM"的例外要写明**：judge 评分本身就是"决定要不要转热"的探针，因此 COLD 下仍会调用（受 gate 次数上限 + 本次新增的单次体积上限约束）。若希望 COLD 严格零 LLM，可把 judge 的 gate 收紧为"仅 @机器人 / 消息密度达标时才评分"（P2 可选项）。

#### 7.2.1 决策记录：为什么不做"默认自动"

- 该参数是本方案的**核心预算旋钮**，同时决定 ①请求前裁剪（`applyTokenBudget`，`src/utils/message.ts:280-315`）②归档/结算触发（`archiveByTokenIfNeeded`，`src/context/context.ts:419-449`）。方案不改它的地位，只讨论"默认值怎么给"。
- **"自动"的前提是能知道模型窗口，而插件现在拿不到**：
  - `/models` 只解析 `data[].id`，不取窗口字段（`src/model/list.ts:2-3`）；
  - 模型能力分类只管 text/vision/embed/gen/tts，不含窗口（`src/model/catalog.ts`）；
  - **唯一来源是被模型拒绝时报错里的数字**（`parseMaxContextTokens`，`src/model/api_error.ts:214-233`）——即"第一次必然要错一次"。
- 三案对比（保留为决策记录）：

| 方案 | 默认 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A | `0 = 自动` = min(探测窗口 × 0.8, 硬上限) | 换模型自动跟随 | 无可靠窗口来源；`0` 的含义从"无效值"变成"自动"；首次仍可能被拒 | **不采用** |
| **B** | 保持 `1000000` + 超窗告警 | 不动默认语义、改动最小 | 该参数本身仍形同虚设 | **采用**（有界性改由字数折叠线提供） |
| C | 改成 `100000` + 超窗告警 | 配置框直观 | 对 1M 窗口模型浪费、对 32k 模型仍偏大 | 备选 |

- 采用 B 后，"一次发出几十万 token"由 **§5.4/§6.7 的字数折叠线**解决：冷态窗口 ≈5000 字、热态窗口按 token 预算 → 请求体天然有界。
- `.ai ctx` 仍显示"已知窗口（来源：报错探测，128k）"与"当前预算 1000000（未受限）"，让用户判断这个数字是否合理。
- 可选增强（P2，需另行确认）：把 `/models` 返回里若存在的 `context_length` 类字段读进来；或提供 `模型上下文窗口` 手填项。

### 10.2 技能用例（`skills/aiplugin4-test-suite/references/`）

- 新增 `CTX-xx`：`.ai ctx` 快照（COLD/HOT 两种状态）；

### 10.3 真机验收口径

1. 待机群灌 500 条消息（含事件），观察 `[ctx-cost]` 日志与 `.ai tk` 用途视图：compression/summarization 调用应为 0（除按时间的批量结算）。
2. 期间触发一次对话：请求体 token ≤ `min(配置, 窗口×0.8)`；`[model-error] context_too_long` 出现次数 = 0。
3. 检查 `session_<id>` 存储体积不再随消息数线性增长（P1 后）。

## 13. 附录 A：成本模型

参数：压缩阈值 `T=2000` 字（中文 ≈1 token/字）；压缩输出 `O` 字；块大小 `B`。触发间隔 ≈ `T − O`，故

```
每 C 字入站流量的压缩调用数 ≈ C / (T − O)
单次调用 ≈ B(输入) + 50(提示词) + O(输出)
```

按待机群 20 条/分（≈30k 字/时）与 100 条/分（≈150k 字/时），**每群每小时**：

| 场景 | O=1000（压缩有效） | O=1900（无上限的坏情况） |
| --- | --- | --- |
| 20 条/分 | ≈30 次调用；≈75k 输入 + 30k 输出 | ≈300 次调用；≈870k 输入 + 570k 输出 |
| 100 条/分 | ≈150 次调用；≈375k 输入 + 150k 输出 | **≈1500 次调用；≈4.3M 输入 + 2.9M 输出** |

叠加的一次性开销：

- **归档单块**：50k token 输入 × 最多 3 次重试 = 最高 150k 输入/块；再加每条 fact 的 embedding 调用、每簇 1 次观察合成 LLM。
- **超长被拒的一次请求**：待机上下文积累到多少就先发多少（默认 1e6 上限下可能数十万 token）。

> 换算成金额时按各家实际单价计算；上表只给出 token 量级，避免绑定特定供应商价格。

### 17.1 编码代理先例：Claude Code（官方文档已核对）

Claude Code 是"长会话 + 昂贵上下文 + 必须自动压缩"这一问题的成熟工业实现，其机制与本方案的每一项决策都能对上。

| 机制 | 具体事实（含阈值） | 出处 |
| --- | --- | --- |
| 自动压缩窗口 | `autoCompactWindow` 取值 `100000`~`1000000` token，**上限受当前模型上下文窗口约束**；默认不设 → "按模型调优的窗口"；`/autocompact 500k` 可显式设定 | `ccdocs/settings-reference.md:2776-2791`、[context-window](https://code.claude.com/docs/en/context-window) |
| 空闲压缩 | `idleCompaction` 默认开；条件：交互式会话 + 会话处于 **1 小时缓存 TTL** + 上下文 ≥ **200000** token（阈值可调，下限 `100000`）+ **距上次请求约 54 分钟且机器醒着**；设计理由原文是"在 prompt cache 过期前不久压缩" | `ccdocs/settings-reference.md:2964-3004` |
| 压缩后"什么活下来" | system prompt / 输出风格继续生效；项目 `CLAUDE.md`、无作用域规则、自动记忆**从磁盘重新注入**；git 状态重读；计划重注入；路径作用域规则与嵌套 `CLAUDE.md` **按需重载**；最近修改的**至多 5 个文件重读**（单文件 >5000 token 只回路径引用）；调用过的 skill 正文重注入（**每个上限 5000 token、总上限 25000**，最旧的先丢）；后台任务继续跑；hook 注入的内容随对话一起被摘要掉 | [context-window#what-survives-compaction](https://code.claude.com/docs/en/context-window) |
| 摘要保留什么 | 用户请求与意图、关键技术概念、查看/修改过的文件与关键代码片段、错误与修复方式、待办、当前工作；**逐字对话被替换，完整工具输出与中间推理丢失** | 同上 |
| 压缩与缓存 | "压缩**按设计**会使对话层失效，因为下一个请求拥有更短的新历史，与旧历史不共享前缀"；摘要请求复用同一前缀，**缓存热时压缩成本只是上下文大小暗示的一小部分**，缓存冷时（恢复旧会话）最贵 | [prompt-caching#compacting-the-conversation](https://code.claude.com/docs/zh-CN/prompt-caching) |
| 缓存匹配规则 | "匹配是**精确**的，因此前缀中**任何位置**的更改都会重新计算其后的所有内容。没有按文件或按段的缓存"；请求按"system → 项目上下文 → 对话"分层排列，对话层只追加即可保住前两层缓存 | 同上 |
| 截断优于摘要 | `/rewind` 把对话截断回较早轮次时，**剩余历史与当年构建缓存时的内容相同**，因此能命中更早的缓存条目；而压缩是构建全新前缀 | 同上 |
| 破坏缓存的操作要批量 | 移除最旧的图片/PDF 时**一批一批移除**，"你会看到每批一个较慢的轮次，而不是每张新截图一个" | 同上 |
| 压缩即大请求 | 成本文档明确："`/compact` 会读取它要摘要的对话，**压缩一个大上下文本身就是一次大请求**"；"想要干净重来"时 `/clear` 不花钱 | [costs#why-usage-climbs](https://code.claude.com/docs/en/costs) |
| 可观测性 | `/context` 给出按类别的实时分解与优化建议；`/usage` 的 `Prompt cache (main)` 行：`14 requests · 91% of input tokens from cache · 2 misses · 1 expected rebuild (compaction or tool-result clearing) · warm (1h TTL, last activity 40s ago)` | 同上、[context-window#check-your-own-session](https://code.claude.com/docs/en/context-window) |
| 压缩会替换缓存内容 | hook 输入字段 `prompt_cache_likely_expired` 的定义包含"或**之后的压缩替换了被缓存的对话**" | `ccdocs/hooks.md:1246` |

**对编码代理场景的适用性差异（必须承认的边界）**：编码代理有明确的任务边界（一次任务结束就是天然压缩点），而群聊是**无边界、持续流入**的；因此本方案不能照抄"任务间压缩"，而要引入 **COLD/HOT 状态**来制造边界——这正是 §5 存在的理由。

### 17.6 本项目内既有先例（同一原则已经落地过）

本方案不是新理念，而是把一个**已经在本项目验证过**的原则从"工具"扩展到"消息历史"：

| 已落地 | 事实 | 出处 |
| --- | --- | --- |
| 工具按需加载 | 核心 8 个工具常驻（`list_tools`/`search_tools`/`list_mcps`/`call_tool`/`use_skill`/`call_ob11_api`/`run_ext_command`/`run_core_command`），其余工具靠 `search_tools` + `call_tool` 调度；**system prompt 从约 2 万字符降到约 2800 字符** | `src/tool/tool.ts:24-37`、`src/changelog.ts:461` |
| 工具回调不再压缩 | 超长工具结果改为 head 截断 + `rawText` 保留原文，**不再调用压缩智能体** | `src/context/context.ts:383-409`、`src/changelog.ts:105` |
| 事件文本不再压缩 | 事件提示词由纯代码模板生成，超长仅 head 截断兜底 | `src/pipeline.ts:568-570`、`src/changelog.ts:100` |
| 原文检索工具 | `read_raw` / `grep_raw` 按 `kind`（tool/user/image/event）按需回读完整原文，原文不参与渲染与 token 估算 | `src/tool/tools/raw/tool_raw.ts:1-30` |

结论：**"原文留档 + 展示层只给必要部分 + 需要时按需回读"已经是本项目的既定取向**；唯一还没跟上的是"用户消息历史"这一块——本方案补上它。

### 17.8 明确不建议照搬的做法

| 做法 | 为什么不照搬 |
| --- | --- |
| **水位线式触发（90% / 200K / 967K）** | 编码代理有任务终点（做完 `/clear`），群聊是**无限消息流**；堆到 90% 再压意味着整个待机期都在付全量 token。我们的水位必须由**成本预算**决定，且 COLD 应零 LLM |
| **"压缩后继续干同一件事"的假设** | 编码代理压缩后要接着完成任务，所以"保留 plan/待办/错误修复"有价值；群聊压缩后机器人可能只回一句闲聊。**不应为"保持任务连续性"付费** |
| **"最近 N 个修改文件"式对象回填** | 群聊的相关性由**社交关系与话题**决定，不由"最近修改时间"决定；Aider 的图/热度排序比"最近优先"更接近 |
| **对摘要再摘要（递归压缩）** | Wu et al. 2021 自承 compounding errors；Findings of ACL 2025 指出递归合并放大幻觉；五步链实证退化。标准解法是**分层 + 每步接地原文 + 原文永久保留** |
| **"每条消息一次 LLM"** | A-MEM 正是该路线：对抗类 F1 50.03 < 基线 69.23；Mem0 逐条抽取 Judge 66.88 < 全上下文 72.90 且**写入成本未计入** |
| **GPTCache 式语义缓存用于群聊主链路** | 假阳性/假阴性、淘汰仅 LRU/FIFO；`temperature=2` 必跳过缓存（与回复多样性冲突）；生成缓存 key 还要**额外调用摘要模型** |
| **让模型逐条判断"值不值得记"** | 官方批评"推理该存什么会影响 agent 延迟"；Letta 的 agent 自主 archival 前提是单人任务 agent，群聊无任务目标 → 应改为**规则/阈值触发批量结算** |
| **旧版"摘要替换历史"类 API 语义** | LlamaIndex `ChatMemoryBuffer` 已标废弃、LangChain 旧 memory 参数已废弃；照搬旧语义＝照搬已被放弃的设计 |
| **KV 淘汰类机制（StreamingLLM / H2O）** | 需要控制模型内部 KV cache 与注意力，**闭源 API 无法落地**；仅作"小窗口 + 检索"的方向性支持 |
| **"换个便宜模型继续同一条对话"** | 会重建该模型的前缀缓存（官方举例：Opus 到 100k token 时切 Haiku **更贵**）；要省钱应走**独立前缀**的用途模型/子代理，而不是换 chat 模型 |
