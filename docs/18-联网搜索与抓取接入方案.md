# 18 - 联网搜索与抓取接入方案（已实现 P0）

> 状态：**已实现（P0，4.27.0）**。配置生成器同步上线；插件侧 `src/web/` + 「联网」页 + `web_search`/`web_fetch` 已落地，单测见 `scripts/unit-test-web.ts`。托管搜索（§6.8）为调研存档、本期未实现。
>
> 目标版本：4.27.0。

## 1. 背景

DeepSeek 已上线独立的 **Search / Fetch API**（自研搜索引擎，按次计费），见
[官方指南](https://api-docs.deepseek.com/zh-cn/guides/search/) 与
[Search API 参考](https://api-docs.deepseek.com/api/search/)：

| API | Endpoint | 关键参数 | 返回 |
| --- | --- | --- | --- |
| Search | `POST https://api.deepseek.com/v1/tools/search` | `query`（必填，≤128 字）、`count`（1~50，默认 10）、`ori_question`、`localization`、`need_content`（默认 false） | `results[]`：`title / url / snippet / summary / content / date / site_name / rerank_score / authority` |
| Fetch | `POST https://api.deepseek.com/v1/tools/fetch` | `url`（必填，http/https） | `title` + `content`（Markdown 正文） |

- 鉴权：`Authorization: Bearer <DeepSeek API Key>`，错误为 OpenAI 兼容格式。
- 计费：Search / Fetch 各 5 元 / 1000 次**成功**请求（只有 HTTP 200 且产生结果才计费）。
- 限速：Search / Fetch 各 5 QPS（账号级，与 API Key 无关）。

插件目前只有 `web_search`，且**写死 SearXNG**；趁此机会把「搜索/抓取」做成可插拔的接入层，而不是再为 DeepSeek 加一条硬编码分支。

## 2. 现状与差距

`src/tool/tools/web/tool_web.ts`（当前唯一联网工具）：

- 固定 `GET {联网搜索}/search?q=...&format=json&pageno=...`，解析 `results[].title/content/url/score`；
- 把一页拆成两个「半页」做 `page` 映射（SearXNG 特有逻辑）；
- 配置只有「后端 → 联网搜索」一个 URL，无 key、无多提供商、无抓取能力；
- 换 DeepSeek 需要改代码 → 想支持更多厂商会继续堆分支。

可复用的既有能力：

- `src/utils/web.ts` 的 `fetchData` / `withTimeout` / `ApiError`（超时、HTTP 错误分类、Retry-After）；
- `src/model/media.ts` 的 `getByPath`（`a.b.0.c` 取数路径，可直接用于 generic 方言的响应映射）；
- v5 模型配置的「provider + dialect + baseURL + apiKey + request 覆盖」思路，本方案沿用同一套哲学。

## 3. 目标与非目标

**目标**

1. 一套工具接口（`web_search` / `web_fetch`），背后可接多个搜索/抓取后端；
2. **配置级泛化**：新厂商优先用 JSON 描述（generic 方言 + 取数路径）接入，不改代码即可用；
3. **全部兼容**：内置 DeepSeek / SearXNG / Kimi / Brave / Tavily / Serper / 博查 / 智谱 / Exa / Firecrawl 十家方言（格式见 6.7），其余厂商走 generic；模型厂商的**托管搜索**见 6.8；
4. 归一化返回结构，工具层与厂商无关；有序路由 + 失败回退；
5. 保持 `web_search` 工具名与现有 SearXNG 配置兼容，升级不破坏线上。

**非目标（本期不做）**

- 结果缓存 / 去重（P2 可选）；
- 模型侧 server-side search tool（DeepSeek 对话接口内的那段逻辑不在插件控制范围）；
- WebUI 管理页（配置走「联网配置」JSON；可视化交给配置生成器，见 6.6）；
- 搜索引擎的网页摘要再加工（不做二次 LLM 总结，避免额外成本）。

## 4. 设计总览

```
工具层   web_search / web_fetch          （src/tool/tools/web/）
            │  只吃归一化请求/返回
服务层   WebService                      （src/web/service.ts）
            │  路由选择 / 失败回退 / 归一化 / 截断
适配层   dialect: deepseek / searxng / generic / …   （src/web/dialects/*）
            │  请求体构造、响应取数、错误文案
HTTP 层  withTimeout + fetch + ApiError  （复用 src/utils/web.ts + api_error.ts）
```

与「模型 v5」的关系：同一套 provider 配置哲学，但**独立页签、独立 JSON**（模型配置只服务对话/媒体，不掺搜索）。

核心取舍：**「方言」= 内置的通用适配器 + 一份预设数据**。DeepSeek / Tavily / Bocha 等都用同一台引擎（请求模板 + 响应路径映射）跑，generic 就是「用户自己写这份数据」；只有 SearXNG 因分页语义特殊保留少量代码分支。

## 5. 归一化数据模型

```ts
/** 单条搜索结果：字段缺失 = undefined/空串，渲染时跳过 */
interface WebSearchItem {
  title: string;
  url: string;
  snippet?: string;   // 短摘要（列表展示用）
  summary?: string;   // 长摘要（给模型读，DeepSeek 600~800 字）
  content?: string;   // 网页正文（need_content / content 详情时）
  date?: string;      // RFC3339
  site?: string;      // 站点名
  score?: number;     // 相关度（各厂商语义不同，仅作参考）
}

interface WebSearchResponse {
  provider: string;   // 实际命中的 provider id
  query: string;
  results: WebSearchItem[];
  attempts: string[]; // 失败过的 provider 及原因（成功时为空）
}

interface WebFetchResponse {
  provider: string;
  url: string;
  title: string;
  content: string;    // Markdown
  format: 'markdown' | 'text';
}
```

## 6. 配置

### 6.1 位置

新增配置页签 **「联网」**（`src/config/configs/web.ts`），内含单个 JSON 配置项 **「联网配置」**。页签顺序放在「工具」之前（它属于工具能力的依赖项）。

> 为什么不塞进「后端」：后端页是各后端服务 URL 的散装清单，与「多 provider + 密钥 + 路由」不是一类配置；也不塞进模型 v5 JSON，避免把对话模型与搜索后端耦合。

### 6.2 Schema v1（尽量小）

原则：**能省的全省**。`version` / `defaults` / `routes` 全部可省略；内置方言自带 `baseURL`，也可省略。
DeepSeek 手写最小配置只有 3 行：

```jsonc
{ "providers": [ { "dialect": "deepseek", "apiKey": "sk-..." } ] }
```

SearXNG 只需 `{ "providers": [ { "dialect": "searxng" } ] }`（沿用现有默认地址）。

完整形态（生成器输出，所有可选项）：

```jsonc
{
  "version": 1,
  "defaults": {
    "count": 5,              // 工具默认返回条数（1~50）
    "detail": "summary",     // snippet | summary | content
    "timeout": 20,           // 单次请求超时（秒）
    "maxContentChars": 4000, // 单条正文截断
    "fallback": true         // 失败时是否按 routes 顺序换下一个
  },
  "providers": [
    { "id": "deepseek", "dialect": "deepseek", "apiKey": "sk-xxxx" },
    { "id": "searxng",  "dialect": "searxng" }
  ],
  "routes": { "search": ["deepseek", "searxng"], "fetch": ["deepseek"] }
}
```

字段说明：

| 字段 | 必填 | 缺省 | 说明 |
| --- | --- | --- | --- |
| `version` | 否 | `1` | 不匹配则整体拒绝并报错 |
| `defaults.count` | 否 | `5` | 工具默认条数，钳制 1~50 |
| `defaults.detail` | 否 | `summary` | `snippet` / `summary` / `content` |
| `defaults.timeout` | 否 | `20` | 秒 |
| `defaults.maxContentChars` | 否 | `4000` | 单条正文截断 |
| `defaults.fallback` | 否 | `true` | 失败时换下一个 provider |
| `providers[].id` | 否 | `dialect`（同方言多个时必填） | 路由引用键 |
| `providers[].dialect` | 是 | — | `deepseek` / `searxng` / `generic` / 后续内置名 |
| `providers[].baseURL` | 否 | 方言内置（generic 必填） | 基础地址；端点路径由方言决定 |
| `providers[].apiKey` | 按方言 | — | 占位符 `sk-xxxx` 视为**未配置**：跳过并提示，不发注定 401 的请求 |
| `providers[].enabled` | 否 | `true` | 显式列出即启用 |
| `providers[].headers` / `.timeout` | 否 | — | 额外请求头 / 覆盖 `defaults` |
| `providers[].search` / `.fetch` | 否 | 方言内置 | 该 provider 的参数覆盖（`count`、`need_content`、`categories`、generic 描述符） |
| `routes.search[]` / `routes.fetch[]` | 否 | providers 顺序 | 尝试顺序；不写就按 provider 出现顺序 |

> 多 provider 的常见情形不用写 `routes`：**provider 出现顺序就是尝试顺序**。`routes` 只在「搜索顺序与抓取顺序不同」时才需要。

### 6.3 泛化：generic 方言

任何「POST/GET + JSON 返回」的搜索 API 都能用 generic 接入，**不需要改代码**：

```jsonc
{
  "id": "my-search",
  "dialect": "generic",
  "baseURL": "https://api.example.com",
  "apiKey": "xxx",
  "search": {
    "method": "POST",
    "path": "/v1/search",
    "headers": { "X-API-Key": "{apiKey}" },
    "body": {
      "q": "{query}",
      "limit": "{count}",
      "full": "{need_content}"
    },
    "results_path": "data.items",          // 复用 getByPath（a.b.0.c）
    "fields": {
      "title": "name", "url": "link",
      "snippet": "description", "summary": "abstract",
      "content": "body", "date": "published_at",
      "site": "source", "score": "rank"
    },
    "error_message_path": "message"
  },
  "fetch": {
    "method": "GET",
    "path": "/reader?url={url}",
    "response_type": "json",               // json | text
    "title_path": "title",
    "content_path": "content"
  }
}
```

可用占位符：`{query}` `{count}` `{need_content}` `{page}` `{offset}` `{site}` `{time_range}` `{ori_question}` `{apiKey}` `{baseURL}`。
整值占位符（如 `"limit": "{count}"`）保留原始类型（数字/布尔），混合串按字符串拼接；值为空时该键省略（与媒体模板的渲染语义一致）。

请求体渲染在 `src/web/template.ts` 自实现（约 40 行），**不**直接 import `model/media_template`（避免 model ← web 的反向依赖）。

### 6.4 DeepSeek 方言映射

| 归一化 | DeepSeek 请求/响应 |
| --- | --- |
| `query` | `query`；`{site}` 转 `site:域名`，`{time_range}` 转 `after:YYYY-MM-DD`，都追加进 query 字符串 |
| `count` | `count`（钳制 1~50，默认 10 → 插件默认取 `defaults.count`） |
| `detail=content` | `need_content: true`，取 `content`（空则退 `summary` → `snippet`） |
| `detail=summary` | `need_content: false`，取 `summary` |
| `detail=snippet` | `need_content: false`，取 `snippet` |
| `ori_question` | 可选；P1 从会话当前用户消息自动截取 128 字填入 |
| 返回 | `results[]` → `title/url/snippet/summary/content/date/site_name/rerank_score` |
| Fetch | `POST {baseURL}/v1/tools/fetch`，body `{url}` → `{title, content}` |
| 错误 | OpenAI 兼容 `{error:{message,...}}`；402 余额不足、403 抓取被拒、404 抓取不到正文 |

> `baseURL` 建议 `https://api.deepseek.com`，端点路径 `/v1/tools/search`；若沿用模型页的 `https://api.deepseek.com/v1`，方言内部做「已含 /v1 则不重复拼接」的归一化。

### 6.5 SearXNG 方言映射（兼容现状）

- 保持 `GET {baseURL}/search?q&format=json&pageno&categories&time_range` 与**半页拆分**逻辑（`page` 映射拆到适配器里，工具层不再感知）；
- `content` 既是短摘要也是唯一正文来源：`snippet = content`，`summary` 同；`score` 取 `score`；
- 无 key；错误多为非 JSON，按文本截断报错。

### 6.6 配置生成器（aiplugin4-config）新增「联网搜索」分区

生成器是独立仓库（本地同级 `../aiplugin4-config`，零依赖静态页），目前只服务模型配置。给它加一个同级分区，用户就不用手写 JSON：

**布局**

- 顶部一级切换：`模型配置` / `联网搜索`（两个 tab，各自独立状态、独立输出与复制按钮，互不干扰）。
- 联网 tab 左侧：
  - **Provider 卡片列表**：方言、主机、Key 掩码、启用开关；上下移即调整顺序（= 默认路由顺序）。
  - **编辑面板**：接入方式（`DeepSeek` / `SearXNG` / `自定义 generic`）；预设自动填 `baseURL`，只需填 Key；高级折叠（`timeout`、额外 `headers`、默认 `count` / `need_content`）；generic 模式填 HTTP 方法/路径、body 模板（JSON 编辑器 + 占位符提示）、响应取数映射（`results_path` + 字段表单）、错误路径、抓取端点。
  - **默认项**：`count` / `detail` / `timeout` / `maxContentChars` / `fallback`。
  - **搜索/抓取顺序**：默认按卡片顺序；只有需要不同顺序时才出现 `routes` 编辑。
- 联网 tab 右侧：`联网配置` JSON 预览、校验问题、复制、下载、**导入**（粘贴已有联网配置反向填表）、遮蔽 Key。

**与插件的一致性**

- 生成器新增纯逻辑模块 `js/web.js`（`validate / build / serialize / maskKeys / parseImport`），规则与插件侧 `src/web/schema.ts` **一一对应**（同 v5 的 `js/v5.js` ↔ `schema.ts` 模式）；
- 跨仓库联测扩展 `scripts/integration-config-generator.mjs`：把生成器产出的联网 JSON 喂给插件的解析/校验层，钉住两侧不漂移；
- 生成器测试 `node tests/web-check.mjs`（构建 / 校验 / 导入往返 / 遮蔽 / 排序 / 序列化；默认紧凑、可格式化）；`tests/run.mjs` 继续跑模型用例。

### 6.7 内置方言矩阵（全部兼容）

以下格式均已按官方文档 / OpenAPI / 实际代码核实（来源见 6.7 末尾）。`baseURL` 为预设缺省值；
归一化字段含义见第 5 节（`title/url/snippet/summary/content/date/site/score`）。

| 方言 | 搜索端点 | 鉴权 | 搜索请求关键字段 | 搜索响应取数 |
| --- | --- | --- | --- | --- |
| `deepseek` | `POST {base}/v1/tools/search` | Bearer | `query` `count` `need_content` `ori_question` | `results[]`：`title` `url` `snippet` `summary` `content` `date` `site_name` `rerank_score` |
| `searxng` | `GET {base}/search?q&format=json&pageno` | 无 | `q` `pageno` `categories` `time_range` `language` | `results[]`：`title` `url` `content`→snippet `score` |
| `kimi` | `POST {base}/v1/tools/search`（Basic）或 `/v1/tools/search_pro`（Pro） | Bearer | `text_query` `limit`(≤20) `include_content` `timeout_seconds`；Pro 另支持 `sites` `time_window` | `search_results[]`：`title` `url` `site_name`→site `date` `snippet` `text`→content（`include_content=true`）；Pro 为 `chunks[]` |
| `brave` | `GET {base}/res/v1/web/search` | `X-Subscription-Token` | `q` `count`(≤20) `offset`(≤9) `country` `search_lang` `freshness` | `web.results[]`：`title` `url` `description`→snippet `page_age`→date |
| `tavily` | `POST {base}/search` | Bearer | `query` `max_results`(≤20) `search_depth` `include_domains` `exclude_domains` `topic` `time_range` `include_raw_content` | `results[]`：`title` `url` `content`→snippet `score` `raw_content`→content `published_date`→date |
| `serper` | `POST {base}/search` | `X-API-KEY` | `q` `num` `gl` `hl` `location` | `organic[]`：`title` `link`→url `snippet` `position`；另有 `knowledgeGraph` / `peopleAlsoAsk` / `relatedSearches` |
| `bocha` | `POST {base}/v1/web-search` | Bearer | `query` `count`(≤50) `summary` `freshness` `include` `exclude` | `data.webPages.value[]`：`name`→title `url` `snippet` `summary` `siteName`→site `datePublished`→date |
| `zhipu` | `POST {base}/web_search` | Bearer | `search_query` `search_engine`(默认 `search_std`) `search_intent` `count`(≤50) `search_recency_filter` `search_domain_filter` `content_size` | `search_result[]`：`title` `link`→url `content`→snippet `media`→site `publish_date`→date |
| `exa` | `POST {base}/search` | `x-api-key` | `query` `numResults`(≤100) `type` `contents.text` `includeDomains` `excludeDomains` `startPublishedDate` | `results[]`：`title` `url` `text`→content `highlights`→snippet `score` `publishedDate`→date `author` |
| `firecrawl` | `POST {base}/search` | Bearer | `query` `limit`(≤100) `tbs` `location` `scrapeOptions.formats=["markdown"]` | `data[]`：`title` `url` `description`→snippet `markdown`→content |

抓取（`web_fetch`）支持情况：

| 方言 | 抓取端点 | 取数 |
| --- | --- | --- |
| `deepseek` | `POST {base}/v1/tools/fetch` `{url}` | `title` + `content`（Markdown） |
| `kimi` | `POST {base}/v1/tools/fetch` `{url}` | `title` + `markdown` |
| `tavily` | `POST {base}/extract` `{urls:[url]}` | `results[0].raw_content` |
| `exa` | `POST {base}/contents` `{urls:[url], text:true}` | `results[0].text` |
| `firecrawl` | `POST {base}/scrape` `{url, formats:["markdown"]}` | `data.markdown` |

其余方言（searxng / brave / serper / bocha / zhipu）只参与搜索，不参与抓取。

**参数翻译（工具层 → 各方言）**：

- `allowed_domains` → tavily `include_domains`、exa `includeDomains`、zhipu `search_domain_filter`、bocha `include`、deepseek `site:`、firecrawl `site:`、kimi Pro `sites`；brave/serper 暂不映射（仅在 query 里保留 `site:`）；
- `blocked_domains` → tavily `exclude_domains`、exa `excludeDomains`、bocha `exclude`、deepseek `-site:`；
- `time_range` → searxng `time_range`、tavily `time_range`、bocha `freshness`、zhipu `search_recency_filter`、firecrawl `tbs`、kimi Pro `time_window`；brave 映射 `freshness`（pd/pw/pm/py）；exa 映射 `startPublishedDate`；
- `count` → 按各 API 上限钳制（brave ≤20、tavily ≤20、kimi ≤20、bocha/zhipu ≤50、exa/firecrawl ≤100、deepseek ≤50）；
- `detail=content` → deepseek `need_content:true`、kimi `include_content:true`、tavily `include_raw_content:true`、firecrawl 必带 `scrapeOptions.formats`、exa `contents.text`；其余方言退回 `snippet/summary`。

**未内置、走 generic 的**：Jina Reader（`GET https://r.jina.ai/{url}`，响应纯文本 markdown，`response_type:"text"`）；Google Custom Search（`GET https://www.googleapis.com/customsearch/v1`，需 key+cx，可用 generic 的 `{apiKey}` + 额外参数）；Bing Web Search 已下线，不再考虑。

### 6.8 模型厂商自带的托管搜索（server-side）

> **状态：调研存档，本期不实现。** 结论：插件已有 `web_search` 工具（客户端搜索），模型能通过它正常联网；厂商托管搜索只影响「模型自己是否内置搜索 + citations」，不是必需能力。等有明确需求再接入（Anthropic/xAI/Qwen 成本低，OpenAI/Gemini 需补协议）。

这类搜索**不是独立搜索 API**，而是模型厂商在对话请求里执行的「服务端工具/开关」：搜索、读页、引用都在厂商侧完成，返回的是带 citations 的对话结果。因此它们不进「联网配置」的 providers，而是**模型请求参数**（v5 的 `models[].request.body` 或专门的 `serverTools` 字段）。

| 厂商 | 开启方式 | 响应里的搜索产物 | 插件现状/可行性 |
| --- | --- | --- | --- |
| OpenAI | Responses API：`tools:[{"type":"web_search"}]`（`filters.allowed_domains`、`user_location`、`search_context_size`、`external_web_access`） | `web_search_call` 输出项：`action` = `search{query/queries,sources[]}` / `open_page{url}` / `find_in_page{pattern,url}`；正文带 `url_citation` 标注 | **受阻**：插件当前不支持 `openai-responses`，Chat Completions 无此工具 |
| Anthropic | Messages：`tools:[{"type":"web_search_20250305","name":"web_search","max_uses":3,"allowed_domains":[...]}]`；抓取用 `web_fetch_20250910` | `server_tool_use` + `web_search_tool_result`（`title/url/page_age/encrypted_content`）+ citations 块 | **可行（低成本）**：插件已走 `/messages`，只需注入 `tools` 并解析新块 |
| Gemini | 原生 `generateContent`：`tools:[{"google_search":{}}]` | `grounding_metadata`：`web_search_queries`、`grounding_chunks[].web{uri,title,domain}`、`grounding_supports` | **受阻**：插件走 OpenAI 兼容端点，需原生协议 |
| xAI (Grok) | 请求体 `search_parameters`：`mode`(auto/on/off)、`from_date`、`to_date`、`return_citations`、`max_search_results`、`sources`(web/news/x/rss) | `return_citations` 时返回引用来源（域名/链接） | **可行（低成本）**：OpenAI 兼容接口，body 注入即可 |
| Kimi | 旧的 `$web_search`（`builtin_function`）2026-10-20 退役；官方改为独立 `/v1/tools/search|search_pro|fetch` | 独立 API 的 `search_results[]` / `markdown` | **改用独立 API**（已作为 `kimi` 方言接入 6.7） |
| Qwen (DashScope) | OpenAI 兼容模式请求体 `enable_search: true`（可加 `search_options`）；原生 SDK 同名参数 | `search_info.search_results[]`（`title/url/site_name/index/...`） | **可行（低成本）**：body 注入 + 结果展平 |
| DeepSeek / 智谱 | 无对话内托管搜索，只有独立 Search/Fetch API | — | 已作为方言接入（6.7） |

**集成设计（建议）**：

- 在 v5 模型配置里加**每模型**的 `serverTools`（数组，按 `api` 方言解释），而不是复用通用 `request.body`：
  - `api: "anthropic-messages"` → `serverTools` 原样并入请求 `tools`（与插件自己的函数工具共存）；响应处理增加 `server_tool_use` / `web_search_tool_result` / `citations` 的解析与日志；
  - `api: "openai-completions"` → 支持 `xai`（`search_parameters`）与 `qwen`（`enable_search`）两种 body 注入；响应只取正文与 `citations`/`search_info`（可选写进系统提示或结果前缀）；
  - `api: "openai-responses"` → 需要先实现 Responses 协议（P2）；`gemini` 原生协议同理。
- **工具语义区别**：托管搜索由模型自己决定何时搜，插件的 `web_search` 工具对它不可见；两者可共存（模型自搜 + 需要结构化结果时再调 `web_search`），但会有重复计费风险，配置里应二选一或写明策略。
- **成本与上限**：Anthropic `max_uses`、xAI `max_search_results`、OpenAI `search_context_size`、Qwen `search_options` 都是防失控旋钮，生成器/文档要给出建议值。
- **展示**：托管搜索的 citations 只存在于模型响应里；插件当前只渲染正文。若要让 AI 引用来源，需要把 `url_citation` / `web_search_result` 转成上下文里的「来源」注记（P2）。

## 7. 路由、回退与错误处理

- 依次尝试 `routes.*` 中 `enabled` 且已配置（key 非占位）的 provider；
- 错误分类复用 `ApiError`：
  - `401/403` → 记录并**换下一个**（不重试本家）；
  - `402` → 余额不足，换下一个，日志 warning；
  - `429/5xx/网络/超时` → 当前 provider 退避重试 1 次（`Retry-After` 优先），仍失败则换下一个；
  - `400/422` 等参数错误 → **不换**，直接报错（属于配置问题，换家只会掩盖错误）；
- 全部失败 → 返回汇总文案（每个 provider 一行原因），并提示「联网」页配置；
- `defaults.fallback=false` 时只试第一个，便于排障；
- 每次调用日志：`provider / query / count / 耗时 / 是否回退`；不打印 apiKey；
- QPS：DeepSeek 5 QPS 是账号级共享，建议 P1 加「同 provider 最小请求间隔」配置（默认 250ms），本期至少文档提示。

## 8. 工具接口

### 8.1 `web_search`（保留名称，向后兼容）

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `query` | string | 必填；**兼容旧参数名 `q`**（两者任一） |
| `count` | integer | 1~50，默认取配置 |
| `offset` | integer | 结果偏移（分页）；`page` 传入时映射为 `(page-1)*count` |
| `detail` | string | `snippet` / `summary` / `content`，默认 `summary` |
| `allowed_domains` | string[] | 只保留这些域名（DeepSeek 转 `site:`） |
| `blocked_domains` | string[] | 排除这些域名（DeepSeek 转 `-site:`） |
| `site` | string | 单域快捷方式，等价 `allowed_domains: [site]` |
| `time_range` | string | `day/week/month/year`；DeepSeek 转 `after:`，SearXNG 走参数 |
| `page` | integer | 兼容旧用法（SearXNG 半页拆分），新代码建议 `offset` |

输出示例（保持旧格式的主体，补充日期/站点）：

```
搜索「DeepSeek V4 发布」：共 5 条（deepseek）
1. 标题：DeepSeek V4 模型发布
   链接：https://example.com/...
   摘要：……
   时间：2026-06-01 / 站点：Example News / 相关度：2.4
```

兼容处理：旧参数 `q` / `categories` / `time_range` 继续接受；`categories` 仅 SearXNG 生效；正文按 `maxContentChars` 逐条截断，整体仍走既有「工具响应截断字数」兜底。

> 不把 `provider` 放进模型可见的参数表：主流实现都没有这个参数，模型容易乱填。需要强制指定时走内部调用（`.ai web` 命令 / 测试），不进 tool schema。

### 8.2 `web_fetch`（新增）

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `url` | string | 必填，http/https |
| `max_chars` | integer | 可选，本次返回的正文长度上限（默认取 `maxContentChars`） |
| `start_index` | integer | 可选，从第几个字符开始返回；用于「上次被截断，继续读」 |
| `raw` | boolean | 可选，返回原始 HTML（默认 false，转 Markdown） |

输出：`标题：…\n来源：…\n\n<Markdown 正文>`；被截断时附 `[内容已截断，可传 start_index=N 继续]`。默认开启（只读）；归入「网页」工具组。

### 8.3 业界实现对照（2026-10 调研，非猜测）

调研对象（源码/官方文档）：

| 实现 | 形态 | 关键点 |
| --- | --- | --- |
| smolagents `WebSearchTool` / `ApiWebSearchTool` | 客户端 | 必填 `query`；DDG/Bing/Brave/Exa；返回 `## Search Results` + 编号 markdown；自带 1 QPS 限速 |
| MCP `brave-search` | 客户端 | `query` / `count`(1~20) / `offset`(≤9)；输出 `Title/Description/URL` 文本；local 无结果回退 web |
| MCP `fetch` | 客户端 | `url` / `max_length`(默认 5000) / `start_index` / `raw`；robots.txt + 拒绝私网 IP；HTML→Markdown；截断给下一步 index |
| OpenAI Agents SDK `WebSearchTool` | 服务端(hosted) | 声明 `type=web_search`；`filters.allowed_domains` / `user_location` / `search_context_size` / `external_web_access` |
| Anthropic `web_search_20250305` | 服务端(hosted) | `allowed_domains` / `blocked_domains` / `max_uses` / `user_location`；结果块含 `title/url/page_age/encrypted_content` + citations |
| Anthropic `web_fetch_20250910` | 服务端(hosted) | `allowed_domains` / `blocked_domains` / `max_content_tokens` / `citations` |
| Claude Code `WebSearch` / `WebFetch` | 服务端 | WebSearch：`query` + 允许/屏蔽域名 → `results` + 耗时；WebFetch：`url` + `prompt` + `offset` → 抽取结果 + bytes/code |
| LangChain `TavilySearch` | 客户端 | 参数极多（`include/exclude_domains`、`search_depth`、`topic`、`start/end_date`）；返回原始 dict；空结果抛 `ToolException` 并给建议 |
| CrewAI `SerperDevTool` | 客户端 | 只暴露 `search_query`；返回结构化 dict（organic / knowledgeGraph / peopleAlsoAsk / news） |
| LlamaIndex `TavilyToolSpec` | 客户端 | 返回 `List[Document]`（正文 + `url` metadata），交给框架序列化 |

由此归纳、并用于校准本方案：

1. **两种形态**：hosted（OpenAI / Anthropic / Claude Code，搜索与读页都在服务端，schema 只有域过滤/位置/上下文预算，结果带 citations）与 client-side（smolagents / MCP / 各框架，agent 运行时发 HTTP，返回文本）。DeepSeek 的 Search/Fetch 是裸 API，插件只能走 client-side。
2. **必填只有 query**；`count/max_results` 默认 5~10、上限 20~50；分页统一用 `offset`。
3. **域名过滤是标配**（allowed/blocked domains），时间范围是第二标配；`search_depth/topic` 只有 Tavily 这类富 API 有。
4. **search 与 fetch 分离**；fetch 侧统一 `url` + 长度上限 + `start_index` 续读，Claude Code 额外用 `prompt` 让服务端先抽取，Anthropic 用 `max_content_tokens` 控预算。
5. **输出以文本为主**：编号 + 标题/链接/摘要的 markdown 最通用；结构化（dict / Document）只在框架支持 artifact 时才有意义；hosted 工具返回结构化 citations 供正文标注。
6. **空结果必须给建议**（换宽泛查询 / 去掉过滤条件），不能返回空串（LangChain、smolagents 都这么做）。
7. **预算控制**：`max_uses`（单次请求最多搜几次）、`max_content_tokens`、`search_context_size`、客户端截断，四层都在防上下文爆炸。
8. **合规与安全**：自建抓取默认 robots.txt + 拒绝私网 IP（DNS 解析后校验）+ 自定义 UA；搜索侧普遍做 QPS 限速。

对应到本方案：参数表补齐 `offset` / `allowed_domains` / `blocked_domains`；`site` 降级为快捷方式；`detail` 默认 `summary`（业界默认只给摘要，正文交给 fetch）；fetch 增加 `start_index`；自建 generic 抓取方言必须做 robots + 私网拒绝（DeepSeek 由服务端代抓，风险低）；`provider` 不进模型 schema。P1 可借鉴 DSH 的 `queries[]` 多查询一轮，减少工具往返。

> 工具名保持 `web_search` 的另一个原因：`session.toolState` 按工具名持久化，改名会让所有人的开关状态失效。

## 13. 风险与待确认

**风险**

- **上下文成本**：`summary` 每条 600~800 字，10 条就是 8k 字符；默认 `count=5` + `summary`，`detail=content` 必须逐条截断；
- **抓取任意 URL**：DeepSeek 由服务端代抓，风险低；自建 Jina/Reader 类方言需注意内网 SSRF，文档标注；
- **密钥与计费**：DeepSeek 按次计费（5 元/1000），插件侧只记日志、不做账；误配置（如把搜索接到对话模型 key）要给出可读报错；
- **第三方 API 普遍要 key**：默认仍走 SearXNG，避免「升级后搜索直接不可用」。

### 14.2 关键接口

```ts
interface SearchInput {
  query: string; count: number; offset: number; detail: 'snippet'|'summary'|'content';
  allowedDomains?: string[]; blockedDomains?: string[]; timeRange?: string;
  page?: number; oriQuestion?: string;
}
interface BuiltRequest { method: 'GET'|'POST'; url: string; headers: Record<string,string>; body?: unknown; provider: string; }
interface DialectAdapter {
  dialect: string; defaultBaseURL: string; needKey: boolean; supportsFetch: boolean;
  buildSearch(baseURL, apiKey, input, provider): BuiltRequest;
  parseSearch(data, input): WebSearchItem[];
  buildFetch?(baseURL, apiKey, url, provider): BuiltRequest;
  parseFetch?(data, url): { title: string; content: string };
}
```

### 14.3 行为约定

- **provider 解析**：`routes.search` 缺省 = providers 顺序；跳过 `enabled:false`、key 为空且 `needKey`、key 为占位符 `sk-xxxx`；
- **回退**：某个 provider 失败（401/403/402/429/5xx/网络/超时）→ 记录原因并换下一个；`400/422`（参数/配置错）**不换家**，直接报错；429/5xx/网络在当前 provider 重试 1 次；
- **detail**：`snippet` 不取正文；`summary` 取长摘要（无则 snippet）；`content` 让方言请求正文（deepseek `need_content`、kimi `include_content`、tavily `include_raw_content`、exa `contents.text`、firecrawl 必带 `scrapeOptions.formats`），逐条按 `maxContentChars` 截断；
- **page 兼容**：SearXNG 保持「半页拆分」；其他方言 `page` 映射为 `offset=(page-1)*count`；
- **输出**：编号 markdown；空结果给「换宽泛查询/去掉过滤」建议；全失败汇总每个 provider 一行原因；
- **legacy**：`联网配置` 为空时用「后端 → 联网搜索」合成 `searxng` provider（id `legacy-searxng`），升级后行为不变；
- **校验失败**：整体拒绝 + 逐条日志，并回退 legacy，不让插件启动崩。
