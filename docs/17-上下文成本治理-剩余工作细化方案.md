## 1. P1-1 打分（judge）请求体积上限

### 1.1 现状问题（证据）

- `JudgeManager.buildHistory()`（`src/judge/judge_manager.ts:387-408`）按"最近 `context_count`（默认 10）**条消息**"收集，并用 `buildContent(m)` **整条**渲染。
- 待机群里所有群聊消息都追加进**同一条** user 消息 → "最近 10 条消息"实际就是那一条 → **打分 prompt 可能包含整个待机块**。
- gate 只限制调用**次数**（`max_judge_per_hour` 默认 20，`src/config/configs/trigger.ts:41`），**不限单次体积**。

### 1.2 改法（推荐 A，B 作兜底）

**A. 复用主对话的渲染窗口**（推荐）：把 `buildHistory` 改成"取折叠后的窗口"——
- 在 `src/utils/message.ts` 抽出一个可复用函数：

```ts
/** 给辅助请求（judge 等）用的"窗口化历史"：与主对话同一套折叠规则 */
export function renderWindowedHistory(session: Session, messages: ContextMessage[], maxChars: number): string
```

- `maxChars` 取 `renderFoldBudget(session, messages)`，为 0（非待机会话）时退化为 `冷态窗口字数`，仍为 0 时用内置常量 5000。
- `buildHistory` 改为：先 `foldContextMessages(clone(messages), maxChars)`，再按现有逻辑拼 `[用户]/[bot]` 行，最后追加本轮消息（现有兜底保留）。

**B. 兜底硬上限**（无论 A 是否生效都要有）：拼好的历史文本超过 `maxChars` 时 head 截断，并在末尾加 `…（更早内容已省略）`。

### 1.3 代码点

| 文件 | 改动 |
| --- | --- |
| `src/utils/message.ts` | 新增并导出 `renderWindowedHistory`（内部复用 `foldContextMessages` / `renderFoldBudget` / `buildContent`） |
| `src/judge/judge_manager.ts` | `buildHistory` 改为调用 `renderWindowedHistory`；`JudgeBuilt.messages` 组装处不变 |

### 1.4 配置

**不新增配置**（复用 `冷态窗口字数`）。

### 1.5 测试

| 用例 | 断言 |
| --- | --- |
| `testJudgeHistoryBounded` | 待机会话 + 一条含 100 条消息（>20000 字）的 user 块 → `buildHistory` 输出字数 ≤ `冷态窗口字数` × 1.1 |
| `testJudgeHistoryNonStandbyUnchanged` | 非待机会话 → 走原有整条渲染（不折叠），行为不变 |

### 1.6 验收

- 真机：待机群开评分触发，观察 judge 请求的输入 token（日志 `dims:` 前后）显著下降；`.ai ctx` 的 judge 调用次数不变。

## 2. P1-2 全量原文库分片（会话存档瘦身）

### 2.1 现状问题

- P0 只把**归档出去**的内容写进分片（`session_<id>:arc:<seq>`）；**窗口内**的原文仍留在 `session_<id>` 这个大 JSON 里。
- 结果：写入**次数**降了（保存节流），但单次写入的**体积**仍随消息数线性增长；海豹 storage 是叠加式，大键写一次占一份。

### 2.2 目标

`session_<id>` 的体积**有上界**（≈ 渲染窗口 + 折叠摘要 + 少量元数据），与消息总量解耦。

### 2.3 设计：两级移出（这是 P1 的核心结构）

```
新消息入库
   │
   ├─ 窗口内：留在 context.messages（会发给模型）
   │
   ├─【L1 窗口移出】纯代码、零 LLM、可频繁
   │    当"窗口外条目"累计 > 窗口上限时：
   │      写 raw 分片 session_<id>:raw:<seq>（只写一次、幂等）
   │      → 从 messages 移除这批条目（窗口回到上界内）
   │      → 受「归档保留原文」开关控制：关＝直接丢（不写分片）
   │
   └─【L2 记忆结算】LLM、按积压批量（见 §3）
        从 raw 分片读回原文 → summarize 抽 facts → consolidate
        成功后推进 settledSeq 水位（已结算的分片不再重复总结）
```

**关键点**：

1. **L1 与 L2 解耦**：窗口移出是纯代码（随时做、零成本）；记忆结算是 LLM（按积压批量、有上限）。
2. **L1 的粒度**：以"整条消息"或"**工具原子组**（`assistant(tool_calls)` + 紧随的 `tool` 结果）"为单位移出，绝不拆散工具组（否则请求 400 / 工具结果被孤儿清理）。
3. **原文可查**：`read_raw` / `grep_raw` 的 `kind=user` 采集器同时列 `raw:` 与 `arc:` 分片（同一套读写函数，键前缀参数化）。
4. **折叠摘要物化**：P1-2 后 `context.messages` 只保留窗口，窗口外内容用一条 `[system:折叠摘要]` 条目常驻（不再每次渲染现算），这样 `session.save()` 的体积才真正恒定。

### 2.4 数据结构

| 项 | 内容 |
| --- | --- |
| 新存储键 | `session_<id>:raw:<三位序号>`，内容与归档分片同构：`{seq, from, to, items:[{messageId,userId,time,text}], settled?: boolean}` |
| 新持久化字段 | `Session.rawSeq`（已写分片数）、`Session.lastRawAt`（时间戳）→ **必须同步进 `Session.validKeysMap`** |
| 折叠摘要 | 物化为 `messages` 里的一条 `[system:折叠摘要]` 条目（`eventType` 不用，用 `systemName`），随窗口一起持久化 |
| 复用 | `src/context/archive_store.ts` 的 `writeShardIfAbsent` / `readShard` / `listShardsDesc` / `clearShard` 参数化键前缀 |

### 2.5 代码点

| 文件 | 改动 |
| --- | --- |
| `src/context/archive_store.ts` | 键前缀参数化（`arc` / `raw`），新增 `ShardKind` |
| `src/context/context.ts` | 新增 `trimToWindow()`（L1）：算窗口外条目 → 写 raw 分片（或按开关丢弃）→ 移除；在 `addUserMessage` 之后、`archiveByTokenIfNeeded` 之前调用；`archiveOldestItems` 与它合并为同一套逻辑 |
| `src/session/session.ts` | `rawSeq` / `lastRawAt` 字段 + `validKeysMap` |

| `src/config/configs/context.ts` | 新配置：`窗口上限字数`（默认 20000；0=不限制，即 P0 行为） |

### 2.7 迁移与兼容

- 旧会话不动：窗口外内容仍在 `messages` 里，下次超限时按新逻辑移出。
- `read_raw kind=user` 的 `blk:`（压缩块）路径不变；新增 `raw:` 路径。
- `arc:` 与 `raw:` 语义区分：`arc:` = 归档（token 超限触发）、`raw:` = 窗口移出（窗口上限触发）。二者都只是"原文留档"，对模型不可见。

### 2.9 验收

## 3. P1-3 结算三条件 + 两阶段（记忆沉淀）

### 3.1 现状问题

- 记忆沉淀只在 `archiveByTokenIfNeeded` 触发时发生，而它的默认门槛是 `上下文最大token = 1000000` → 实际几乎不触发。
- 结果：待机群的历史**基本不进长期记忆**，AI 只能靠 `read_raw` 现查原文。

### 3.2 设计

**触发（三条件同时成立）**：

```
① 待结算积压 ≥ 结算水位（token，默认 3000）
② 上下文总量 ≥ 结算最小门槛（token，默认 20000）
③ 距上次相关活动 ≥ 结算空闲门槛（秒，默认 600）  或  状态转入 COLD（转冷时结算一次）
```

**执行（两阶段）**：

1. 阶段一：从 `raw:`/`arc:` 分片读回未结算原文 → `MemoryManager.summarizeChunkWithRetry`（现有）抽 facts → 写入记忆库；
2. 阶段二：`engine.consolidate(bankId)`（现有）把 facts 合并为观察记忆。

**上限与退避**：单次结算最多 `单次结算调用上限`（默认 2）次 LLM；单轮最多处理 `单轮结算批次数上限`（默认 4）个分片；失败按会话 + bank 指数退避（5/15/60 分钟）。

**水位**：`Session.settledSeq`（已结算到的分片序号）；结算只处理 `settledSeq+1 .. rawSeq`，天然幂等。

### 3.3 代码点

| 文件 | 改动 |
| --- | --- |
| `src/context/context.ts` | `stateOf()` 返回 COOLING/COLD 时置 `needSettle`（运行时标记） |
| `src/session/session.ts` | `settledSeq`（持久化）+ `validKeysMap`；`settleBackoffUntil`（运行时） |
| `src/memory/manager.ts` | 新增 `settleBacklog(session, shards, limit)`：批量 summarize + consolidate，受上限约束 |
| `src/pipeline.ts` 或 `src/agent/agent.ts` | 请求前/转冷时调用结算（有界、不阻塞回复） |
| `src/config/configs/context.ts` | 4 项配置（见下） |

### 3.4 配置

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| 结算水位 | 3000 | 待结算积压达到该 token 数才结算（参考 LlamaIndex `token_flush_size`） |
| 结算最小门槛 | 20000 | 上下文总量低于该值不做 LLM 结算 |
| 结算空闲门槛 | 600 | 秒；距上次相关活动达到该时长才结算（0=不要求空闲） |
| 单次结算调用上限 | 2 | 每次结算最多 LLM 调用数 |

### 3.5 测试

| 用例 | 断言 |
| --- | --- |
| `testSettleGateThreeConditions` | 假时钟：三条件任一不满足都不结算；全满足才调用 summarize |
| `testSettleIsIdempotentByWatermark` | 同一批分片跑两次 → 第二次不重复 summarize（`settledSeq` 已推进） |
| `testSettleRespectsCallLimit` | 积压 10 个分片 + 上限 2 → 单次只处理 2 个 |
| `testSettleBackoffOnFailure` | 失败后 5 分钟内不再尝试 |

### 3.6 验收

- 真机：待机群跑一天 → `.ai ctx` 的 `归档总结` 次数 > 0 且与积压量相称；`.ai memo` 能看到该群的事实条目。

## 4. P1-4 分片清理（命令 + TTL + 上限可配）

### 4.1 现状

- 分片超过 200 片时把最旧的 `storageSet(key, '')` 置空（硬编码 `ARCHIVE_SHARD_LIMIT`）；**没有手动清理入口**。

### 4.2 改法

| 项 | 设计 |
| --- | --- |
| 命令 | `.ai forget --all`（别名 `--raw`）：清空该会话的 `raw:`/`arc:` 分片（逐个置空）+ 重置 `archiveSeq`/`rawSeq`/`settledSeq`；权限 I（邀请者以上）；回复"已清除 N 个原文分片" |
| TTL | 新配置 `原文分片保留天数`（默认 30，0=不限制）；惰性清理：首次访问该会话分片时按分片 `from` 时间淘汰过期片 |
| 上限 | `ARCHIVE_SHARD_LIMIT` 改为配置 `原文分片上限`（默认 200） |

### 4.3 代码点

`src/cmd/sub_cmd/forget.ts`（新增 `--all` 分支）、`src/context/archive_store.ts`（`clearShardsFor(sessionId, kind, maxSeq)`）、`src/config/configs/context.ts`（2 项配置）。

### 4.4 测试

`testForgetAllClearsShards`（命令后分片键为空串、`archiveSeq=0`、`read_raw` 返回"未找到"）、`testShardTtlEviction`（过期分片被置空、未过期保留）。

### 4.5 验收

`.ai forget --all` 后 `storage.db` 体积下降；已沉淀的记忆不受影响（记忆在 `memv2:*`）。

## 5. P1-5 新增开关：归档保留原文（**已在 P0 实现**）

### 5.1 语义

| 开关 | 行为 |
| --- | --- |
| **开（默认）** | 归档时：写归档分片（原文可 `read_raw kind=user id=arc:序号` 回查）+ 调用总结智能体沉淀记忆 |
| **关** | 归档＝**直接丢弃**：不写分片、**不调用总结智能体**，只把消息移出上下文（零 LLM、零新增存储） |

> 配置名：`归档保留原文`（bool，默认 true，组「上下文」）。
> **已拍板（原"待确认"项）**：关闭时**仍然 summarize 沉淀记忆，只是不写分片**——开关只控制"原文档留"，
> 不控制"记忆沉淀"。理由：若关掉连记忆也不沉淀，历史会既不进长期记忆又查不到原文，等于白丢。

### 5.2 代码点（已实现）

- `src/config/configs/context.ts`：`registerBoolConfig("归档保留原文", true, …)` + `ARCHIVE_KEEP_RAW`
- `src/context/context.ts`：`archivePrefix` / `archiveOldestItems` 在 `ARCHIVE_KEEP_RAW === false` 时**只跳过分片写入**，
  仍然调用 summarize（保留记忆沉淀）后移除
- 单测：`testArchiveDiscardWhenKeepRawOff`（断言 **summarize 被调用**、不产生分片键、消息仍被移出）
- README 配置表 + changelog 4.26.0 已同步

## 6. 收尾小项（复核遗留）

| # | 事项 | 改法 | 测试 |
| --- | --- | --- | --- |
| B1 | `writeShardIfAbsent` 读异常被当"不存在"后仍写入 → 理论上可覆盖既有分片 | 读异常直接返回 `'failed'`（不写、不移除来源） | `testShardWriteFailsOnReadError` |
| B2 | `.ai ctx` 调 `stateOf()` 会写 `lastRelevantAt`（命令副作用） | `stateOf(now, { touch = true })`，命令传 `touch: false` | `testStateOfReadOnly` |
| B3 | `pipeline.ts:809/851` 指令/机器人消息入库只判 `setting.standby`，不看全局待机 | 补 `|| Config.base.GLOBAL_STANDBY` | 手测全局待机下指令入库 |
| B4 | `reply()` 每工具轮多一次整份写盘 | 可选：仅当本轮无 `tool_calls` 时立即写，其余交给轮末 | **决定不做**（见下） |

**B4 的结论：不做（记录理由，避免以后重复讨论）**。
- `reply()`（`session.ts:566`）是"必须落盘"的关键路径：回复已发出后若延迟写盘，进程崩溃会丢这条 assistant 记录，
  造成上下文与真实聊天记录不一致。docs/14 §5.11 明确把回复、命令、归档列为立即写。
- 收益已被 P1-2 吸收：B4 想解决的是"每工具轮整份重写"，而 P1-2 让 `session_<id>` 的体积**有上界**
