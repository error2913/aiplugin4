# 03 - 核心模块详解

本章按 `src/` 目录顺序逐个说明模块的职责、文件布局、关键类型、主要流程与不变量。代码路径均相对仓库根目录。分层与依赖规则见 [02-架构设计](02-架构设计.md)，工具系统详见 [04-工具系统](04-工具系统.md)，命令与配置项详见 [05-命令与配置](05-命令与配置.md)。

## 1. 入口与装配（src/index.ts）

**职责**：进程入口。装配宿主端口、配置、注册表与事件，不承载业务逻辑。

**装配顺序（契约，不可随意调整）**：

1. `setHost(createSealHost())` —— 宿主端口必须先装，后续存储/时钟/网络全走它。
2. `registerConfigAppliers()` —— 配置应用钩子先注册（`Config.warmup()` 会触发）。
3. `installAuxLlm()` / `installPromptMemorySource()` —— 端口实现先于配置预热安装，预热钩子可用端口。
4. Handlebars Helper：`index`（从 1 开始）、`json_stringify`、`time`。
5. `Config.registerConfig()` —— 注册 21 个配置分组并 `warmup()`（触发模型配置应用等钩子）。
6. `initAgents()` / `registerAgentApi()` / `checkUpdate()`。
7. `registerAllTools()` —— 内置工具 + 技能 + MCP。
8. `TimerManager.init()` / `MemoryScheduler.init()` / `MediaTaskManager.init()` / `ImageGC.init()` / `knowledgeService.init()` / `BlockManager.initBlockList()`。
9. `registerAllCmds()` / `PrivilegeManager.reviveCmdPriv()`。
10. `MessagePipeline.subscribeOb11Receive()` —— ob11 依赖存在时订阅其事件分发。
11. 写 `storage_version`（结构升级时）。
12. 绑定 `ext` 事件：`onNotCommandReceived` / `onCommandReceived` / `onMessageSend` / `onPoke` / `onGroupMemberJoined` / `onGroupLeave` / `onMessageDeleted` / `onBecomeFriend` / `onGroupJoined`。消息类委托 `MessagePipeline`；通知类先归一 UNI-ID（`normalizeUserId` / `normalizeGroupId`）再交 `handleNativeNoticeEvent`，与 ob11 依赖路径共用事件去重。

**注意事项**：入口只做装配；新增注册表必须提供 `xxx/bootstrap.ts`（或等价装配函数）且只被 `index.ts` 调用，避免「注册表 ↔ 实现」环。

## 2. 宿主端口与跨层端口（src/core/）

**职责**：隔离 SealDice 环境与业务代码，提供可注入的内存实现，供单测/模拟器替换。

| 文件 | 职责 |
| --- | --- |
| `host.ts` | 端口接口 `HostStorage` / `HostClock` / `HostFetcher` / `HostExt` 与 `setHost/getHost` |
| `seal_host.ts` | SealDice 适配器：唯一直接读 `seal` / `ext` 的模块；`getStorage/getClock/getFetcher` 实现 |
| `ports/agent_registry.ts` | 按名取 Agent 的端口（默认委派 `Agent.get`，保住测试桩） |
| `ports/aux_llm.ts` | 内部推理端口（摘要/评分/抽取等），实现由组合根注入 |
| `ports/session_lookup.ts` | 按 id 取会话，供 timer/media 等消费，不反向 import `session_service` |
| `ports/judge_wait.ts` | 评分轮末等待 ↔ 定时器双向登记，拆掉 judge ⇄ timer 环 |
| `ports/media_notice.ts` | 媒体完成通知「已送达」回置，session 侧消费，不反向 import media |

**约定**：业务代码统一 `getHost()` 访问宿主能力；双向协作用端口各注册一半，实现为动态委派（不要缓存函数引用，否则测试桩失效）。

**不变量**：`Config.registerConfig()` 的预热必须走 `getCache`（`warmup()`），否则分区钩子（如模型配置应用）不执行；解析失败的分组保留默认/上次结果并记日志，不整机崩溃。

### 配置读取禁令（重要）

**禁止读取未注册的配置键，禁止为旧键保留 `oldInt/oldBool` 兼容读取。**

SealDice 的 `getIntConfig/getBoolConfig/...` 在键不存在时不会抛普通 JS 异常，而是 Go 侧 `nil pointer dereference`：

```go
// sealdice-core/dice/dice_jsvm.go
if ei.dice == nil || d.ConfigManager.getConfig(ei.Name, key).Type != "int" {
```

`getConfig` 返回 `nil` 时取 `.Type` 直接 panic；这个 panic **无法被 JS 的 `try/catch` 接住**，会表现为“扩展处理非指令消息异常”，并且日志打不出来。

因此：

1. 读配置前必须确认该键已在对应 `configs/*.ts` 的 `register()` 中注册为**相同类型**；
2. 删除配置键时，必须同时删除所有读取点，**不要保留**“旧键读不到就 try/catch 回 0”的兼容代码；
3. 生产事故记录：`ContextConfig` 曾读取已不再注册的 `对话保存轮数`，通过 `getIntConfig` 触发 nil panic，第一条普通消息即崩溃；根因是旧键读取，不是配置类型变更。

排查方法：`grep -rn "getIntConfig\|getBoolConfig" src/config/configs` 的每个 key 都必须能在同文件 `register()` 中找到注册项。

## 4. 消息管线（src/pipeline.ts + src/pipeline/）

**职责**：所有消息/事件的唯一分发入口；负责过滤、触发判定、会话获取与模式分流。

| 文件 | 职责 |
| --- | --- |
| `pipeline.ts` | `MessagePipeline` 编排：非指令/指令/机器人消息/戳一戳/ob11 补充接收；`resolveEndpointId` 兼容 re-export |
| `pipeline/dedup.ts` | 核心/依赖配对状态机：配对表（TTL/容量淘汰）、依赖整条兜底墓碑、事件「后到覆盖先到」引用表、`filterOb11SupplementSegments` |
| `pipeline/events.ts` | 事件分发与事件提示词入库：ob11 通知/请求、原生通知 → 黑名单 → 待机 → 去重 → 录入上下文；录制成功后按事件触发规则决定是否起轮（忙时挂起） |
| `pipeline/inbound.ts` | ob11 入站段渲染：卡片/语音/文件/视频/音乐/商城表情/XML/Markdown/消息节点/合并转发 → `MessageSegment[]`，含嵌套深度上限 |
| `pipeline/endpoint.ts` | 按机器人自身 ID 反查通信端点（优先已连接端点），事件分发与管线共用 |

**主要流程**：

- `handleNonCommand`：忽略私聊/忽略条件/忽略正则 → CQ 白名单 → **触发域统一入口**（门控链 → @ → 正则 → AI 条件 → 计数器/概率/延迟 → 评分）→ `chat()`（返回 `ChatOutcome`）或仅入库。**录制闸** = `aiEnabled || 全局待机`；**触发闸** = `aiEnabled`（全局待机只记录，不触发任何模式）。
- `handleCommand`：`.ai` 根命令分发（默认不入上下文，开启 AI 后入库）。
- `handleBotMessage`：先交 `session.tool.listen`，再按配置入库；跳过刚发出的回复。
- 事件三兄弟：仅 `aiEnabled`/全局待机时录入；录制成功后按「链事件规则 → v1 事件触发规则」匹配，命中则让会话响应（空闲时链规则**异步起轮**、v1 fire-and-forget，不阻塞 ob11 分发；忙时把唤醒文本挂进 `pendingQueue(kind:'trigger')`，轮末由 `resumePending` 补一轮）；触发闸仅为 `aiEnabled`；机器人自身事件由原生回调覆盖、ob11 侧跳过；poke 优先走消息管线；两路径共用去重 key。

**不变量**：核心优先、依赖补充（避免同一条消息双录）；事件去重 key 含整包内容指纹，连续但内容不同的事件不会互吞；重复/双路径到达「后到覆盖先到」就地替换（位置不变）；事件原始 JSON 挂 `raw`，不渲染、由 `read_raw kind=event` 读取。

## 5. 会话（src/session/）

**职责**：会话状态、触发判断、收信/发信、保存节流。

| 文件 | 职责 |
| --- | --- |
| `session.ts` | `Session` 主体：字段/工具状态、`chat()`/`chatStream()` 编排、`stopConversation()`；其余方法委派叶子 |
| `setting.ts` | `Setting`：priv、`aiEnabled`（绝对触发闸，新会话默认关）、activeMode、timerTrigger、regexTrigger、counter、timer、prob、judge、activeTimeInfo（旧存档兼容）、overrides；`enabled()` 为统一闸值。**@ 触发是全局配置（`Config.trigger.AT_TRIGGER`），不在 Setting 内** |
| `rhythm.ts` | 纯函数：`computeSessionState`（冷/余温/热状态机）、`activeTimeSegmentIndex`、`nextActiveTimePoint`；`COLD_AFTER_MS` / `COOL_DOWN_MS` / `HOT_HOLD_MS` |
| `persistence.ts` | 序列化与保存节流：`SESSION_RUNTIME_KEYS`、`serializeSession`/`serializePendingQueue`、`writeSessionRecord`/`writePendingRecord`（5 秒或 20 次合并一次） |
| `inbox.ts` | 收信与排空：`handleReceipt`/`deferReceipt`/`drainPending`/`flushPending`（挂起消息入库）/`flushNotices`（子代理/媒体通知） |
| `outbox.ts` | 发送：`deliverReply`（分段延时 → `replyToSender` → 上下文回填 → 落盘；headless 只收集不发送） |
| `session_service.ts` | `getSession(sid)` 从存储复活会话；`SessionService` 持有 `sessionMap` 与全局记忆 |
| `tool_listen.ts` | 工具「等待消息返回」监听（`ToolListen`/`ToolWaitHandle`） |
| `group.ts` / `user.ts` | 群档案（角色/群主/管理员/成员/忽略名单）与用户档案（名称） |
| `types.ts` | `SessionType('group'|'user')`、`State`、`GroupInfo`、`UserInfo` |

**关键字段**：`agentName`、`sessionId`、`sessionType`、`state`、`context`、`memory`、`setting`、`stream`、`bucket`、`tool`（state/callCount/listen）；运行时字段 `running`/`starting`/`stopVersion`/`stopEvent`/`pendingQueue`/`activeRuns` 不持久化。

**主要流程**：

- `chat()`：`aiEnabled` 闸（可 bypassGate）→ 令牌桶检查 → 重置 BLOCKED 工具 → 模型流式判定 → `chatStream` 或 `Agent.run()`；返回 `ChatOutcome`（fired/deferred/bucket-empty/gated），只有 `fired` 才记 judge WAIT 冷却，`deferred` 退还令牌。
- 收信：运行中收到新消息 → 先做**强触发轻量判定**（链规则/@/正则/AI 一次性条件）：命中则 `deferReceipt(kind:'trigger', wakeText)`，轮末 `resumePending` 补一轮；未命中按 `kind:'record'` 只入库。计数/概率/延迟/评分忙时**不推进**。每轮模型请求前 `flushPending` 统一入库；触发闸关闭时 `flushPending` 不写 trigger 提示。
- 发送：`deliverReply` 分段发送并回填上下文；回复/命令/摘要等关键路径立即 `save`，待机消息/事件用 `coalesce` 节流。
- 工具开关：`toolState` getter 合并 `BLOCKED`、`DEFAULT_CLOSED`、已删除工具清理与子代理 `toolRestriction`（allow/deny 求交）。
- 技能/知识库会话开关 `skillState`/`kbState` 只记录被关闭项，缺省开启，参与 prompt 静态段缓存 key。

**不变量**：`.ai stop` 通过 `stopVersion`/`StopEvent` 中止，检查点后丢弃结果；`chat()` 不做静默丢弃——忙时由调用方 `deferReceipt`/`decideWake` 决定，媒体/子代理结果必须进队列（见 [02-架构设计](02-架构设计.md) 异步章节）。

**主要流程/不变量**：

- 写入：单写者同步 append，flush 只写新页 + 常量 head；旧 `messages` 数组在新实现启用后不再落盘。
- 请求：`handleMessages` 在 `session.contextV2` 存在时返回 `compileRequest`；原文可见边界 = max(滚动摘要边界, `archivedThrough`)，按单元过滤、不拆工具组；**可见单元全量渲染**（不按本轮预算挑子集），未结算的工具组本轮不渲染；历史不带 `[msg_id]`/`[time]`，`[from:名字(号码)]` 的名字在写入时冻结，`[quote_of:<msgID>]` 由事件字段直出；系统事件保留 `[time]`（写时冻结值）。渲染量超预算只标 `stats.needsArchive` 供观测，真正兜底是请求超长 → 硬切归档 → 重发（`archiveByTokenIfNeeded` 走 `ArchiveController.forceCutBelow`，返回 `converged`/`busy`/`failed`）。
- 摘要：见下方「上下文 token 水位与归档契约」；摘要 = 滚动摘要 + 记忆 facts 同一请求，失败退避、空不推进；原文始终保留在事件页（可 `read_raw`/`grep_raw` 回查），除非开启「归档保留原文=关」。
- 召回：`read_raw e:<seq>` / `grep_raw` 可穷尽检索，结果带发送时间与消息 ID，`grep_raw` 按时间升序；摘要文本带可解析指针与时间范围。
- 引用解析：`resolve_context_ref` 接受模型原样复制的表示（事件地址、`read_raw` 指针、`[mem:<id>]`、`[img:…]`、`[quote:…]` 等），还原为原文/字段/元数据；`kind=event_raw` 读取 system 事件 `raw`；只读、无网络、不调 LLM。
- 管理：`.ai ctx`（status/archive/hide/purge/set/name/repair/debug）；`hide` 逻辑遗忘、`purge` 物理清除且默认不动记忆；`debug` 只切换前缀漂移探针，不改行为。
- 解耦：上下文不 import 记忆层；归档 facts 经 L0 端口 `core/ports/archive_facts` 交给记忆层，记忆层再排巩固。

#### 上下文 token 水位与归档契约（行为规范）

> 本节是**行为契约**，实现按此对齐。
>
> | 记号 | 定义 |
> |---|---|
> | `L` | 消息上下文预算 = **配置的 token 上限 − 固定提示词 token**（配置 0 时取探测窗口×0.8 再扣固定提示词；**不含** context_too_long 临时 cap） |
> | `n` | 保留强度（`保留强度`，默认 30） |
> | `k` | 触发系数，写死 `0.95` |
> | `A` | 保留目标 = `floor(L × n / 100)` |
> | `B` | 对话后触发线 = `floor(L × k)` |
> | `C` | 待机归档线 = `L + (B − A)`（默认约 `1.65L`） |
> | `T` | 当前消息上下文 token = **未归档原文 + 摘要注入文本 + 活跃注入块**（与 `L` 同口径，不含固定提示词） |

**路径一：对话触发（本轮要发主模型请求）**

```
① T ≥ L（硬上限兜底：先切，后请求，再总结）
   1) 硬切最旧块到 T ≤ L（切时零 LLM、不总结；记下被切块 Cb）
   2) 发主对话请求
   3) 并发发总结请求；按切后状态二选一：
      - B ≤ T < L：从最旧未总结处（含 Cb）继续总结，直到「活动上下文剩余 ≤ A」
      - T < B    ：只把 Cb 总结掉（活动上下文不再总结）
   （硬切不影响已经在飞的总结；总结结果照常使用）

② B ≤ T < L（正常总结，无硬切）
   发主对话请求
   → 并发发总结请求：从最旧未总结处标记「标记块 M」
     总结到「剩余 ≤ A」为止（T = B 时正好切 (B − A)；T > B 时切得更多）
   → M 只标记、暂不归档，后续请求仍可使用
   → 总结任务与主对话并发，不阻塞回复

③ T < B
   不总结、不归档
```

标记块 M 的生命周期（单会话单飞，同一时刻最多一个总结任务）：

```
[无标记]
   │ B ≤ T < L（或 T≥L 硬切后 B≤T<L），启动总结
   ▼
[已标记 · 总结中] ──新请求且 T ≥ L──► 硬切 M 的活动部分（Cb 已归档）
   │                                   （在飞总结继续，结果照常使用）
   ├──新请求且 T < L → 保持
   ├──工具链执行中且 T ≥ L → 硬切 M 的活动部分
   ├──总结完成 → 写入滚动摘要 + 记忆 facts，归档 M
   └──总结报错 → 直接归档 M（无摘要、不写记忆；原文仍可检索）
```

**路径二：未触发对话（待机 / 没被 @）**

```
T < C   → 继续存，不总结、不归档
T ≥ C   → 零 LLM 归档最旧 ≥ (B − A) 的整条消息块，直到 T ≤ L
          不生成摘要、不写记忆；归档块只能通过检索回查
```

- 待机期间允许一路涨到 `C`（约 `1.65L`）；到 `C` 才切回 `≤ L`。
- 若在待机期间涨过了 `L`，随后触发对话：直接适用「路径一 ①」——先硬切回 `≤L`，再按切后状态决定总结范围（`T<B` 只总结被切块 `Cb`；`B≤T<L` 从 `Cb` 起继续总结到活动上下文 `≤A`）。
- 开启「归档保留原文 = 关」时，归档时物理清理对应事件页，之后检索不可达（省存储，不省 LLM）。实现口径：只清理**已被滚动摘要覆盖**（`seqEnd ≤ summarizedThrough`）的页；硬切块 Cb 与待机归档块等未总结内容先保留原文，等被后续总结覆盖后再清理（否则摘要无法覆盖 Cb、检索也会丢原文）。

**切割规则**

- 块边界只落在**单条消息边界**：一条消息整条进块或整条留下，绝不从消息中间切。
- 工具调用组（assistant `tool_calls` + 对应 `tool` 结果）整组进/整组留，不拆散。
- 单条消息自身大于块目标时，允许该条独占一块（允许超目标）。
- 硬切目标是 `T ≤ L`，允许因整条消息边界略低于或略高于 `L`；总结目标是「剩余 ≤ A」。

**总结内容**

- 一次总结任务 = 一个 LLM 请求，同时产出：滚动摘要（覆盖标记块）+ 长期记忆 facts（见 [13-记忆系统](13-记忆系统.md)）。

**检索口径**

- `read_raw` 是**地址寻址**（`e:<seq>`、区间、`msg_id`、旧分片），**不能按内容搜**；
- 按内容搜用 `grep_raw`，命中后拿 `e:<seq>` 再 `read_raw`；
- 归档块只要原文页未删除就可被 `grep_raw` 搜到；「归档保留原文=关」时页被清、不可达。

#### 前缀缓存不变量与增量注入块（#163）

请求体结构：`B_k = S ⊕ H ⊕ Δ`（`S`=system prompt + 预设上下文 + 工具 schema，恒定；`H`=冻结历史；`Δ`=本轮新增的注入块与新消息）。三条不变量：

| 编号 | 含义 | 怎么保证 |
| --- | --- | --- |
| **R1** 严格前缀扩展 | 未归档时 `B_k` 必须是 `B_{k+1}` 的**字节前缀** | 渲染只读事件内冻结字段；不读时钟/活名/活开关；历史不受本轮预算影响（全量渲染）；单元边界随发送冻结（`segmentUnits(..., { anchorSeq })`，跨 anchor 的相邻 user 不合并） |
| **R2** 幂等重编译 | 同一快照编译两次，字节完全相同 | `compileRequest` 是纯函数（时间/名字/估算全部注入）；注入块按 `slot()` + `compareBlocks()` 完全确定排序 |
| **R3** 归档是唯一 rebase 点 | 断裂必须可归因且显式记账，水位只前移 | `session.notePrefixRebase(reason, throughSeq)` 统一打点；`prefixSnapshot` 同 tick 作废；`rebuild` 白名单见 [05-命令与配置](05-命令与配置.md) |

**历史层渲染规则**（这些是"删掉的东西"，最容易被误写成旧行为）：

- **不带 `[msg_id]`、不带 `[time]`**。它们原本按"本轮剩多少预算"从最新往回分级（`computeTagDecisions`），窗口一晃边界就平移 ⇒ 已发送区中间字节被改写。整段逻辑随 `EventFlags`/`TagDecisions`/`dateKeyOf`/`isMessageEvent`/`seqOf` 一起删除。模型定位历史改用 `grep_raw` → `read_raw`。
- **`[from:<名字>(<号码>)]` 的名字写入时冻结**：`UserEvent.fromName` 在事件落盘时取一次（`context/roster.ts` 的 `frozenUserName`；legacy 路径另有 `UserMessageItem.frozenName`）；旧数据缺字段时回落当前显示名，**不回填历史页**（改了名就只影响此后写入的消息）。
- **`[quote_of:<msgId>]`**：引用回复展开后，被引消息作为独立 user 事件写入（`service.appendUserWithQuote`，eventId 固定 `q:<msgId>`），回复事件带 `quoteOf` 指针；渲染时 `[quote_of:]` 排在 `[from:…]` 之后，不受任何开关门控。
- **唯一保留的时间标签是系统事件的 `[time:<时间>]`**（`renderSystemEvent`）：那是事件写入时冻结的 `at`，仍是前缀函数；唤醒/离线补偿类事件需要它判断间隔。用户问"现在几点"由 `kind:'time'` 注入块与 `get_time` 工具承担。
- **全量渲染**：`budgetTokens` 不再决定渲染多少单元，只用于 `stats.needsArchive` 观测。删掉选择器的理由同上（预算抖动会从历史中间丢消息）。超窗口由 `context_too_long` → 硬切归档 → 重发兜底。
- **未结算的工具组不渲染**：`unit.settled === false`（缺结果且之后没有更晚的对话事件）本轮跳过。否则结果晚到会把"调用未完成"文本改写成真实 tool 消息，等于改写已发送区。
- **可见性过滤为空时不回退全量**：只标 `stats.boundaryDefense`。回退会让脏数据把已归档内容重新渲染出来（凭空往前插历史，前缀直接崩）。
- **冻结守卫**（兜底，非正常路径）：传上一轮快照时逐条比对，若已发送区变了 ⇒ 记 `stats.prefixDrift`（首个差异下标），用快照覆盖冻结区，并由调用方记一次 `prefix-drift-freeze` rebase。只损失"这一次漂移"，下轮起字节恢复稳定。

**增量注入块**：

- **载体**：`kind:'event'` 的 `SystemEvent` + `raw.injection`。**不新增** event kind、不新增 `RecordEntry.kind`、不新增 `ContextHead` 字段，`CONTEXT_SCHEMA_VERSION` 仍为 `2` ⇒ 旧会话无需迁移。
- **`InjectionMeta`**：`{ v, kind, afterSeq, tokens, items[], createdAt, banks? }`；条目 `InjectionItem = { k, r, h, text, refSeq? }`（`k`=去重键、`r`=内容修订、`h`=正文哈希、`refSeq`=来源事件 seq，供 redact 失效判定）。
- **`afterSeq` 写入时冻结**：渲染时按它把块插到对应单元边界之后，此后永不改写（`clampAnchor` 只做防御性夹紧）。
- **永不进单元/摘要/facts**：`splitInjections` 必须在 `segmentUnits` **之前**调用。
- **释放水位** = `max(summarizedThrough, archivedThrough)`（与编译的 `hiddenBoundarySeq` 同口径）。`afterSeq ≤ 水位` ⇒ 已释放（内容已被摘要覆盖），事件不删不改。
- **token 双计防护**：注入 token **不进** `head.unarchivedTokens`（`store.ts` 的 append / `commitSummary` / 水位重算三处口径一致）；`T` = 未归档原文 + 摘要注入 + 活跃注入（`ArchiveController.estimateT`，第三项由 `activeInjectTokens` 现算并做单槽 memo）。归档时用 `releasedInjectTokens` 只扫注入块扣减（O(块数)，不重扫全量事件）。
- **三处归档切分同口径**：`selectCut` / `selectMarkForTarget` / `selectMarkTo` 都按「`L` 减去摘要注入与活跃注入」算目标，且**跳过注入块**（只切对话单元）；`selectMarkForTarget` 发现注入 token 已超过保留目标时记 `inject-exceeds-retain-target` 观测并放弃（不切）。
- **`L` 的唯一实现**：`utils/context_budget.ts` 的 `resolveArchiveL({ permanentBudget, prefixTokens, toolsReserveTokens, runtimeTokens })`，编译与注入预算闸共用，避免"注入以为装得下、编译以为装不下"。
- **渲染形态**：`[system:inject-<kind>] <正文> [/system]`；同位置的多个块合并成一条消息，顺序由 rank 决定（`slot` 定位、`compareBlocks` 定序）⇒ 同快照两次编译字节一致（R2）。
- **写入口** `injection_writer.ts`：收集 → 同 kind 合并 → 去重 → 三层额度（单轮 512 / 冷启动 2048 / 活跃窗口 4096、硬上限 5120）→ 预算闸（**先归档后写块**）→ 唯一写入口。**禁止跳注**（`result.skipped` 恒 0）；**绝不删块**（"消失"只能是归档释放或 redact 失效，两者本身都是白名单 rebase）。
- **去重判定**（`injection_dedup.ts`）：`new` / `dup`（同 `k` 同 `r`）/ `dup-text`（异 `k` 同正文）/ `updated`（同 `k` 异 `r`，正文加 `(updated) ` 行首）/ `re-inject`（曾被释放且内容未变，允许再注一次）。索引**不持久化**，每轮从活动块现算 —— 持久化 `k→r` 会在归档释放后把条目误判 `dup` 而永久饿死。

**主要流程**：

- `run()`：组装消息 → `requestModel` → 工具轮（function calling 或提示词工程）→ 复读检测重试 → 最终回复；单轮最多 3 次尝试。
- **每轮注入规划（#163 D3）**：`runInternal`/`runStreamInner` 在 `handleMessages` **之前**调 `planInjections()` → `planAndWriteInjections()` 跑内置 provider 写增量注入块。两个时序前提：①必须早于 `handleMessages`（编译按当前快照渲染块，写晚了本轮看不见）；②必须早于 `archive.beginRequest()`（writer 的预算闸自己会调 `archive.beforeRequest`，随后 `beginRequest()` 清快照、由编译钩子用真实 `L` 重建，两条归档路径不打架）。任何异常只记日志与 `prefixObservation`，绝不打断本轮回复。
- **注入锚点推进**：请求成功发出后 `markInjectionSent()` 把 `session.injectionAnchorSeq` 推到本轮编译覆盖到的最大 seq（`Math.max` 单调，归档让 `lastSelectedSeq` 变小时也不回退 —— 回退会让下轮块锚到已发送区中间，破坏 R1）；请求未发出/失败时 `advanceInjectionAnchorOnFailure()` 推到 `head.nextSeq - 1`（"已入库的最新一条"，锚在它之后仍落在新增历史尾部）。
- 错误分类处理：上下文超长按模型窗口重算预算后重发一次；**v2 下改为** `Context.archiveByTokenIfNeeded(target)` → `ArchiveController.forceCutBelow(target)` 零 LLM 硬切推进 `archivedThrough` 并显式记 `('archive', 新水位)` rebase，返回 `converged`/`busy`/`failed`；余额不足等按「跨厂商优先/配置顺序」切备用模型并持久化覆盖；单 run 各至多一次。
- 停止：检查点检测 `stopVersion`/`StopEvent`，命中即中止（goja 无 AbortController，结果丢弃）；排队项由 `requestLimiter.cancelBySession` 丢弃。
- 子代理：headless 子会话（spawn 无 seed / fork 继承父上下文），原生模式只注入 list_tools/search_tools/call_tool；完成后写父 `noticeQueue` 或 job 结果。

**主要流程/不变量**（详见 [02-架构设计](02-架构设计.md) 异步章节）：

## 20. 日志（src/logger.ts）

- 输出格式：`【AI骰娘4】[级别短标签] [模块标签] 内容`；级别 ERROR/WARN/INFO/DEBUG 与海豹面板对应。
- 通过 `logger.withTag('模块名')` 生成带标签日志；级别由「日志级别」配置控制。
- 「日志简短打印」是唯一的内容截断开关——关闭=完整打印（对象完整 stringify、模型思维链/响应/请求上下文正文等全文，调用方不得预先截断）；开启=整行超 1000 字时只保留首尾各 500 字（`\n...\n` 分隔）。`logLong()` 分片打印并标注段号（开启时 900/片、关闭时 1500/片）。
- 密钥脱敏：`api_key`/`token`/`authorization`/`secret`/`password` 等字段、URL query、`Bearer`、`sk-` 前缀、access/refresh token；脱敏在截断之前执行，data URI 与 JSON `base64` 字段的二进制载荷先折叠为 `[base64 已省略 N 字符]` 占位（不算日志截断，避免关闭截断后整段 base64 灌进日志）。
- `exception()` 错误进 error，响应体原文（`ApiError.rawText`）与堆栈进 debug；`printRequestMessages()` 默认只打摘要，正文受「日志记录消息内容」开关控制，长度由「日志简短打印」统一处理。
