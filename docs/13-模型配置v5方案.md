## 0. 为什么改

现有「api连接」+「模型规则」两个 TOML 框存在**结构性**问题（不是语法问题）：

| 问题 | 证据 | 后果 |
| --- | --- | --- |
| 连接序号是位置语义 | `model.ts:459` `ref = "[0]:name"` | 删/挪一个框，所有规则引用静默漂移 |
| 规则靠**模型名字符串**匹配连接 | `request_rules.ts:108-128` | 改名/换钉住清单 → 规则静默失配，不报错 |
| `[types]` 表必须写在框末尾 | `model.ts:301` | 表后出现任何键 → 整框解析失败 |
| 模型名含 `. : /` 需加引号 | `model.ts:301` | 被解析成嵌套表，该键静默失效 |
| 两趟合并（use 组 → models 定向） | `request_rules.ts:131-140` | 用户难以预判最终生效值 |
| 用途绑定存 storage，不在配置里 | `model.ts:50-64`、`MODEL_PURPOSE_OVERRIDES_KEY` | 重装/迁移即丢（v5 加一层配置默认值；storage 保留为运行时覆盖，见 2.3.3） |
| 解析失败只记日志、跳过该框 | `model.ts:341` | 用户看到的是"模型莫名没了" |

v5 用**单个 JSON 配置**替换两个 TOML 框，逐条消除上表。

## 1. 总则：职责边界判据

> **凡是输入依赖于「运行时才知道的信息」，必须留在插件；凡是输入完全来自配置与静态数据的，可搬到配置生成器。**

"运行时才知道"只有三类：

1. **网络拉取的模型列表**（`GET /models` 的返回）
2. **用户的真实消息内容**（语音正文、待识别图片）
3. **运行环境能力**（后端是否在线、goja 能否读二进制）

生成器是**纯静态页面**，不联网、不知道用户账号下有哪些模型，因此凡依赖上述三类的判断一律不能外移。

### 1.1 平台硬约束（设计前必读）

这两条是 SealDice 侧的限制，任何方案都绕不开：

| 约束 | 依据 | 影响 |
| --- | --- | --- |
| **配置只读** | `seal.ext` 只有 `register*Config` 与 `get*Config`，**无 setter**（`seal.d.ts:722-805`） | 插件**无法回写配置框**。任何"命令改配置"的设计都不成立 → 见 2.3.3 的 purposes 分层 |
| **无环境变量** | `seal.ext` 读不到宿主环境变量 | 无法用 `apiKeyEnv` 这类凭据引用（DSH/Codex/Claude 都靠它）。v5 因此只能**明文存 key**（既定取舍） |

另有两条已知的运行时限制（v4 既有，v5 不变）：

| 约束 | 影响 |
| --- | --- |
| goja 无 `AbortController` | 请求无法设超时；MCP/网络调用可能挂起（见 `docs/10-TODO.md`） |
| goja 读不了二进制响应 | 整响应体即音频/图片的接口需后端中转（`media_presets` 依赖此） |

## 2. v5 配置格式规范

### 2.1 承载方式

- **单个配置项**，用 `seal.ext.registerStringConfig` 注册（字符串，非 template 数组）
- 配置项名：`模型配置`
- 值：**一个 JSON 对象**（密集格式，无注释、无换行要求）
- 旧的两个 template 配置项 `api连接`、`模型规则` **不再注册**（不读取、不迁移、不兼容，见第 8 节）

### 2.2 完整结构

```json
{
  "version": 5,
  "providers": [
    {
      "api": "openai-completions",
      "baseURL": "https://api.deepseek.com/v1",
      "apiKey": "sk-xxx",
      "models": [
        { "id": "flash", "name": "deepseek-v4-flash", "kind": "text" }
      ]
    }
  ],
  "purposes": { "chat": ["flash"] },
  "groups": [
    { "purposes": ["chat"], "body": { "max_tokens": 8192 } }
  ]
}
```

### 2.3 字段定义

#### 顶层

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `version` | number | ✅ | 固定 `5`。缺失或不为 5 → 拒绝并提示 |
| `providers` | array | ✅ | 至少 1 项。**模型嵌套在 provider 内**（见下） |
| `purposes` | object | ⭕ | 用途 → 模型 id 的**有序数组**（优先用这些，按此顺序；见 2.3.2.3）。缺省时由插件按该用途的候选顺序取第一个（**候选已按类型精确筛过**，见 6.3 / 9.2.1） |
| `groups` | array | ⭕ | 用途组默认请求体 |

> **变更说明（相对本方案初稿）**：初稿把 `models` 放在顶层、用 `models[].provider` 反向引用连接。现改为**嵌套**在 `providers[].models[]` 内。理由见 2.3.1。

#### `providers[]`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `api` | enum | ✅ | `openai-completions` \| `anthropic-messages` \| `openai-responses` |
| `baseURL` | string | ✅ | 必须 `http(s)://` 开头。**不再兜默认值**（见第 5 节） |
| `apiKey` | string | ✅ | 明文。非空，字符集 `[\x21-\x7E]` |
| `provider` | string | ⭕ | **vendor 标识，通常不填** —— 由 `baseURL` 的 host 自动识别（见 2.3.2）。仅当自动识别失败且该地址代理某家原生接口时才手工指定 |
| `models` | array | ⭕ | 该连接下的模型。**空数组/缺省 = 启动时自动拉取**（见 6.2） |
| `enabled` | boolean | ⭕ | 默认 `true`。`false` = 忽略该连接（取代 `ignore = 1`） |
| `displayName` | string | ⭕ | 仅供 UI 展示（自定义接入时给个可读名字） |
| `timeout` | number | ⭕ | 秒，请求超时 |
| `request` | object | ⭕ | 连接级请求覆盖：`list_url` / `auth_header_name` / `headers` / `balance_url` / `balance_json_path` / `balance_divisor` / `balance_currency` |

**没有「连接 id」字段。** 初稿设计过 `id`，但核查后确认它只是标签（见 2.3.2），已删除。识别连接在输出里改用「数组位置 + vendor」。

**`providers` 用数组而非映射**：`model.ts:512-513` 取用途候选的**第一个**（`pool[0]`），候选顺序由 `rebuildEntries()`（`model.ts:439-444`）按连接顺序 + 列表顺序决定。**顺序是真实语义**，JSON 对象 key 顺序在规范上不保证，故必须用数组。

#### `providers[].models[]`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | ✅ | **全局唯一**（跨所有 provider），被 `purposes` 引用 |
| `name` | string | ✅ | 发给 API 的真实模型名（可含 `/`、`.`、`:`） |
| `kind` | enum | ⭕ | `text` \| `vision` \| `embed` \| `gen` \| `tts`。**取代 `[types]` 表**。缺省时按 `classifyModel` 判定 |
| `contextWindow` | number | ⭕ | 容量，供压缩策略参考 |
| `maxTokens` | number | ⭕ | 输出上限 |
| `request` | object | ⭕ | **per-model 请求覆盖**（取代规则的 `models` 定向）：`body` / `request` / `response` / `params` / `prompt` |
| `bodyMode` | enum | ⭕ | `merge`（默认）\| `replace`。见 2.4 |

##### 2.3.1 为什么嵌套而非顶层平铺

| 理由 | 说明 |
| --- | --- |
| **消掉一整类校验错误** | 平铺时 `models[].provider` 可能悬空，需要引用完整性校验；嵌套后该引用不存在，**错误不可能发生** |
| 与迭代顺序 1:1 对应 | `rebuildEntries()`（`model.ts:439-444`）就是"先连接、再该连接的模型"两层循环 |
| 与生成器 UI 一致 | 模型是在**供应商卡片内**配置的（见 9.2），嵌套与用户心智模型一致 |
| 与 DSH 一致 | `dsh-llm-pi-ai` 的 `providers.<id>.models[]` 同样是嵌套（调查报告 §一.3） |

**代价**：同一模型经两个网关接入时，需写成两条（`id` 不同）。这**恰恰是正确的**——它们是两个不同的连接，`ref` 本就该区分。注意这里的 `id` 是**模型 id**（必填、全局唯一），不是连接标识。

##### 2.3.2 vendor 标识由 URL 自动识别（用户不填）

**背景：`provider`（vendor）功能上必需，但不该让用户填。**

它必需，因为插件的两处功能按 **vendor**（而非 `api` 协议）索引：

| 功能 | 位置 | 用途 |
| --- | --- | --- |
| `media_presets` | `media_presets.ts:300-308` | 决定**媒体请求的 body 结构**。键是 vendor：`openai` / `siliconflow` / `zhipu` / `dashscope` / `alibaba` / `google-cloud` / `minimax` / `fishaudio` / `elevenlabs` / `baidu` / `volcengine` / `tencent-tokenhub` / `stability` … |
| `balance` | `balance.ts:63-82` | 内置余额端点（deepseek / moonshot / siliconflow） |

**关键风险**：`resolveMediaPreset` 是**回落**而非报错——

```js
const entries = table[key] ?? table[''];   // 找不到就落通用预设
```

vendor 丢失会静默落到 `table['']` 的通用 OpenAI 兼容结构。对兼容厂商无碍，但对**原生结构的那十来家**（Google Cloud TTS、MiniMax、FishAudio、ElevenLabs、百度、火山方舟、腾讯 TokenHub、Stability、百炼原生 dashscope…）会**发出错误的请求体且不报错**。

**解法：从 `baseURL` 的 host 自动识别。**

这与插件现有做法一致 —— `balance.ts:70` 本来就在做 `host.includes('api.deepseek.com')`。**v4 的 `PROVIDER_MAP` 因此不能删除，而是换个方向用**：

| | v4 | v5 |
| --- | --- | --- |
| 表内容 | vendor → 默认 baseURL | 同一张表 |
| 用途 | **填充**省略的 base_url | **反查** host → vendor |

解析顺序：

```
1. 配置显式写了 provider              → 用它（逃生舱）
2. 否则按 baseURL 的 host 查表         → 命中即用
3. host 认不出 → 按 URL 的**路径尾段**再试一次（vendor 独有的端点路径）
4. 都不命中                            → ''（按 OpenAI 兼容处理）
```

##### 2.3.2.1 第 3 步为什么必须存在（实测踩到的 400）

**只看 host 会漏掉"直接粘完整端点地址"这一大类写法** —— 而 v4 的「api连接」就是那么填的
（`base_url` 直接写完整接口地址）。典型：

```
https://llm-xxxx.cn-beijing.maas.aliyuncs.com/api/v1/services/aigc/multimodal-generation/generation
        └─ 专属部署域名，不在 PROVIDER_MAP 里，host 反查为空
```

host 反查为空 → 退回**通用预设** → 把 `/images/generations` 拼到原生端点后面：

```
…/api/v1/services/aigc/multimodal-generation/generation/images/generations   ← 畸形地址
```

百炼对此返回 **400 `url error, please check url！`**（[官方文档](https://www.alibabacloud.com/help/en/model-studio/error-code#error-url)：*Model name does not match the API endpoint*）。
用户的现象是"v4 明明能用，v5 就 400"—— 因为 v4 的 TOML 里显式写了 `provider = "dashscope"`，迁移到 v5 时那一行丢了。

**第 3 步的判据从 `media_presets` 自己算出来，不手抄**（`vendor.ts` 的 `SUFFIX_TO_VENDOR`）：

- 跳过通用预设（`''` 键不代表任何 vendor）
- 跳过含 `{占位符}` 的（如 ElevenLabs 的 `/v1/text-to-speech/{voice}`，无法字符串匹配）
- **只收"恰好一个 vendor 拥有"的路径**

第 3 条是关键：`/images/generations`、`/audio/speech` 被 6~7 个 vendor + 通用预设共用，
拿它们反查会把**自建网关误判成某一家**。收窄后实际命中的只有 7 条：

| vendor | 路径 |
| --- | --- |
| dashscope | `/api/v1/services/aigc/multimodal-generation/generation`、`/api/v1/services/aigc/text2image/image-synthesis` |
| stability | `/v2beta/stable-image/generate/ultra`、`/core` |
| google-cloud | `/v1beta1/text:synthesize` |
| fishaudio | `/api/open/v3/speech/tts` |
| minimax | `/t2a_v2` |

反例已验：`https://my.host/v1`、`https://my.host/images/generations`、`https://my.host/audio/speech` 都**不**反查出 vendor。

**配套：`baseURL` 是完整端点时，列表拉取要早失败**（`list.ts`）。
拼 `/models` 会得到 `<端点>/models`（必然 404），所以命中第 3 步时**在发请求前**就抛出可操作提示
（"改填基础地址，或用 `request.list_url` 指定"）。注意 `describeListError` 会把普通 Error 截到 120 字符，提示必须短。

**生成器侧不做同样的拦截**：它看不到 `media_presets`，唯一可用的判据是"路径段数很多"这类启发式，
而那会把 `https://gw/a/b/c/d/v1` 这种**本来可用**的自建网关误判成端点、直接拒绝拉取 —— 把能用的弄坏。
所以生成器只把 404 的失败文案说清楚（点名"若填的是完整端点"），拉取本身仍按尽力而为降级到手动输入。

##### 2.3.2.2 共用 host 的 vendor

`alibaba`（`…/compatible-mode/v1`）与 `dashscope`（`dashscope.aliyuncs.com`）**host 相同**，
host 反查必然都得到 `alibaba`。所以「百炼原生」这个生成器模板**必须显式写 `provider`** ——
`providerForTemplate()` 正是按"地址反查不回自己就写"的规则决定要不要写。

**为什么不让用户填**：这是个用户既不知道、也不关心的内部标识；让手填只会产生拼写错误，而错误的表现是"媒体请求静默发错结构"。生成器侧则完全隐藏该字段（只在卡片上展示识别结果）。

**逃生舱**：极少数情况需要手工指定 —— 例如自建网关代理的是**百炼原生 wanx** 或 **Google Cloud TTS**，其 host 无法识别。故 `provider` 保留为可选字段，在生成器的连接面板里（带建议列表，可自由输入）。

#### `purposes`

- key ∈ 8 个已知用途：`chat` / `compression` / `summarization` / `judge` / `image-understanding` / `text-embedding` / `tts` / `image-generation`
- value = **模型 id 的有序数组**（`string[]`），元素是某个 `providers[].models[].id`（**全局唯一**，不带 provider 前缀）
- 语义：**持久默认值**（配置层），不是唯一来源 —— 见 2.3.3

##### 2.3.2.3 用途绑定是**有序数组**（多模型 + 按顺序取用）

初版写成单个 id（`"chat": "flash"`），只能绑一个模型。改成**数组**：

```json
"purposes": { "chat": ["kimi-k2", "deepseek-chat"] }
```

**语义是"优先用这些，按此顺序"，不是"只允许这些"**：

| 位置 | 含义 |
| --- | --- |
| 数组里的 | 用户排的优先顺序，下标越小越优先 |
| 未列出的同类型模型 | 仍在候选池里，排在列出的**之后**（保持连接顺序 + 列表顺序） |

三处消费点都因此自动服从用户排序（**只改一处排序，三处都成立**）：

| 消费点 | 行为 |
| --- | --- |
| `resolveForUse(use)` | 取数组里**第一个仍然有效**的（前面几个可能已退役/改名） |
| `listModelsForUse(use)` | 按数组下标排序；这是"按顺序取用"的**唯一实现点** |
| `agent.pickNextModel()` | 失败回退**顺着同一个列表往后走** |

**失败回退是既有的**（`agent.ts` 的自动切换：余额不足/权限不足等按 `SWITCH_KINDS` 触发，
写 `purposeModelOverrides` 后重发）—— 它本来就按 `listModelsForUse` 取下一个，
所以只要排序对了，"首选 + 回退"两件事同时成立。

> **同时修了一个既有 bug**：`pickFallbackModel` 原实现是"取第一个**不等于当前**的"，
> 当前模型若不是列表首位就会**绕回开头** —— A→B 之后 B 失败又切回 A，在两个模型间来回跳。
> 现改为**只往后走**（`pool.slice(idx + 1)`），走到末尾返回 null 而不是重试已失败过的。
> 抽成导出的纯函数 `pickNextModel(pool, current, strategy)`，让单测跑**真代码**而不是复刻一份逻辑。

**单字符串仍接受**（手写配置里"就绑一个"很常见，不该被迫写 `["x"]`），
校验与消费两侧都经 `normalizePurposeList` 归一为单元素数组（去重、去空、去两端空白）。
生成器**一律写数组**，形状统一。

**引用不存在的模型仍是整份拒绝**（既有设计：校验失败一律整体拒绝），
所以"跳过失效项"只适用于**运行时**失效（模型退役/改名）—— 那时依次试数组里的下一个。
数组项的报错路径带下标（`$.purposes.chat[0]`），用户才知道是第几项错了。

##### 2.3.3 `purposes` 与 `.ai model` 命令的分层（**v5 初稿在此处有误**）

初稿写的是「`purposes` **取代** `ext.storageSet(MODEL_PURPOSE_OVERRIDES_KEY)`」。**这行不通**，原因是一条硬约束：

> **`seal.ext` 没有配置写入 API。** 只有 `register*Config` 与 `get*Config`（`seal.d.ts:722-805`），没有 setter。插件**无法回写配置框**。

而 `.ai model <用途> <模型>` 现在靠 `savePurposeModelOverrides()`（`cmd/sub_cmd/model.ts:157-158`）写 `ext.storageSet` 持久化。若 `purposes` 只存在于配置里，该命令就只能改内存，**重载即丢** —— 是功能倒退。

**正确设计：两层，配置为默认、storage 为运行时覆盖。**

| 层 | 位置 | 谁写 | 优先级 |
| --- | --- | --- | --- |
| 持久默认 | 配置的 `purposes` | 用户在配置/生成器里改 | 低 |
| 运行时覆盖 | `ext.storageSet(MODEL_PURPOSE_OVERRIDES_KEY)` | `.ai model` 命令 | **高** |

解析顺序：**storage 覆盖 > 配置 `purposes` > 该用途候选的第一个**（见 6.3）。

这样两边的好处都保住：

- 配置里的 `purposes` 让用途绑定**跟着配置走**（重装/迁移不丢）—— 这是初稿想要的改进
- `.ai model` 仍能即时改并持久化 —— 不破坏现有功能
- 用户想固化命令的设置时，从 `.ai model` 输出抄进配置即可

**需要在 `.ai model` 的输出里标注**当前值来自哪一层（配置默认 / 运行时覆盖），否则用户分不清「我改了为什么配置里没变」。

#### `groups[]`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `purposes` | string[] | ✅ | 该组适用的用途 |
| `body` | object | ⭕ | 请求体模板 |
| `request` / `response` / `params` / `prompt` | object | ⭕ | 同 v4 语义 |

### 2.4 合并语义（必须显式）

**生效顺序**（后者覆盖前者）：

```
代码兜底默认（model_defaults.ts）
  < groups[] 中命中该用途的 body
  < 该模型自己的 request.body
```

**`bodyMode` 是必要的**，因为现有代码有两种语义且必须区分：

- `merge`：逐键深合并（对话类）
- `replace`：**整体替换**（媒体用途——`media_template.ts:238-241`，写了 `[body]` 就不叠预设结构）

v4 靠"是不是媒体用途"隐式决定；v5 显式声明。**默认值**：`kind` 为 `gen`/`tts` 时默认 `replace`，否则 `merge`。

深合并**必须判两侧都是普通对象**（`request_rules.ts:80-92` 的教训：只判一侧会把字符串 `"{text}"` 展开成 `{0:'{',1:'t'…}`）。

### 2.5 密集格式示例（出厂默认）

```json
{"version":5,"providers":[{"api":"openai-completions","baseURL":"https://api.deepseek.com/v1","apiKey":"","models":[{"id":"flash","name":"deepseek-v4-flash","kind":"text"}]}],"purposes":{"chat":"flash","compression":"flash","summarization":"flash","judge":"flash"},"groups":[{"purposes":["chat","compression","summarization","judge"],"body":{"temperature":1,"top_p":1,"max_tokens":8192,"stop":null,"stream":false}}]}
```

**出厂默认保留最小可用示例**（而非完全空）：海豹用户中"只想能用"的占多数，空配置会被认为插件坏了。`apiKey` 留空 → 启动时明确提示"请在「模型配置」填写 API Key，或用配置生成器生成"。

## 3. 插件侧：读取与解析规范

### 3.1 解析流程

```
1. 读「模型配置」字符串
   ├─ 空/仅空白 → 用出厂默认；日志 warning 提示填 key（并从旧版升级时提示重建）
   ├─ JSON.parse 失败 → 报错（含 position），并提示「可用配置生成器生成」
   └─ 成功 → 进入 2

2. 结构校验（见 3.2）——任一条失败即整体拒绝，不"尽力猜测"
   ├─ version === 5 → 通过
   └─ 其它 → 拒绝并提示版本不受支持

3. 构建运行时：ConnConfigLike[] + ModelRuleTemplate[] → Model.bootstrap()
```

**只有这一条路径。** 没有"先看有没有 v4 旧配置"这一步 —— v5 不做兼容（第 8 节）。

**行为变更**：v4 是"解析失败跳过该框、记一行日志"（`model.ts:341`）。v5 改为**整体拒绝 + 精确报错**——配置是一份完整文档，部分生效比不生效更危险。

### 3.2 校验清单（全部在解析期完成）

| 类别 | 规则 | 失败处理 |
| --- | --- | --- |
| 版本 | `version === 5` | 拒绝 |
| 唯一性 | 模型 `id` **跨所有 provider 全局唯一** | 拒绝，指出重复 id |
| 引用完整性 | `purposes` 数组里每个 id 必须存在 | 拒绝，指出路径（数组项带下标 `[j]`） |
| **类型匹配** | `purposes` 绑定的模型 `kind` 必须满足该用途（对应 `isEligible`） | 拒绝，指出路径与不匹配原因 |
| 引用完整性 | `groups[].purposes` 的元素 ∈ 8 用途 | 拒绝 |
| 必填 | `provider.apiKey` 非空 | 拒绝 |
| 必填 | `provider.baseURL` 非空且 `http(s)://` | 拒绝 |
| 枚举 | `api` ∈ 3 值 | 拒绝 |
| 枚举 | `kind` ∈ 5 值 | 拒绝 |
| 枚举 | `bodyMode` ∈ 2 值 | 拒绝 |
| 字符集 | `apiKey` 全部 ∈ `[\x21-\x7E]` | 拒绝（HTTP 头可携带集） |
| 可选值 | `provider` 若填写须为非空字符串 | 拒绝 |

### 3.3 错误报告规范

**必须给出 JSON 路径**，这是 JSON 相对 TOML 的核心优势：

```
「模型配置」校验失败：$.models[2].provider = "deepsek" 未找到对应的 provider（已定义：deepseek, silicon）
```

规则：
- 路径用 `$.a.b[0].c` 形式
- 报错包含**实际值**与**可选项**
- 一次报**全部**错误（不首错即停），便于用户一次改完
- 记 `Logger.error` 的同时，在 `.ai model` 命令输出里可见

### 4.1 从「按厂商」改为「按协议」

现状问题：`provider` 字符串同时决定多件事。**全部硬编码点（已核对：7 处，跨 5 个文件）**：

| 位置 | 代码 | 决定 |
| --- | --- | --- |
| `provider.ts:155` | `if (provider !== 'anthropic')` | 请求走哪套 |

| `adapter.ts:35` | `if (provider === 'anthropic')` | 请求体转换 |
| `adapter.ts:41` | `if (provider === 'anthropic')` | 响应归一化 |
| `list.ts:192` | `if (ctx.provider === 'anthropic')` | 列表拉取方式 |

| `session.ts:486` | `model.provider === 'anthropic' && chatStream` | 流式回退 |

（表内 7 行跨 5 个文件；**`model.ts:113` 的 URL 拼接是最容易漏的一处**——它决定了请求打到哪个端点。）

v5 改为读 `api` 字段分派：

| `api` | 请求体 | 响应 | 列表 | 鉴权头 |
| --- | --- | --- | --- | --- |

**收益**：新增一家用 Messages 协议的中转站，用户改 `api` 即可，**不必改插件源码**。

**`openai-responses` 是否本期实现**：见 12.1 待决。

### 4.2 保留的厂商特例（唯一保留项）

**百度双密钥**（`apiKey = "APIKey:SecretKey"` → 换 `access_token`）保留为**唯一**硬编码特例。

**核对结论：它已经是配置驱动的，v5 无需改动。**

- 触发条件是 `request.auth_token === "baidu-token"`（`provider.ts:148`），**不是** `provider === 'baidu'`
- 全仓库**不存在** `provider === 'baidu'` 判断（已核对）
- 内置预设自带该字段（`media_presets.ts:201`），用户也可在 `[request]` 手写（`model.ts:122` 的描述里已文档化）

因此 v5 只需**原样保留** `request.auth_token` / `auth_token_scope` 两个字段的语义（`provider.ts:73-76` 的 snake_case → camelCase 映射），不新增也不删除。

理由（为何不配置化/不删除）：它是真实存在的需求、已实现且已测（`baidu_token.ts`），配置化反而增加抽象成本。

### 4.3 `classifyModel` 瘦身（重要）

**保留**（"终值"语义，猜错后果严重——误判成对话模型会直接报错或浪费钱）：

- `rerank` / `reranker` → `gen`
- 嵌入白名单（`GENERIC_EMBED_PATTERNS`）
- 生图白名单（`GENERIC_GEN_PATTERNS`）
- 语音白名单（`GENERIC_TTS_PATTERNS`）
- 手动声明（`extra.manual`）优先级最高 —— 保留
- 接口自报能力位（`extra.embed` / `extra.vision`）—— 保留

**删除**：`GENERIC_VISION_PATTERNS` 全部 12 条正则（`catalog.ts:79-92`）。

理由：这批正则（`/[a-z0-9.-]*vision/`、`gpt-5`、`kimi-k2` 等）**最容易过期**，且猜错只是"少一个识图候选"，代价远低于误判类型。删除后一律归 `text`，由用户在配置里显式写 `"kind": "vision"`。

**同时建议放宽生图白名单的锚定**：现为 `/^flux/i`、`/^imagen/i`、`/^seedream/i`、`/^midjourney/i`、`/^sd3/i`、`/^veo/i`，锚定开头导致聚合平台的厂商前缀名（`black-forest-labs/FLUX.1-schnell`）识别不到——而这类名字在硅基流动等平台上是**主流写法**。改为词边界（`/(^|[^a-z0-9])flux/i`）即可覆盖，已用反例验证不误伤（见 9.7）。

**顺序不变**：语音必须在 vision 之前判定（`catalog.ts:109-110` 的注释：`gpt-4o-mini-tts` 含 `gpt-4o`）。删除 vision 正则后此约束自然消失，但**保留注释以防回归**。

#### 4.3.1 补入 `qwen-image`（实测发现）

阿里百炼官方的生图模型是 `qwen-image-3.0-pro` / `qwen-image-3.0` / `qwen-image-2.1-pro`，
而原白名单里**没有 `qwen-image`** —— 后果是：

- 用户在生成器里加这个模型，它被判成 `text`，**每次都得手动把类型改成「生图」**
- 若漏改，它进不了 `image-generation` 候选，表现为"配了却用不了"

已补入**两侧**（`catalog.ts` 与生成器的 `classify.js`）：

```js
/(^|[^a-z0-9])qwen-image/i
```

反例已验：`qwen-plus`、`qwen-vl-max` 仍归 `text`（视觉不靠命名猜）。这条与白名单的其余部分一起由联测 §K 守卫。

### 6.1 保留在插件（不可外移）

| 职责 | 依据 |

### 6.2 拉取行为（不变）

- `providers[].models` 为空/缺省 → 启动时 `GET /models`（等价 v4 的"不写 `models`"）
- 有 `models` → 视为钉住清单，**跳过拉取**（等价 v4 的"写了 `models`"）
- 失败按连接降级（`pending`/`error`），不影响其它连接
- `.ai model pull` 强制重拉（无视钉住清单）

### 6.3 用途解析（`resolveForUse`）

```
1. storage 运行时覆盖（.ai model 写的）存在 → 按模型 id 查（校验用途资格）
2. 配置的 purposes[use] 存在                → 按模型 id 查（校验用途资格）
3. 都没有                                   → 取该用途候选中的第一个（pool[0]）
4. 候选为空                                 → null（报"该用途无可用模型"）
```

相比原逻辑（`model.ts:503-514`）只多了一层「配置默认」，且**第 3 步与原行为一致**。分层理由见 2.3.3。

覆盖失效时（模型退役 / 改名 / 用途不符）**保留现场并记日志**，回退到下一层——与原实现一致（`model.ts:509-510`）。

## 8. v4 兼容与迁移：**不做**（硬切）

### 8.1 结论

v5 **不兼容 v4 配置、不提供迁移**。旧的两个模板框（`api连接` / `模型规则`）v5 **不再注册**，也不读取。

老用户升级后会看到出厂示例，需要**用配置生成器重新生成一份**并粘贴到「模型配置」。
出厂为空时的日志会明确提示这一点。

### 8.2 为什么（这不是取舍，是能力边界）

**迁移的本质是「读旧 → 转换 → 写新」，而海豹给不了第三步。**

`seal.ext` 只有 `register*Config`(带默认值) 与 `get*Config`，**没有 setter**（1.1）。
插件能读 `api连接`、能在内存里转成 v5，但**永远无法把结果写回「模型配置」**。

于是所谓"迁移"只能退化成**每次启动都跑一遍的兼容垫片**：

| 后果 | 说明 |
| --- | --- |
| 旧配置永远删不掉 | 没有写权限，就无法"迁移完成后清空旧框" |
| `js-toml` 必须永久保留 | 每次启动都要解析旧 TOML |
| 用户看不到转换结果 | 结果只在内存，用户无法编辑它、也无法确认对不对 |
| "保留一个版本周期"没有意义 | 迁移既然永远无法自我完成，保留期就是无限期 |

**既然永远无法完成，就不该开始。** 半吊子的兼容比没有兼容更糟：用户以为迁移过了，
实际上每次启动都在做一次看不见的转换，而旧框里的内容永远是权威来源（无法删除）。

### 8.3 影响与代价

| 项 | 影响 |
| --- | --- |
| 老用户 | 必须重新生成配置（生成器已就绪，README 有指引） |
| `.ai model` 写入的用途覆盖 | **不受影响**：存在 `ext.storageSet`（插件自己的 KV，有写权限），继续生效 |
| `js-toml` 依赖 | **不能删** —— `src/config/configs/trigger.ts` 的「评分触发配置」仍在用 |
| `STORAGE_VERSION` | **不需要递增** —— 本次改动不涉及存储结构 |

### 8.4 与 v4「模型配置 v4」的历史对照

| v4 | v5 |
| --- | --- |
| 两个 TOML 框（`api连接` + `模型规则`） | 单个 JSON 框（`模型配置`） |
| 框序 = 连接序号（位置语义） | `providers[]` 数组顺序 |
| `provider` 兼作厂商 + 协议 + 鉴权 | `api`（协议）+ `provider`（vendor，通常由 URL 反查） |
| `[types]` 表（须写在框末尾） | 模型上的 `kind` 字段 |
| `ref = [连接序号]:模型名` | 模型 `id`（全局唯一，与模型名解耦） |
| 旧配置键不再兼容读取 | **同样**：旧配置键不再兼容读取（v5 亦然） |

## 9. 配置生成器规范

### 9.1 职责（必须做）

| 职责 | 说明 |

| 遮蔽 API Key | 明文 key 前提下，分享截图必备 |
| 反向导入 | 解析已有 v5 JSON 回表单（见 9.4） |
| 本地草稿 | localStorage 存连接结构与模型选择，**含 API Key**（刷新不丢）—— 见 9.1.1 |

#### 9.1.1 API Key 存不存本地：**存**（已改，附理由）

初版按"永不落盘"做：`scheduleSave()` 写 localStorage 前把 `apiKey` 抹成空串，
`loadDraft()` 读回来也强制清空。代价是**每次刷新都要重贴 Key**。

**改成保存**，理由：

- 这是**本机上的静态页面**，而 Key **本来就已经明文存在海豹配置里**（插件侧没有环境变量可放，
  见 1.1）—— 同一台机器、同一个信任边界。再存一份到 localStorage 的**增量**风险很小。
- 代价却是实打实的：配置要反复调，每次刷新重贴一次很烦。

**唯一的真实风险场景**：把页面**托管到公网**（而不是本机打开）。那时 localStorage 属于那个源，
同源下的其它脚本能读到它。若需要公网托管，把 `scheduleSave` 里的 `providers: state.providers`
改成映射出 `apiKey: ''` 即可恢复不落盘（或换 `sessionStorage` 只保本次会话）。

界面提示同步改成"会保存在本机浏览器里（刷新不丢）；公用电脑用完请点「清空」"——
**行为必须写在界面上**，否则用户只能靠踩一次才知道（初版就没写，用户以为刷新丢 Key 是 bug）。

契约由 `tests/persist-e2e-check.html` 钉住：**两次独立页面加载 + 同一个浏览器配置**
（等价于按 F5），断言第二次加载后面板与预览里的 Key 都还在。
> 不用 `iframe.location.reload()`：headless 的 `--virtual-time-budget` 下 iframe reload 会挂住。

##### 9.2.1 「不指定」的真实语义（**已核实**）

**插件的用途解析是「先按类型精确筛候选，再取第一个」—— 不是"顺序取第一个能用的"。**

`model.ts:536-538` / `547-564`：

```ts
listModelsForUse(use) { return Model.entries.filter(e => isEligible(e, use)); }  // ① 先筛
// resolveForUse: storage 覆盖 → configPurposes → 都没命中时：
const pool = Model.listModelsForUse(use);
return pool.length > 0 ? pool[0] : null;                                          // ② 再取第一个
```

`isEligible` 是精确匹配：`text-embedding` 只吃 `embed`、`image-understanding` 只吃 `vision`、
`image-generation` 只吃 `gen`、`tts` 只吃 `tts`、对话类**排除** embed/gen/tts。
**没有该类型的模型时返回 `null`，不会退而求其次。**

验证（`unit-test-entry.ts` 的 `testPurposeExactTypeSelection`，跑真正的 `Model`）：
把 `text`/`embed`/`gen`/`tts` 四个模型按"错类型在前"排列且不绑定 `purposes`，
每个用途仍**只**命中自己类型的那个；缺类型时返回 `null`。

##### 「请求体覆盖」编辑区（折叠）

请求结构有三层来源，此前**后两层在界面上无法表达**，本轮补上：

| 层 | 来源 | 界面 |
| --- | --- | --- |
| 内置预设 | 插件 `media_presets`（**只有 tts / image-generation**） | 选对 `provider` 即可，**不用写** |
| 用途组 body | 配置 `groups[].body` | 「请求体覆盖（高级）」（折叠） |
| 逐模型覆盖 | 配置 `providers[].models[].request` | 每个模型的「请求覆盖」（折叠） |

##### 三层的命名（此前撞车，已改）

三个编辑区都写 `request`/`body` 相关字段，**名字必须能区分开**，否则用户会以为重复做了两遍：

| 层级 | 配置字段 | 名称 | 管什么 |
| --- | --- | --- | --- |
| 连接 | `providers[].request` | **连接设置覆盖** | 模型列表地址 / 鉴权头 / 超时 / 余额接口 —— **与请求体无关** |
| 模型 | `providers[].models[].request` | **请求与响应格式** | 该模型的请求体、响应取数、地址覆盖、可覆写参数、提示词 |
| 用途组 | `groups[].body` | **用途组请求体** | 某类用途共用的请求体字段 |

> 初版把前两个都叫「请求覆盖」，第三个叫「请求体覆盖」—— 三个名字互相咬，看着像做了三遍。

**逐模型「请求与响应格式」**（在模型行下方，默认折叠）**分块编辑**，不再是一个大 JSON 框：

| 子项 | 形式 | 理由 |
| --- | --- | --- |
| **请求体 body** | JSON 框（**默认展开**） | 结构自由（各厂商字段完全不同），拆分会有损 |
| **响应格式 response** | **结构化表单**（**默认展开**） | 字段固定且就那几个，做成表单用户不必懂 JSON、也不会拼错键名 |
| 地址与请求头 request | JSON 框 | 键固定但组合多变 |
| 可覆写参数 params | JSON 框 | 值是嵌套的元信息对象 |
| 提示词 prompt | JSON 框 | 就一个 `extra` 字段，但内容自由 |
| 与内置预设的合并方式 bodyMode | 下拉 | 只在有覆盖时有意义 |

**响应格式**按插件 `media.ts` 的字段一一对应（别漏也别编）：

- 取数：`data_path`（点分路径，支持数组下标）/ `data_type`（auto / url / base64 / hex）/ `error_message_path`
- 异步任务轮询（子折叠）：`task_id_path` / `task_status_path` / `poll_url` / `poll_interval`（秒）/ `poll_max` /
  `success_values` / `failure_values`（后两个在界面里是**逗号分隔**，写进配置时拆成数组）

默认值写在占位符里（插件的兜底：轮询 15s × 20 次，成功 `SUCCEEDED`/`SUCCESS`/`COMPLETED`）。
**空值一律删键**，不留空字符串 —— 配置要保持紧凑；全部清空后整个 `request` 也会消失。
##### 10.5.1 一个差点漏掉的陷阱：`Number(null) === 0`

数值字段（`poll_interval` / `poll_max`）**不能直接 `Number(v)` 再写回**：

| 表达式 | 结果 |
| --- | --- |
| `Number(null)` / `Number('')` / `Number(false)` / `Number([])` | **都是 0** |
| `Number('abc')` / `Number('1e999')` | NaN / Infinity → `JSON.stringify` 变成 **null** |

而插件侧原来的兜底是 `Number.isFinite(Number(v)) && Number(v) >= 0 ? Number(v) : 15` ——
`null → 0 → isFinite(0) 为真 → 0 >= 0 为真` → **`poll_interval` 变成 0**，
语义是"**不等待就轮询**"，会把对方接口打爆。

两侧都修：

- **插件**：`media.ts` 的 `numOrDefault()` 只接受 `number` 与数字字符串，
  `null`/布尔/数组/对象/空串一律当"没写"用默认值。（同类 `Number()` 用法我全过了一遍，
  其余都有 `> 0` 或显式空值守卫，只有 `poll_interval` 因为守卫是 `>= 0` 而中招。）
- **生成器**：新增 `subNumber()`，**非有限值不写回**（并标红），与 `jsonEditor` 同一套约定。

单测覆盖 11 种非数值输入 × 两种模式，且**把旧写法放回去验证过测试确实会失败**：

```
AssertionError: 非数值 null 必须回退默认，不能算成 0
0 !== 15
```

> body 与 response **默认展开**是刻意的：这两个是绝大多数场景要改的，
> 都折叠的话用户得点两次才够得着（外层一次 + 子层一次）。

**连接级「request 覆盖」**（在 API Key 下方，默认折叠）编辑 `providers[].request`：
`list_url`（模型列表地址）、`auth_header_name` / `headers`、`timeout`、
`balance_url` / `balance_json_path` / `balance_divisor` / `balance_currency`。
**这一项此前完全没有界面** —— 数据模型是通的（`build()` 会写、导入会保留），
但用户只能手改 JSON，于是"列表地址不在 `<baseURL>/models`"这类专属部署根本配不了。

> **为什么这两项特别需要**：识图与嵌入**没有 vendor 预设机制**
> （`MediaPresetUse` 只有 tts / image-generation），它们的结构由代码默认 + 协议转换决定。
> 用户要按 vendor 改（例如某些嵌入模型不接受 `dimensions` 参数），此前只能手写 JSON。

**JSON 编辑器的行为约定**（`jsonEditor()`，别简化）：

1. **非法 JSON 不写回** —— 用户输入到一半（`{"a":`）时若写回 `undefined`，
   配置会在用户不知情的情况下丢掉这段覆盖。只在解析成功时提交。
2. **不重建面板** —— 提交发生在 textarea 的 `input` 事件里；此时若调 `renderPanel()`
   会换掉正在输入的 textarea，立刻失焦（表现为"只能输入一个字"）。所以只切换
   关联控件的 `disabled`，绝不重渲染。
3. **空串 = 清除覆盖**，并在提示里说清。
4. 错误就地显示（红框 + 文案），不弹窗、不阻塞其它字段。

##### 供应商用途支持标注

供应商输入框下方会写出该 vendor **在插件里收录了哪些媒体用途**：

```
媒体用途：仅收录了 语音合成（未收录的用途会退回通用 OpenAI 兼容结构，多半会失败）。
```

**为什么需要**：`MEDIA_VENDORS` 是两个用途的并集，其中有只做 tts 的（ElevenLabs）
和只做生图的（Stability）。选错用途时插件的 `resolveMediaPreset` 会**静默退回通用预设**
（`table[key] ?? table['']`），请求打到 `/images/generations` 而该 vendor 没有这个接口 ——
必然失败且原本没有任何提示。

- **模型清单可为空** → 插件启动时自动拉取（见 6.2）
- 每个已选模型可标 `kind`（`text`/`vision`/`embed`/`gen`/`tts`）
- 已选模型的 `id`（**模型** id）自动生成（去重），用户可改
- **手动输入始终可用**，不依赖拉取成功

### 9.3 自动拉取模型列表

#### 9.3.1 现实约束（必须先说清）

拉取是**浏览器直连供应商** `GET {baseURL}/models`。浏览器强制 CORS：**若供应商未返回 `Access-Control-Allow-Origin`，请求会被浏览器拦下**，与 API Key 是否正确无关。

**已实测**（2026，headless 浏览器，无有效 key 也能测——CORS 头由服务器返回，与鉴权结果无关）：

| 供应商 | 浏览器直连 | 实测结果 |
| --- | --- | --- |
| DeepSeek | ✅ **放行** | HTTP 401（过了 CORS，仅鉴权失败） |
| 智谱 GLM | ✅ **放行** | HTTP 401 |
| 阿里百炼 | ✅ **放行** | HTTP 401 |
| 硅基流动 | ✅ **放行** | HTTP 401 |
| Moonshot | ✅ **放行** | HTTP 401 |
| OpenRouter | ✅ **放行** | HTTP 200 |
| Anthropic | ❌ 拦截 | 首轮「网络可达但被 CORS 拒」；次轮网络不可达 → **判为拦截**（其 `/models` 需 `anthropic-dangerous-direct-browser-access`，实测仍未放行） |
| OpenAI / xAI / Mistral | ⚠️ 本机不可达 | DNS 受干扰（`api.x.ai` 解析到 Meta 的 IP），**CORS 状态未知**；用户需自备代理 |

**结论：国内厂商全部放行**，而 aiplugin4 的用户群主要用国内厂商 —— 所以「自动拉取」**可作主入口**（按 9.2 的设计），只需对 Anthropic 与境外厂商走手动输入降级。

仍须保留降级路径：放行是**供应商当前的策略**，随时可能改。

#### 9.3.2 落地要求

1. **必须有降级路径**：拉取失败 → 显示明确原因 + 自动聚焦手动输入框
2. **错误文案要区分原因**：
   - CORS/网络失败 → 「该服务商未开放浏览器直连（CORS 限制），请手动填写模型名」
   - 401 → 「API Key 无效」
   - 404 → 「该服务商无 `/models` 接口」
3. **禁止**用公共 CORS 代理。**这会把 API Key 泄露给第三方**，绝对不允许
4. **不引入后端**（Cloudflare Worker 等一律不做——那会把 key 过一手，且违背纯静态）
5. **隐私提示**：拉取时 API Key 由浏览器**直连**发给该供应商（无第三方经手，这是最安全的方式），但会出现在开发者工具的网络面板；提示用户注意浏览器扩展

#### 9.3.3 拉取结果的处理：**先读供应商自报的能力位，再考虑按名字猜**

拉取到的**不只是模型名** —— 不少供应商在 `/models` 里直接说明模态：

| 供应商 | 字段 |
| --- | --- |
| DeepSeek | `input_modalities: ["text","image"]`（另有 `name`/`context_window`/`output_modalities`） |
| OpenRouter | `architecture.input_modalities` / `architecture.output_modalities` |
| LM Studio / vLLM | `type` / `model_type` / `kind` / `task` |
| Ollama | `capabilities`（数组或对象） |
| 通用 | `supports_vision` / `vision` |

**这是权威证据，比按名字猜准得多。** 尤其 v5 起插件不再靠命名推断视觉（4.3），不读它就会把多模态模型错标成 `text`。

##### 决定写不写 `kind`：四级优先（`decideKind`）

1. **用户手选** → 用用户选的
2. **供应商自报能力位** → 用自报的（卡片上标「· 自报」）
3. **名字命中终值白名单** → 用名字判定的（嵌入/生图/语音可确定）
4. **都不确定 → 不写这个字段**

##### 第 4 条是这套规则的核心：**猜一个错的，比不写更糟**

配置里的 `kind` 在插件侧就是 `manual`，而 `catalog.ts:110` 是：

```ts
if (extra.manual) return [extra.manual];   // 绝对优先，直接返回
```

**`manual` 一旦存在，插件自己从 `/models` 读到的 `input_modalities` 根本不会被看。**

所以：

- 生成器若把"没有证据"当成"是文本"、写下 `kind:"text"`，会把插件本来能正确识别的多模态模型**抹成纯文本** —— 用户看到的是"我明明配了视觉模型，却用不了识图"
- 留空反而让插件用 **hints + 命名兜底** 各显其能

同理，**"只报了 text" 也不当作证据**（与插件 `extractHints` 的取舍一致：网关的保守元数据会把多模态模型降级）。只有**正向证据**（vision/embed/gen/tts）才写 `kind`。

##### 顺带修正的两处同类问题

| 位置 | 原状 | 现改为 |
| --- | --- | --- |
| 生成器出厂示例 | `kind: 'text'` | 不写 `kind` |
| 插件出厂默认 `DEFAULT_V5_CONFIG` | `kind: 'text'` | 不写 `kind` |

出厂就钉一个 `kind:"text"`，等于**提前废掉**该模型的视觉能力，与用户自己添加时的规则不一致。

##### 本节修订记录

初版写的是「拉取到的模型名 → 复用插件的分类规则预填 `kind`；判定为 `text` 的**保持默认**」——
"保持默认"即写成 `text`，正是上面说的错误。已改为四级优先 + 不确定则不写。

#### 9.3.4 落地结论（**已实测完毕**）

实测结果见 9.3.1：**国内 5 家全部放行**，OpenRouter 放行；Anthropic 拦截；境外 3 家本机网络不可达。

因此：

- 「自动拉取」作**主入口**，按 9.2 的设计
- Anthropic 与境外厂商**必须能优雅降级**到手动输入（9.3.2 的文案要求）
- 卡片上已用角标标注各厂商的连通性（可直连 / CORS 拦截 / 需代理），让用户事先知道

仍在待决的只剩「境外厂商是否要额外提示自备代理」——见 12.6。

### 9.4 导入（导出的逆）

「导入…」按钮打开一个**居中对话框**，粘一份 v5 配置进来接着改 —— 对应"我配置已经跑起来了，
想微调两处"这个最常见的诉求。

两条硬约定：

1. **校验不通过就不改动任何东西** —— 用户粘错内容时不能把现有配置毁掉。
   错误就地显示（带 `$.providers[0].api` 形式的路径），对话框保持打开。
2. **表达不出来的部分不静默丢** —— 见下方"非标准用途组"。

`parseImport()`（`js/v5.js`，纯函数、可单测）负责解析与还原：

| 配置字段 | 还原到 |
| --- | --- |
| `providers[]` | 连接数组（`uid`/`templateId`/`mode` 由 app.js 按 URL 补，属 UI 概念） |
| `providers[].{displayName,timeout,request,enabled,provider}` | 原样保留 |
| `providers[].models[]` | 原样保留，含 `request` / `bodyMode` / `contextWindow` / `maxTokens` |
| `purposes` | 用途绑定 |
| `groups[]` | 命中标准分组的 body → `useBodies`；**其余 → `extraGroups` 原样保留** |

#### 9.4.1 非标准用途组（`extraGroups`）

本工具只认三种固定分组（对话系 / 识图 / 嵌入），但手写配置可能有别的分组方式。
**丢掉它们等于静默改坏用户配置**，所以原样保留、导出时附在标准分组之后，并明确警告。

一条踩过的坑：最初的做法是"把被覆盖的用途从标准分组里剔除"，结果**造出了一个新的非标准分组**
（如 `[compression,summarization,judge]`），于是反复导入导出时分组**不断增殖**。
现改为：**该族只要有一个用途被非标准分组覆盖，整族交给它们**。这样往返是幂等的。

（分组顺序可能与原文不同 —— 但 `covered` 保证了标准分组与 `extraGroups` 的用途**互不重叠**，
组间优先级只在重叠时才有意义，所以重排无影响。）

#### 9.4.2 往返不变量

`build(parseImport(x)) ≡ x`（按键序规范化比较），且**幂等**（多次往返收敛）。
联测 §I 另外钉住：往返产物必须仍被**插件**接受 —— 否则"导入改一下再导出"会得到一份装不进插件的配置。

> 注：生成器会按自己的字段顺序规范化输出（例如手写的 `bodyMode` 在 `request` 之前，
> 导出后变成 `request` 在前）。JSON 键序无语义，比较时须用键排序后的规范形式。

### 9.5 禁止事项（做了就是错的）

- ❌ 用公共 CORS 代理拉模型列表（泄露 API Key）
- ❌ 引入任何后端 / 云函数
- ❌ 校验 API Key 有效性（那是拉取的副产物，不是独立能力）
- ❌ 把 API Key 发往除该供应商外的任何地址

### 9.6 产出格式

- **单个 v5 JSON 对象**，密集格式
- 一键复制（不是"自动写入海豹"——纯静态页访问不到海豹实例）
- 附带"粘贴到 模型 → 模型配置"的说明
- 导出前跑一遍**与插件同源的校验**（3.2 的 12 条），不通过则禁止复制

### 9.7 数据单一来源（关键）

供应商默认值与示例**不得在生成器里手抄**。方案：

```
aiplugin4 仓库：src/config/static_config/providers.ts
                 ↓ 构建期导出
        dist/provider-templates.json
                 ↓ 生成器构建时读取
aiplugin4-config 仓库：js/templates.js（生成，不手写）
```

**`classifyModel` 的分类规则同样需要同源**（9.3.3 要用）：

```
aiplugin4 仓库：src/model/catalog.ts（终值白名单）
                 ↓ 构建期导出
        dist/model-classify.json
                 ↓ 生成器构建时读取
aiplugin4-config 仓库：js/classify.js（生成，不手写）
```

**落地方式**（三选一，见 12.4）：构建期脚本生成 / 生成器运行时 fetch 插件仓库的 raw 文件 / CI 定时同步并开 PR。

无论哪种，**必须有一致性测试**：

- 断言生成器的每个 provider 默认 `baseURL` 与插件侧一致
- 断言分类的**超集不变量**（**不是相等**，见下）

#### 分类的关系：超集，不是相等

两者用途不同，**不应要求一致**：

| | 插件 `classifyModel` | 生成器 `classify.js` |
| --- | --- | --- |
| 角色 | **运行时兜底** | **给用户的建议** |
| 输入 | 拉回的未知模型名 | 拉回或用户输入的模型名 |
| 原则 | 保守（猜错会把嵌入当对话，报错/浪费钱） | 尽量准（预填 kind，让配置显式化） |
| 可否多认 | — | **可以** |

**不变量：插件判为 X 的，生成器也必须判为 X。反之不要求。**

一致性测试断言的是这条，而不是"结果完全相同"。若断言相等，生成器就永远无法比插件更聪明，也就失去了"减少插件猜测"的意义。

#### 已知的有意差异

插件生图白名单用 `/^flux/i`、`/^imagen/i` 等**锚定开头**写法，因此聚合平台的厂商前缀名（`black-forest-labs/FLUX.1-schnell`）识别不到，必须靠用户声明。生成器放宽为词边界匹配（`/(^|[^a-z0-9])flux/i`）以便正确预填。

**建议插件侧同步放宽**（属 4.3 的"保留终值白名单"范围内，不改变判定顺序）；放宽后已用反例验证不误伤（`video-generation-helper`、`influx-db-model` 仍归 `text`）。

### 9.8 与 v4 生成器的关系

原 `aiplugin4-config` 产出 v4 TOML（含 `[types]` 置尾、斜杠加引号等逻辑）。**v5 改造已完成**：

- 那些 TOML 特例逻辑**全部删除**（`toml-gen.js` / `toml-parse.js` 已移除）
- **已实现**：`kind` 选择、`purposes` 绑定（含类型过滤）、供应商卡片 + 二级抽屉面板（9.2）、卡片顺序调整（↑/↓）、模型拉取（9.3）、vendor 自动识别、路径报错、API Key 不落盘
- **未实现**：拉取失败的降级路径尚未有自动化用例（代码已实现，见 10.3）
- 测试从 v4 的 50 逻辑 + 28 浏览器，重写为 v5 的 **126 逻辑 + 69 浏览器**

### 10.4 防漂移守卫：**必须放在跨仓库联测里**

生成器手抄了插件三样东西（供应商模板、16 个媒体 vendor、分类白名单），
方案 §12.4 说"靠测试守卫缓解"。**但原来的守卫是假的。**

`tests/run.mjs` 里曾有一条自称"防漂移守卫"的用例：

```js
// 这条是防漂移守卫：插件 media_presets 收录的每个 vendor 都必须能被用户选到/填到
const have = new Set(KNOWN_VENDORS.map(v => v.value));
const missMedia = MEDIA_VENDORS.filter(v => !have.has(v));
```

`KNOWN_VENDORS` 与 `MEDIA_VENDORS` **都是 `templates.js` 里的常量** ——
这个用例在检查"生成器的列表包含生成器的列表"，**恒真**，
从来没读过插件的 `media_presets.ts`。插件加第 17 个 vendor 它照样过。

**根因**：生成器单测是纯 Node，看不到插件源码。能做这件事的只有**跨仓库联测**
（它能同时 import 两边）。所以真守卫落在 `scripts/integration-config-generator.mjs` §G：

| 用例 | 断言 |
| --- | --- |
| G1 | 生成器 vendor 列表 **双向**等于插件 `media_presets` 的 vendor 并集（既不缺也不多） |
| G2 | 按用途拆开：tts 的 11 个、image-generation 的 10 个逐个都在列表里 |
| G3 | `MEDIA_VENDOR_USES` 支持矩阵与插件真实表**逐格**一致 |
| G4 | 关键 vendor 的实际预设真的能取到且带 body |
| G5 | 生成器 `DEFAULT_USE_BODIES` 与插件出厂默认 **逐字段**一致；且 `build()` 默认产出也对得上 |
| G6 | 确认插件 `MediaPresetUse` 仍只有 tts / image-generation（否则"识图/嵌入无预设"的结论要改） |
| **K** | **分类白名单**：38 个样本上"插件判为 X ⇒ 生成器也判为 X"（超集不变量），含反例 |

**G3 当场抓到了我自己手抄的错误**：我把 `google` 标成"也支持生图"，
实际插件生图那栏是 `gemini`（两者是不同的键）。这正是手抄需要守卫的证明。

**K 是 §12.4 列出的第三处手抄**（前两处是 vendor 表与用途组 body），此前一直没有守卫。
不变量是**超集**而非相等：生成器可以多认（它的定位是"建议工具"，要预填 `kind`），
但**绝不能与插件矛盾** —— 插件判为 `gen` 而生成器判为 `text`，就会写下一个错的 `kind`。

生成器单测里那条已改名为「内部自洽性」，并在注释里写明**它不是防漂移守卫**、
真守卫在联测 §G —— 免得下一个人又被名字骗了。

### 10.6 跨仓库联测

`scripts/integration-config-generator.mjs`（`npm run test:integration`）把**生成器的真实产出**喂给插件的解析/校验/适配层。生成器仓库默认取同级 `../aiplugin4-config`，不存在时**跳过**（不失败）。

| 组 | 内容 |
| --- | --- |
| A | 生成器产出的每份配置，插件都必须接受，且适配出的运行时结构符合预期（含 vendor 反查、协议透传、空模型清单→自动拉取、`enabled:false`→ignore、遮蔽 key 后仍合法） |
| B | 对同一份配置，两边对**合法/非法**的判定必须一致（15 个用例：合法最小 / api 非法 / baseURL 缺失 / 无协议头 / apiKey 缺失 / kind 非法 / 模型 id 缺失 / 模型名缺失 / id 重复 / purposes 悬空 / 未知用途 / 用途×类型不匹配 / providers 为空 / groups 空 purposes / 版本错误） |
| C | 插件的出厂默认配置，生成器也必须认；且 baseURL 与 `PROVIDER_MAP` 一致 |
| D | 生成器模板的默认地址，插件必须能反查回同一 vendor |
| E | `/models` 自报能力位 → `kind=vision` → 插件图片识别候选 |
| F | 百炼 MaaS 自建网关：host 认不出 → 必须显式 `provider`；URL 拼接不重复；渲染后的请求体正确 |
| **G** | **防漂移守卫**（见 10.4） |
| H | 逐模型请求覆盖 → 插件真实请求体（`bodyMode: merge` 与预设合并、`response` 取数生效） |
| I | 导入→导出往返产物仍被插件接受，且用途组无漂移 |
| J | 官方百炼兼容模式生图：URL / 请求体 / 参数默认值与官方文档逐项一致，零自定义配置 |
| K | 分类白名单漂移守卫（超集不变量：插件判为 X ⇒ 生成器也判为 X） |
| L | 专属 MaaS + 百炼原生：路径反查、provider 必需性、共用路径不得反查 |
| M | **vendor 判定两侧一致**：手抄路径表与插件算出的逐条相同；16 个 URL 上结论一致；模板是否该写 provider 与插件反查结果吻合 |
| O | **purposes 有序数组**：生成器产出被插件接受、保序归一；单字符串容错；非法项整份拒绝且路径带下标；两侧 normalizePurposeList 同规则 |
| N | **响应格式产出被插件完整接住**：10 个键逐个比对、数组/数字类型不变、合成模板后仍可取到；含 null 的配置仍合法（故必须运行时兜底） |

**这组测试已经抓到三类真实缺陷**（都不可由单方面测试发现）：

1. 生成器的 `validate` 只校验 UI 状态，**不含 `version` 与 `groups`** —— 用户按生成器说"没问题"去粘，插件却报错。已补 `validateConfig(cfg)` 统一口径。
2. 早期测试场景里两个连接用了同一个模型 id，**两边都正确拒绝**（说明判定一致，问题在场景而非代码）。
3. §G3 抓到生成器手抄的 vendor→用途矩阵把 `google` 错标成支持生图（实际是 `gemini`）。

### 11.1 `js-toml` 保留的原因

**与模型配置无关**：`src/config/configs/trigger.ts` 的「评分触发配置」仍在用它解析 TOML。
模型配置改 JSON 后，v5 这条路径已不再需要它（迁移代码已删），但依赖本身要留。

### 11.2 一个仍未实现项：`openai-responses`

schema 接受该枚举值（避免以后加值成为破坏性变更），但运行时**明确报错**而非静默走错协议：

```
暂不支持协议 "openai-responses"（连接 X）；请改用 openai-completions 或 anthropic-messages
```

### 11.3 第 4 步实际踩到的坑（记录备查）

改 `ref` 语义时，`findModelByRef` 里原有的 `e.ref === ref && e.name === ref` 会失效 ——
v5 的 `ref` 是模型 id（`flash`）而模型名是 `deepseek-v4-flash`，两者不再相等。
修正为「先精确匹配 ref，再退回按名匹配**且仅当唯一**」，以保住重名判歧义的既有语义。

### 11.4 清理时改写的既有测试

v4 的旧配置路径删掉后，一批测试失去了播种方式。它们不是简单删掉，而是**改测 v5 的等价语义**：

| 原测试（v4） | 改后（v5） |
| --- | --- |
| `[types]` 解析：大小写容错、点号裸键被解析成嵌套表、`[types]` 顺序错整行跳过 | `testModelKindFromV5`：kind 声明生效、含点号模型名无需引号、非法 kind **整体拒绝**（不再是"忽略该键"） |
| `ignore = 1` 与钉住清单 | `testModelIgnoreField`：`enabled:false` → ignore，进 states 但不产模型 |
| 省略 provider 取默认地址 / 两者都缺则跳过 | `testV5BaseUrlRequiredAndVendorDerived`：`baseURL` 必填（缺则整体拒绝）、vendor 由 URL 反查 |
| 「模型规则」的 `models` 定向生成工具 schema | `testMediaToolSchemaFromRules`：改用 per-model `request`（等价语义） |
| 出厂默认模板框可解析 | 断言旧框**不再注册**、出厂 v5 配置合法且能跑通 |

**这些坑本身消失了**（JSON 无引号规则、无"表必须写在最后"），所以不是"换个写法重测"，而是**测不到那些坑了** —— 这正是 v5 的收益之一。
