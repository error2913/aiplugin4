# 14 - 待机群上下文成本治理（精简方案 · 实现规格）

> 状态：**设计稿（未实现）**。**实现只看本文**；完整推导、状态机与条件表、成本模型、调研与文献见 [15-详细设计与调研存档](15-上下文成本治理-详细设计与调研存档.md)。
> 一句话目标：**待机群不再每条消息都调 LLM 压缩；不白烧 token；不丢历史。**
> 关联：`02-架构设计`、`03-核心模块详解`、`05-命令与配置`、`06-数据存储`。

---

## 1. 要解决的三件事

| # | 现状问题 | 代价 |
| --- | --- | --- |
| 1 | 待机群里**每条消息**都可能触发一次 LLM 压缩（消息块累计超 2000 字就压一次，`src/context/context.ts:248-257`） | 花的钱跟消息量成正比，**哪怕机器人一句话都没说** |
| 2 | 压缩输出无长度约束、失败无退避、**压过的块还会被再压一遍**（`:256` 的 `rawText ?? text` 取到的是上一版摘要） | 同一批内容被反复压，越压越长，原文被摘要覆盖 |
| 3 | 超限时把**整段历史一次删光**（`forceFitContext`，`:465-487`），不归档、不写记忆 | 钱花了、记录也没了 |

---

## 2. 方案（7 条核心）

| # | 方案 | 一句话 |
| --- | --- | --- |
| 1 | 冷态入库零 LLM | 待机时消息只追加 + 纯代码截断，不调压缩智能体 |
| 2 | 压缩三条规则 | 只压一次（含失败不重试）/ 只压新增 / 不更短就不采纳 |
| 3 | 不变量 | 冷态诞生的内容**永不** LLM 压缩 → 转热不回溯压缩 |
| 4 | 归档写独立分片 | 归档内容写一次分片（增量、幂等），不再随 session 重复写 |
| 5 | 转热分级装回 + 余温预热 | L0/L1/L2 三档，余温阶段备好窗口 → 转热零等待 |
| 6 | 账本 + `.ai ctx` | 按用途记 token；顺带修缓存字段未采集的 bug |
| 7 | **保存节流** | 海豹 storage 是叠加式 → `session.save()` 合并写（5 秒 / 20 条），不再每条消息写盘 |

---

## 3. 冷热与滞回（最小集）

**状态是"算出来的"，不是"存下来的"**（无状态机文件、无持久化字段）：

```ts
// src/session/session.ts
const HOT_HOLD_MS = 180_000;   // 热态保持
const COOL_DOWN_MS = 60_000;   // 冷态回落

stateOf(now): 'HOT' | 'COOLING' | 'COLD' {
  if (!(this.setting.standby || Config.base.GLOBAL_STANDBY)) return 'HOT';  // 非待机＝正常对话模式，永远热
  const busy = this.running || this.starting || this.activeRuns > 0;
  if (busy) { this.lastRelevantAt = now; return 'HOT'; }                    // 在途任务冻结衰减
  const idle = Math.max(0, now - this.lastRelevantAt);
  if (idle < HOT_HOLD_MS) return 'HOT';
  if (idle < HOT_HOLD_MS + COOL_DOWN_MS) return 'COOLING';
  return 'COLD';
}
```

**"相关活动"的精确定义（关键简化）**：**凡是调用 `session.chat()` 的，就是相关活动**。

- 覆盖：@机器人、触发正则、计数器/概率/计时器/活跃时间、judge SPEAK、媒体与子代理结果送达、定时任务。
- 不覆盖：普通消息入库（`handleReceipt` → `addUserMessage`）、系统事件（撤回/禁言/上传）。
- 实现：`session.chat()` 入口一行 `this.lastRelevantAt = Date.now()`。
- 理由：若普通消息也算，活跃群永远热；若连 @ 也不算，会频繁变冷。判断依据是"**有没有人跟它说话**"。

**没有第三个时间参数**：余温预热（§5.5）已让"重建冷却"变得多余。

## 5. 具体实现规格

### 5.1 运行时字段（`src/session/session.ts`）

```ts
lastRelevantAt: number;   // 最近一次"相关活动"（ms）
ctxStats: {               // 本会话账本（运行时）
  compression: number; summarization: number; judge: number;
};
lastSaveAt: number;       // 最近一次落盘时间（保存节流用）
saveDeferCount: number;   // 距上次落盘累计的合并写次数
saveTimer: any;           // 延迟落盘的兜底定时器
```

（另有**持久化**字段 `archiveSeq` / `lastArchivedAt`，见 §5.4；两者必须同步进 `Session.validKeysMap`。）

全部运行时字段加入 `SESSION_RUNTIME_KEYS`（`src/session/session.ts:30`）→ **不持久化**，重载后回默认（等价于回冷态，安全）。

> 命名注意：`Session.state` **已被角色状态占用**（`src/session/session.ts:92`），因此本方案不新增名为 `state` 的字段，状态一律用 `stateOf(now)` 方法算出来。

### 5.2 冷态入库（`src/context/context.ts` → `addUserMessage`）

```
async addUserMessage(ctx, text, userId, messageId):
  if 冷态（context.session.stateOf(now) === 'COLD'）:
      cut = truncateMiddle(text, Config.context.COLD_TRUNCATE)   // 留头 2/3 + 尾 1/3，中间插省略号
      umi = { text: cut, time, userId, messageId,
              ...(cut !== text ? { rawText: text } : {}) }        // 复用现有 rawText 机制
      if (cut !== text) umi.text += buildUserTruncateMarker(text.length, cut.length, messageId)
      追加到最后一个 user 消息块（现有逻辑）
      return                                                     // ← 不做单条压缩、不做合并压缩
  否则: 走 §5.3 的热态路径（现状 + 门禁）
```

- **不新建存储**：原文放在现有 `rawText` 字段，`read_raw kind=user` 无需改动即可读到。
- 新增标记：在 `src/utils/raw_marker.ts` 加 `原文已截断` 前缀（与 `原文已压缩` 同结构），并加入 `RAW_MARKER_PREFIXES`；`src/prompt/templates.ts` 的标记约定同步加一句。
- 冷态**不做合并压缩**：合并压缩是"热态"才允许的动作（§5.3）。
- **截断函数**：`truncateMiddle(text, max)` = 保留头 `⌊max×2/3⌋` + `…` + 尾 `⌊max×1/3⌋`；`max ≤ 0` 时不截断（保留尾部是为了不切断结尾的 `[img:…]` / `[audio:…]` 标签）。
- **与现有流程的关系**：冷态路径照常调用 `flushGroupUserMemories`（发言者记忆权重的 5 分钟节流持久化，`src/context/context.ts:28-41`）；**不写 pendingQueue**——冷态入库是尽力而为，不参与"忙时挂起续跑"。
- **`standby` 中途关闭**：无需迁移，下一条消息按热态处理（状态是算出来的）。

### 5.3 压缩规则（`src/context/context.ts` → `compressPreserveIfLong` 与合并压缩段）

**（a）采纳条件**（任一不满足 → 放弃、保留原文、`changed=false`）：

```
if 该批已尝试过压缩（含失败）              → 放弃（只压一次，失败也不重试）
if 输入长度 ≤ 消息压缩阈值                 → 放弃（现状）
out = await compress_agent.chat(text)      // 输出长度由 prompt + max_tokens 约束，见 (c)
if (!out || out.length >= text.length)     → 放弃（不更短就不采纳）
else                                        → 采纳，并标记该批"已尝试压缩"
```

**（b）只压一次 / 只压新增**：

- `UserMessageItem` 新增可选字段 `compressed?: boolean`（语义是"**该批已尝试过压缩**"，**含失败**）。
- 合并压缩的输入只取 `!compressed` 的条目；已尝试过的条目**永不进入下一次压缩输入**。
- 采纳时：被压的那批替换为一条块条目（`compressed: true` + `rawItems` 保留原文，现状语义）。

**（c）输出长度用 prompt 与 `max_tokens` 约束（不做事后比例校验）**：

- `compress_agent.instruction` 写明目标：**"压缩到原文的 1/5 以内、最多 500 字；只保留事实与结论"**。
- `compression` 用途的请求体把 `max_tokens` 调小（默认 8192 偏大，建议 1024）——可在「模型规则」按用途覆盖，**不新增配置**。
- 依据：Cursor 自总结 ≈1000 token、Claude Code 摘要 ≈被摘要量的 12%、Anthropic 子代理回传 1–2k token，都是在**提示词/模板层给目标长度**，而不是事后按比例卡。

**（d）入库串行化（已实现）**：压缩段是异步的，两条消息并发时会在 await 期间互相覆盖 `contentItems`（后完成者用旧快照重建，可能丢掉中间追加的条目）。实现上用**每会话 promise 链**把 `addUserMessage` 串行化（`addUserMessage` 包一层 → `addUserMessageInner`），运行时状态放模块级 `WeakMap`（`runtimeOf(ctx)`），不污染持久化字段。

> **为什么不做"收益比阈值"与"熔断"**：①"只压一次（含失败）"已保证同一批内容不会被反复送审，**空转在结构上不存在**；②"不更短就不采纳"是布尔判断，效果等价于收益比阈值却**不需要调参**；③Claude Code 的 thrashing 熔断针对的是"压缩后上下文被立刻重新填满"的循环（文件/工具输出反复占位），我们这里是消息流、新消息是新内容，不构成那个循环。

### 5.4 归档：写独立分片 key（增量、不重复写；修问题 3 且不丢历史）

**海豹的存储只有 `storageGet` / `storageSet`（`types/seal.d.ts:502-504`，无 append / list / delete）**，所以"增量存储"＝**按 key 分片，只重写变化的那一个 key**。项目内先例：`src/memory/v2/storage.ts` 把一个记忆库拆成 `meta`/`units`/`links`/`docs`/`obs` 五个 key，只写变化的那份；删除用 `storageSet(key, '')` 置空（`:69`、`:92`、`:95`）。

**归档分片（只写一次、永不重写）**

- Key：`session_<id>:arc:<seq>`，`seq` 从 1 开始、零填充三位（如 `arc:001`）。
- 内容：

  ```json
  { "seq": 3, "from": 1712345678, "to": 1712349999,
    "items": [{ "messageId": "…", "userId": "QQ:1", "time": 1712345678, "text": "原文…" }],
    "facts": ["本批 summarize 抽出的事实（可选，便于只读回查）"] }
  ```

- **幂等**：写前先 `storageGet(key)`，已存在则跳过 → 同一批重试不会重复写。
- 只 `storageSet` **新增的那个分片**；已存在的分片永不重写。

**session blob 只多两个数字**（持久化字段，**不进** `SESSION_RUNTIME_KEYS`）：

```ts
archiveSeq: number;        // 已写入的分片数
lastArchivedAt: number;    // 最近一次归档时间（审计/水位）
```

→ 归档**不额外增加**一次全量写（session 本来每条消息就要 save 一次）。

**归档流程**（`archiveByTokenIfNeeded`）：

```
while (估算 token > target):
    keepStart = getKeepStart(messages, MAX_ROUNDS)
    toArchive = messages.slice(0, keepStart)
    if (toArchive.length > 0):
        ok = await archivePrefix(toArchive)          // 现有：分块 summarize 沉淀记忆
        if (!ok) break                                // 失败即退出（不再整段硬删）
        写分片 session_<id>:arc:<archiveSeq+1>（原文 + facts）；已存在则跳过
        从 messages 移除这批条目（原文已落在分片，read_raw 仍可查）
        archiveSeq++；lastArchivedAt = now
    else:
        // 轮数不够（待机群常见：只有 1 轮）→ 走 archiveOldestItems()：按 contentItem 粒度取出最旧一段
        ok = await summarizeChunkWithRetry(这批)          // 仍先 summarize（归档的意义就是沉淀记忆）
        if (!ok) break
        写分片 → 从 messages 移除这批条目（不整段删）
```
> 实现说明：该分支同样经过 `summarize`（否则这些内容永远进不了记忆，只剩分片原文）；代价是"超限且轮数不足"时会多一次总结调用，但这只在 `上下文最大token`（默认 100 万）被突破时才会发生。

**为什么是"移除"而不是"标记"**：标记会让 session blob 随消息数持续膨胀，而且每次归档都要重写整个 blob（正是"重复写"）；写分片是增量写，还顺带让 session 体积下降（缓解 M11 写放大）。

**读取**：`read_raw` / `grep_raw` 的采集器（`src/tool/tools/raw/tool_raw.ts`）顺序改为 ①消息内 `rawText`/`rawItems` → ②归档分片（按 `archiveSeq` **从新到旧**扫描；`grep` 默认只扫最近 K 个分片以免慢）。

**清理**：分片数超过上限（默认 200）时，把最旧的分片 `storageSet(key, '')` 置空（无 delete API，置空即项目先例做法）。

**其它**：

- `forceFitContext` 的整段硬删逻辑删除；`dropOldestRound` 只保留"极端单条超限"的渲染层截断兜底（不动持久化数据）。
- 顺带修：`src/agent/agent.ts:379-393` 检查归档结果——`'failed'` 时不置 `handled.archived`、不打"已归档"、记 `[ctx-cost] 归档未完成` 并放弃本轮；`'busy'`（已有归档在飞）仍允许重发一次，保持原有"超长可自愈"的行为；`'converged'` 正常重发。
- 归档分片写入失败时**不得移除来源条目**：`writeShardIfAbsent` 返回 `written`/`exists`/`failed`，`writeArchiveShard` 返回 `stored`/`nothing`/`failed`，只有 `stored`/`nothing` 才允许移除。
- **`exists` 也要推进 `archiveSeq`**（`Math.max(archiveSeq, seq)`）：否则一旦出现"分片已写、archiveSeq 未落盘"的错位（崩溃/存档写失败），后续每批都撞同一个 seq（永远 `exists`），原文再也不会写进分片。
- **连续失败兜底**：`archiveByTokenIfNeeded` 连续失败 `ARCHIVE_FAIL_LIMIT`(3) 次后，允许一次"降级丢弃最早轮次"（不写记忆，日志可见）并返回 `converged`——否则 summarize 长期不可用（或超长内容集中在 assistant/tool、无 user 条目可归档）时，会话会**永久无法回复**。这是旧 `forceFit` 行为的受限版。

### 5.5 转热分级装回 + 渲染折叠（`src/utils/message.ts`）

**档位判定**（纯代码，只看本轮最新一条消息的文本；已实现为导出的 `pickTier`）：

```ts
export function pickTier(text: string): 'L0' | 'L1' | 'L2' {
  if (/总结|回顾|整理一下|前面说过|之前说过|汇总/.test(text)) return 'L2';
  if (/它|这个|那个|刚才|上面|继续|为什么|然后呢|结果呢|那呢/.test(text)) return 'L1';
  return 'L0';
}
```

**渲染预算**（`windowCharsForTier`）：

| 档位 | 整包预算 | 说明 |
| --- | --- | --- |
| L0（默认） | `冷态窗口字数`（默认 5000 字） | 窗口拿 60%、折叠摘要拿 40% |
| L1 | L0 + 20000 字 | 含指代/追问词时多装一段 |
| L2 | 不折叠（0） | 明确要求回顾，交给 token 预算兜底 |

**折叠实现**（`foldContextMessages`，已实现）：
- 按 **contentItem 粒度**从新到旧装窗口（待机群里整段历史是同一条 user 消息，必须能切进条目内部）；
- **`assistant(tool_calls)` + 紧随的 `tool` 结果作为原子组同留同折**——否则可能只折掉 tool_calls 而留下 tool 结果，随后被 `handleMessages` 的孤儿清理删掉，**模型静默看不到工具返回**；
- 更早内容折叠为一条 `[system:折叠摘要]` 条目（`- [from:…][time:…] 开头40字`），明细放不下时只统计条数；
- **窗口优先**：最新一条（或最新原子组）无论多长都保留，因此单条超大时整包可能略超预算（不是"绝不超"）。

**折叠只对待机会话生效**（`renderFoldBudget`）：非待机（正常对话模式）返回 0＝不折叠，交给 token 预算——否则普通私聊也会被压到 5000 字。档位判定只看**最新一条真实用户发言**（跳过系统条目，避免"继续/总结"这类提示文案把档位带偏）。

**不预热（实现时去掉的优化）**：原计划在余温阶段预构建窗口缓存，实现时发现没有收益——折叠是纯代码、毫秒级，而窗口必须按当前 `context.messages` 现算（COLD 期间仍在追加消息，缓存必然过期）；真正的冷启动成本在网络侧（前缀缓存未命中 + 首轮 prompt 大小），后者已由"档位 + 折叠预算"控制。因此**不引入 `windowReady` / `renderedCache` 字段**。

**兜底**：system prompt 已声明 `[原文已压缩]/[原文已截断]` 等标记与 `read_raw` / `grep_raw` 的用法；L0 档下模型需要更早历史时自行回查。
**原则**：含指代/追问的消息必须升 L1，**宁可多装一次，也不要为了快而答错**。

### 5.7 `.ai ctx`（新增 `src/cmd/sub_cmd/ctx.ts`，U 权限）


### 5.10 边界情况

| 情形 | 处理 |
| --- | --- |

| 重载 JS | 运行时字段丢失 → 等价回冷态；`compressed` 标记与归档分片已持久化，行为连续 |
| 字段名冲突 | **不要用 `state` 作字段名**——`Session.state` 已被角色状态占用（`src/session/session.ts:92`） |

### 5.11 保存节流（一条改动）

海豹 storage 是**叠加式**的（写同样的内容也占新空间），而 `session.save()` 现在**每条消息一次**、每次写一份完整会话（`src/pipeline.ts:783`）。实现如下：

```ts
// src/session/session.ts
save(coalesce = false) {
  const now = Date.now();
  if (coalesce) {
      this.saveDeferCount++;
      if (now - this.lastSaveAt < SAVE_MIN_INTERVAL_MS && this.saveDeferCount < SAVE_BATCH) {
          // 只标脏；安排一次兜底写入，保证最后一次变更也会落地
          if (!this.saveTimer) this.saveTimer = setTimeout(() => { this.saveTimer = null; this.save(); }, SAVE_MIN_INTERVAL_MS);
          return;
      }
  }
  …storageSet…
  this.lastSaveAt = now; this.saveDeferCount = 0;
}
```

- 常量 `SAVE_MIN_INTERVAL_MS = 5000`、`SAVE_BATCH = 20`（内置，不进配置面板）。
- **默认仍是立即写**（`save()`）：回复发出后、`.ai` 命令、归档、挂起队列变更等关键路径行为不变——不做 `force` 参数改造，避免漏改某处导致丢写。
- **只有高频入库路径传 `coalesce=true`**：`src/pipeline.ts` 的待机消息入库、ob11 补充段入库、事件录入、待机会话的指令消息入库、机器人自身消息入库（共 6 处）。
- 效果：待机群灌 1000 条消息，落盘次数从 1000 降到 **≤50**（20 条批量为主、5 秒窗口为辅）。

> 其它写入点（`usageMap`、`tokenCalibration` 每请求一次；`timerQueue` 每次定时器变更一次）频率低得多，**v1 不动**；若实测 `storage.db` 增长异常再单独处理。
> 归档分片（§5.4）本身就是"只写一次"，已符合"不要重复写"。
> 海豹是否有清理机制未能核实（`docs.sealdice.com` 404、GitHub 不可达）：归档分片按"尽力保留"对待——`read_raw` 找不到时给可读提示，`.ai ctx` 显示 `archiveSeq` 以便发现被清理。

## 6. 验收（5 个数字）

1. 待机群灌 1000 条消息：**压缩调用 0 次**。
2. 转热首轮整包（窗口 + 折叠摘要）≤ `冷态窗口字数`（默认 5000 字）。
3. 超限时不再出现"整段丢弃"日志；`.ai ctx` 显示归档分片数（`archiveSeq`）。
4. `.ai ctx` 能看到本会话调用次数、全局用途用量与缓存命中。
5. 灌 1000 条消息前后记录 `storage.db` 体积：落盘次数 ≤ 50（原为 1000 次），体积增长与消息量近似线性（而不是每消息一份完整会话拷贝）。

## 7. 明确不做（避免范围蔓延）

**全量**原文库分片（每条消息都落独立 key）、只追加 + 批量折叠的窗口渲染改造、结算三条件与两阶段、`.ai tk` 用途视图、批量/低峰结算、模型窗口自动探测、按会话覆盖、待机入库配额、学习式门禁（感知机 / 逻辑回归）、独立的"预热中"状态与**余温预热缓存**（实现时判定无收益，见 §5.5）、**judge 单次 prompt 体积上限（M16，见存档 §6.12）**、归档分片的清理命令（`.ai forget --all`）。
