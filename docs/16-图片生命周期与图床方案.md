# 16 - 图片生命周期与私人图床（方案 · 实现规格）

> 状态：**设计稿（未实现）**。全文两段：**第一部分** = 方案（决策 / 契约 / 规则 / 分期）；**第二部分** = 实现细化（文件划分 / 路由表 / SQL / 伪码 / 函数签名 / PR 级任务拆解）。规则与写法冲突时以第一部分为准。
> 一句话目标：**图片在源链接失效前被捕获；字节不落进海豹存储；图床既是 AI 的取图源，也是可管理的私人图库。**
> 关联：`03-核心模块详解`、`04-工具系统`、`06-数据存储`、`08-相关后端项目`、`09-注意事项与常见问题`。
> 涉及两个仓库：本仓库（插件）与 `aiplugin4-backends`（后端，源码在 `shop` 分支 `backends/` 下）。

## 0. 决策摘要

| # | 决策 | 理由 |
| --- | --- | --- |
| 1 | **抓取时机与存储位置解耦**：图床只解决"字节放哪儿"，不解决"什么时候抓" | 时机才是当前真正踩的坑（见 §2） |
| 2 | **另开 `image-host` 后端，不扩展 `image-url-to-base64`** | i2b64 是无状态转换器，**可能做成公共 API**；不能给它加持久化职责（见 §5.1） |
| 3 | **图床接受 URL 自己抓**（一跳），主链路不经 base64 | base64 是纯过路费：后端多一份 +33% 字符串、插件 goja 再多一份（见 §5.2） |
| 4 | **图床兼做 base64 出口**（`GET /i/<id>/b64`） | 只吃 base64 的模型直接向图床要，**i2b64 在配了图床后完全退出**（见 §5.2） |
| 5 | **id = sha256(字节)**，`/i/<id>` 即可拼出 URL | 哈希校验去重天然成立 + 不可猜 + 与扩展名无关（见 §5.4） |
| 6 | **引入 SQLite 元数据层**（Python 标准库，无额外依赖） | 来源 / 标签 / 重命名 / 搜索必须有结构化存储；热路径 `/i/<id>` 不查库（见 §5.4） |
| 7 | **PNG / GIF 原格式保存**，不转码；另存缩略图 | 动画 GIF 不能丢帧；"体积够小、访问够快"靠去重 + 缩略图 + immutable 缓存（见 §5.6、§5.7） |
| 8 | **两边都有删除权**：插件按引用释放，图床按 cap/LRU 淘汰 | 两侧都主动清理才健康；安全性由**引用计数**保证，而不是把删除权收归一方（见 §5.9） |
| 9 | **手动上传的图永不自动删**（`origin=manual`） | 人放进来的东西不能被机器清掉；WebUI 可把抓来的图"收进图库"转为 manual |
| 10 | **一个服务三个面**：REST（插件）+ MCP（AI）+ WebUI（人），共享同一份 SQLite | 同一份数据，分进程只会带来跨服务鉴权与一致性成本 |
| 11 | **WebUI 必须鉴权**；`/i/*`、`/t/*` 保持公开 | 画廊能列出全部图片 → "ID 不可猜"失效，必须用登录挡住（见 §5.8、§5.10） |
| 12 | 插件新增 **1 项配置**：「后端 → 图床」地址（默认空 = 不启用） | 与"没配图床保持现状"直接对应 |
| 13 | **图床必须做完整 SSRF 加固**（决策 3 的代价） | 接受 URL 就等于获得出网能力，这是唯一的非零攻击面（见 §5.10） |

## 1. 目标与非目标

### 目标

1. 图片在源链接失效前被捕获，AI 不再"看不见图"。
2. 字节不落进海豹 `storage.db`（当前每张转过的图会带几百 KB base64）。
3. 图床成为**可管理的私人图库**：按来源可查、可重命名、可打标签、可删除。
4. AI 能通过 MCP 检索与管理图库。
5. 两端存储都有界，且**不会互相清掉对方还需要的东西**。
6. 图床故障不成为硬依赖（逐级回退，最坏退回现状）。

### 非目标

- 不做通用图床/CDN：不做多租户、不做对外分享页、不做 S3 后端（P7 可选）。
- 不做语义/视觉搜索（CLIP 之类）：搜索限定在名称 / 标签 / 来源元数据。
- 不做实时转码（`?w=&h=&fmt=` 那套）：慢且吃 CPU；缩略图预生成，原图原样发。
- 不改「识别图片时将url转换为base64」的语义（保持 永不 / 自动 / 总是 三态）。
- **不改 `image-url-to-base64` 的任何行为**（它的加固是关联但独立的事项，见 §5.1）。

## 2. 现状盘点

### 2.1 三条链路

| 链路 | 位置 | 行为 |
| --- | --- | --- |
| 收到消息 | `src/resource/image.ts:404-443` → `createUrlImage`（`:326-335`） | **只登记 URL + imageId，并立即落盘**；不转 base64。识图条件命中才走 `imageToText` |
| 识图 | `src/resource/image.ts:268-297` | 「总是」→ 先转 base64 再识图；「自动」→ **先识图，失败才转** |
| 组包给模型 | `src/utils/message.ts:499-536` | URL 型图片调 `urlToBase64()`（10s 超时），**不受「识别图片时将url转换为base64」配置控制** |

> 结论：转换点是"第一次真的把它当图片用"的那一刻，而不是"收到的那一刻"。

### 2.2 现有兜底（已实现，不要重复造）

- 永久性失败判定：`isPermanentUrlError` 命中 `4\d{2} Client Error` / `url has expired`（`src/resource/image.ts:191-195`）。
- 阻断：1 小时冷却、连续 3 次永久放弃（`src/resource/image.ts:139-144`）。
- 模型报下载失败 → 标记 + 降级重发一轮（`src/agent/agent.ts:323-360`、`markUrlBrokenByUrls` `src/resource/image.ts:172-184`）。
- 渲染期降级：上下文存的是 `[img:id]` 文本，死图自动退化为文本标签。

### 2.3 缺口

| 缺口 | 证据 |
| --- | --- |
| `image_<id>` 只增不减 | 全仓库无删除路径；`Image.save`（`src/resource/image.ts:361-363`）只有 `storageSet` |
| **无法枚举存储键** | `types/seal.d.ts:495-504` 只有 `storageInit / storageClose / storageSet / storageGet`，**没有 remove / list** |
| base64 落进 storage | `JSON.stringify(img)` 含 base64 |
| 转换时机滞后 | 见 §2.1 |
| "图已删除"与"模型够不到"被混为一谈 | 现有降级一律标 `urlBroken`，会把"模型够不到图床"误判为"图没了"（§6.6 必修） |
| 历史图片无法枚举回收 | 没有 `storageList`，只能靠 `agent_<name>` 里持久化的 `sessionService.sessionMap`（`src/agent/agent.ts:601`、`src/session/session_service.ts:26`）尽力枚举 |

### 2.4 一条硬约束：插件自己读不了二进制

海豹的 goja `fetch` 只有 `text()` / `json()`，`text()` 会按 UTF-8 解码把原始字节替换成 U+FFFD 永久损坏（`08-相关后端项目`）。**插件永远无法自己下载图片字节。**

推论：抓取必须由后端完成（决策 3）；插件需要字节时也必须向后端要 base64（决策 4 的 `/i/<id>/b64`，或未配图床时的 i2b64）。

## 3. 设计原则

1. **职责分离**：无状态工具（i2b64）不持有数据；有状态服务（image-host）持有数据，但要为自己获得的能力付安全代价。
2. **主链路不过 base64**：能不中转就不中转。
3. **一个真相**：图片的元数据（来源/名称/标签）只存在于图床；插件只存 `hostedUrl` 与自己的回收索引。
4. **两边都有删除权，靠引用计数保证安全**：谁都可以清自己那一侧，但"删除文件"这件事必须看还有没有别人引用（§5.9）。
5. **人放进来的东西机器不能清**：`origin=manual` 永不自动删。
6. **增强而非硬依赖**：没配图床 = 完全现状；图床挂了 = 逐级回退。
7. **判据同构**：两端都是"最近使用 + 上限"，预算不同（字节 vs 条目）。

## 5. 后端方案：`image-host`

### 5.1 为什么另开，而不是扩展 i2b64

| 维度 | 扩展 i2b64 | 另开 image-host（**采用**） |
| --- | --- | --- |
| 公共服务可行性 | **被破坏**：无状态工具一旦落盘用户图片，就不能作为公共 API 开放（滥用、合规、责任面） | i2b64 保持纯净，随时可公开 |
| 发版节奏 | 图床改动会牵动公共 API 的版本 | 各自独立 |
| 安全面 | 抓取 + 持久化 + 分发 + 管理界面 + MCP 全耦合在一个进程 | 攻击面可单独评估与加固 |
| 依赖 | 需 Pillow / imageio | Flask + requests + Pillow（+ 标准库 sqlite3） |
| 代价 | — | 多一个端口与 registry 条目 |

> **i2b64 的加固（超时 / 大小上限 / scheme 校验 / 私网拦截）不属于本方案**，但因为"可能做成公共 API"，其优先级反而更高——列为**关联独立事项**，单独提 PR。

### 5.2 为什么图床自己抓，且兼做 b64 出口

| 维度 | 两跳（i2b64 → 图床） | 一跳（图床自己抓，**采用**） |
| --- | --- | --- |
| base64 开销 | 后端多一份 +33% 字符串；插件 goja 里再多一份；上传 body 里第三份 | **零**：流式下载直接落盘，边下边算 sha256，全程不进内存 |
| 网络跳数 | 2 | 1 |
| 依赖数 | i2b64 与图床都必须在线 | 只有图床必须在线 |
| 插件内存 | 需在 goja 里持有大字符串 | 只发一个 URL |
| 安全面 | 图床可做到"零出网、SSRF 为零" | **图床获得出网能力 → 必须完整 SSRF 加固**（§5.10） |

**b64 出口为什么放图床**：字节本来就在图床手上，`GET /i/<id>/b64` 只是把它 base64 一下；再让 i2b64 去下载一遍是重复劳动。于是：

> **配了图床之后，i2b64 完全退出**——抓取、内联 b64、论坛上传所需字节，全部由图床提供。i2b64 只在**未配置图床**时继续承担现状职责。

| 项 | 值 |
| --- | --- |
| 目录（`shop` 分支） | `backends/image-host/` |
| 文件 | `backend.json`、`requirements.txt`、`imagehost.py`、`webui.html`、`mcp.py` |
| 端口 | **46680**（紧邻 46678 / 46679） |

### 5.4 数据模型（SQLite）

```sql
-- 一张图 = 一份字节（哈希校验去重：id 就是 sha256，同字节必然同 id）
CREATE TABLE blob (
  id             TEXT PRIMARY KEY,   -- sha256(原图字节)，64 hex
  format         TEXT NOT NULL,      -- png / jpg / gif / webp / bmp
  mime           TEXT NOT NULL,      -- 由 magic bytes 判定，不信任声明
  size           INTEGER NOT NULL,
  created_at     INTEGER NOT NULL,
  last_access_at INTEGER NOT NULL,   -- LRU 依据
  name           TEXT,               -- 重命名（可空）
  origin         TEXT NOT NULL,      -- plugin = 插件抓的（可自动清）/ manual = 人放的（永不自动清）
  orphan_at      INTEGER,            -- 最后一次失去全部引用的时间（淘汰排序用）
  thumb_path     TEXT
);

-- 引用：一次上传 = 一条引用。同一张图被转发 N 次 = 1 份字节 + N 条引用
CREATE TABLE ref (
  id         TEXT NOT NULL,          -- → blob.id
  ref        TEXT NOT NULL,          -- 插件侧 imageId（全局唯一）；手动上传时由后端生成
  platform   TEXT,                   -- QQ / DISCORD / ...
  group_id   TEXT, user_id TEXT, message_id TEXT, session_id TEXT,
  at         INTEGER,                -- 消息时间
  raw_url    TEXT,                   -- 原始（可能已失效的）链接，排障用
  PRIMARY KEY (id, ref)
);

CREATE TABLE tag (
  id TEXT NOT NULL, tag TEXT NOT NULL,
  PRIMARY KEY (id, tag)
);

CREATE INDEX idx_blob_access ON blob(last_access_at);
CREATE INDEX idx_blob_orphan ON blob(orphan_at);
CREATE INDEX idx_ref_blob     ON ref(id);
CREATE INDEX idx_ref_group    ON ref(group_id, at);
CREATE INDEX idx_tag_tag      ON tag(tag);
```

**去重（哈希校验）**：`id = sha256(字节)`，所以"同字节 → 同 id → 目标文件已存在 → 不再写第二份"，只是**追加一条 `ref`**。这就是哈希校验去重，没有别的机制。它同时带来两个好处：不可猜（256 bit）与 URL 与扩展名无关（`/i/<id>` 自足）。

**为什么按 blob 而不是按上传建条目**：QQ 里同一张图被转发极常见，去重是"体积够小"的最大来源；名称/标签挂 blob（同一张图的不同转发不该有两套标签），来源挂 `ref`（转发史要留痕）。

**引用为什么必须存在**：它同时解决两件事——① 多个插件条目可能指向同一个 blob，删谁都不能连带删掉别人；② "两边都有删除权"必须有个不误删的判据（§5.9）。

### 5.5 接口契约

**读写分离的鉴权边界**：`/i/*`、`/t/*` 公开（模型与协议端不带 header）；`/api/*`（除 health）、`/`、`/mcp` 需 token。

#### 公开读

| 路由 | 说明 |
| --- | --- |
| `GET /i/<id>` | 原图。`Content-Type` 取自库；`Cache-Control: public, max-age=31536000, immutable`；支持 `ETag` / `If-None-Match` → `304` |
| `GET /i/<id>/b64` | `{ "base64": "...", "format": "png" }` —— **供只吃 base64 的模型**（插件 `ensureBytes` 用） |
| `GET /t/<id>` | 缩略图（WebUI 画廊用） |
| `GET /api/health` | `{ ok, image_host:true, public_base_url_set, cap_mb, used_mb, count, version }` |

#### 鉴权写 / 管理

**`POST /api/upload`** —— 三种入参形态

```jsonc
// ① 抓取（插件主用）：ref 必填 = 插件侧 imageId，作为这条引用的标识
{ "url": "https://multimedia.nt.qq.com.cn/...&rkey=...",
  "ref": "a1b2c3",
  "source": { "platform":"QQ", "group_id":"...", "user_id":"...",
              "message_id":"...", "session_id":"...", "at": 1730000000000 } }

// ② 已有字节（备用；插件主链路不使用）
{ "base64": "....", "format": "png", "ref": "a1b2c3", "source": { ... } }

// ③ multipart（WebUI 手动上传）：ref 可省略，后端生成；origin 强制为 manual
file=<二进制> + source=<JSON 字符串>
```

```jsonc
// resp 200
{ "id": "9f2c...e1",                                    // sha256
  "url": "https://img.example.com/i/9f2c...e1",
  "b64_url": "https://img.example.com/i/9f2c...e1/b64",
  "thumb_url": "https://img.example.com/t/9f2c...e1",
  "format": "png", "size": 184320,
  "reachable": true,       // = 是否配置了 PUBLIC_BASE_URL
  "dedup": true,           // true = 哈希命中已有字节，只追加了一条 ref
  "ref": "a1b2c3" }
```

错误契约（**插件靠 `upstream_status` 分类永久/可重试**）：

```jsonc
400 { "error": "bad_url" }                                  // scheme 非法 / 私网 / 解析失败
400 { "error": "unsupported_format" }                       // magic bytes 不在白名单
413 { "error": "too_large", "size": 20971520 }              // 超单文件上限（流式中断）
502 { "error": "fetch_failed", "upstream_status": 404 }     // 上游 4xx/5xx 原样透出
507 { "error": "disk_full" }                                // 淘汰后仍放不下（见 §5.9 手动图保护）
```

- **图床不重试**：一次尝试 + 超时即返回；重试策略归插件（复用现有冷却 / 退避 / 三次放弃）。
- 上游 `404` / `400` / QQ 的 `download url has expired` → 插件按现有 `isPermanentUrlError` 规则判永久 → `urlBroken`。
- 上游 `429` / `5xx` → 可重试 → 走冷却。

**`POST /api/release`**（插件释放自己的引用 —— 插件的删除权）

```jsonc
// req —— 按 ref 释放，不是按 id！按 id 会连带删掉别人对这个 blob 的引用
{ "refs": ["a1b2c3", "d4e5f6"] }
// resp
{ "released": 2, "blobs_freed": 1 }   // blobs_freed = 释放后变成"零引用"的 blob 数
```

**`POST /api/exists`**（插件对账 —— 得知图床侧删了什么）

```jsonc
// req
{ "refs": ["a1b2c3", "..."] }
// resp
{ "missing": ["..."] }     // 已不存在的 ref（blob 被清 或 ref 已被释放）；插件据此标 urlBroken / 清条目
```

**`PATCH /api/image/<id>`**（重命名 / 标签 / 收进图库）

```jsonc
{ "name": "群友发的猫",
  "add_tags": ["猫","表情包"], "remove_tags": ["待分类"],
  "origin": "manual" }     // "收进图库" = 改成 manual，从此不自动删
```

**`DELETE /api/image/<id>`**（手动删除，立即生效，连字节一起删）

**`GET /api/list`**（WebUI 与 MCP 共用）

```
?q=&tags=a,b&platform=QQ&group_id=&origin=manual&sort=created|access&order=desc&limit=50&offset=0
```

**`GET /`**（WebUI，鉴权）、**`/mcp`**（MCP Streamable HTTP，鉴权）

### 5.6 抓取与存储实现

```
<data_dir>/image-host/
  image.db                     # SQLite
  shards/ab/<id>.<ext>         # 原图（ab = id 前两位）
  thumbs/ab/<id>.webp          # 缩略图
  tmp/<uuid>.part              # 下载中；完成后 os.replace 原子落位
```

抓取流程（**流式，不进内存**）：

1. 校验 URL：scheme ∈ `http/https`；解析**全部** A/AAAA 记录，拒绝私网 / 回环 / 链路本地（§5.10）。
2. `requests.get(url, stream=True, timeout=(5,20), allow_redirects=True)`，**每一跳重定向都重做校验**，上限 3 跳。
3. 边读边算 `sha256` 并写 `tmp/<uuid>.part`；累计超 `MAX_FILE` 立即中断 → `413`。
4. 用已读前 8 字节判 magic bytes → `format` / `mime`；不在白名单 → `400`。
5. **哈希校验**：目标文件已存在 → 删临时文件，`dedup: true`，不写第二份字节，只追加一条 `ref`。
6. 否则 `os.replace` 原子落位，并生成缩略图（Pillow，最大边 `THUMB_MAX` 默认 512，等比缩放，输出 WebP；GIF 取首帧）。缩略图失败不阻断主流程，只记日志。
7. 写入 `blob`（`origin=plugin`）+ `ref` 行。

**PNG / GIF 处理约定**：

- **原图一律不转码**：PNG 存 PNG、GIF 存 GIF，**动画 GIF 不丢帧**（这是"兼容 gif"的硬要求）。
- 缩略图单独生成，GIF 取首帧 → WebP，不覆盖原图。
- 可选（P7）：JPEG 存前剥 EXIF（省体积 + 隐私）；静态 GIF 的 b64 出口支持 `?format=png`（复用 i2b64 既有语义，给不接受 GIF 的模型用）。

### 5.7 "体积够小、访问够快"的三条来源

| 手段 | 收益 |
| --- | --- |
| **哈希校验去重**（`id = sha256`） | 同一张图多群转发只存一份字节——省空间的最大头 |
| **预生成缩略图** | 画廊不必加载原图；`/t/<id>` 是几十 KB 级 |
| **immutable + ETag** | 内容寻址 URL 永不变内容，浏览器/反代/CDN 可永久缓存；304 省流量 |
| （不做）实时转码 | `?w=&h=&fmt=` 每次请求都转码，慢且吃 CPU —— 明确不做 |

### 5.9 生命周期与**交叉清理**

#### 两侧各自的清理权

| 谁 | 怎么删 | 作用范围 |
| --- | --- | --- |
| **插件** | `POST /api/release { refs }` | 只释放**自己的引用**；字节是否消失由引用计数决定 |
| **图床（自动）** | cap + LRU 淘汰 | 见下面的删除顺序 |
| **图床（手动）** | WebUI / `DELETE /api/image/<id>` | 立即删，无约束（人说了算） |

#### 引用计数是安全底线

```
blob 的引用数 = COUNT(ref WHERE id = blob.id)
插件 release 掉一个 ref  →  引用数 -1  →  若归零则置 orphan_at = now
```

**为什么插件必须按 `ref` 释放而不是按 `id`**：哈希去重意味着多个插件条目可能指向同一个 blob（同一张图被转发多次）。若按 `id` 释放，会连带抹掉其他条目的引用，那些条目就会莫名其妙变成死图。

#### 图床的删除顺序（cap 压力下）

1. `origin=plugin` 且**零引用**的，按 `orphan_at` 最旧优先 —— 插件已经明确不要了
2. 仍不够时，`origin=plugin` 且**仍有引用**的，按 `last_access_at` 最旧优先 —— 图床有删除权，被删的引用由插件下次对账（`exists`）得知
3. **`origin=manual` 永不自动删**。如果手动上传的内容本身就把 cap 占满 → **新上传直接 `507`**，而不是删手动图

> 决策 9 的代价要认下来：`origin=manual` 的图只能由人删。极端情况下图床会因为"手动图占满"而拒绝新抓取，这是刻意的——机器不该清掉人放进来的东西。
> **无宽限期**：`release` 立即生效。安全性不靠等待，而靠引用计数（还有别人引用就不会消失）+ `origin=manual`（人放的不会被清）。

#### 交叉清理（双向信号）

```
插件 → 图床：POST /api/release { refs }
    时机：插件自己的索引淘汰掉某条时（它已不再引用这张图）
    效果：立即释放该引用；若归零则该 blob 进入"可淘汰"队列

图床 → 插件：POST /api/exists { refs }
    时机：插件启动时 + 每 6 小时 + 索引 trim 后
    效果：插件把 missing 的标 urlBroken / 清条目，不再产生 image_url
```

> 注意 `exists` 用 `ref` 而不是 `id`：插件关心的是"我那条引用还在不在"，而不是"这个 blob 还在不在"。

#### 已知泄漏与兜底

插件侧若发生数据丢失（重装、storage 被清、`.ai forget` 之后），它的 ref 永远不会被 release → 那些 blob 会长期留在图床里。兜底：WebUI 按 `origin=plugin` + 最后访问时间排序，人可批量清理；或 P7 提供"释放 N 天未访问的插件引用"的管理动作。

### 5.10 安全模型（决策 3 的代价，必修）

| 面 | 处理 |
| --- | --- |
| scheme | 仅 `http/https`；拒绝 `file://`、`gopher://` 等 |
| SSRF（IP） | 解析**全部** A/AAAA，任一命中私网 / 回环 / 链路本地 / 保留段 → `400` |
| SSRF（重定向） | **每一跳都重新校验**；上限 3 跳（否则可用 302 绕过） |
| SSRF（DNS 重绑定） | 私人部署 + token 下可接受；更强时开启 host allowlist |
| host allowlist（可选） | 默认关闭；开启后只允许白名单域名（如 `*.qpic.cn`、`multimedia.nt.qq.com.cn`）。**公网部署建议开启** |
| 鉴权边界 | 公开：`/i/*`、`/t/*`、`/api/health`；鉴权：`/api/*` 其余、`/`、`/mcp` |
| 上传鉴权 | `AIPLUGIN4_BACKEND_TOKEN`（Bearer 或 `X-Token`）；MCP 走同一 token（插件 MCP 配置支持 headers） |
| WebUI 鉴权 | 密码 + 签名 cookie；**未设密码则整个 WebUI 关闭** |
| ID 不可猜 | 内容寻址 256 bit。**但画廊可列出全部 → 不可猜性对"人"失效，故 WebUI 必须鉴权** |
| 路径穿越 | 只认 `^[0-9a-f]{64}$`；`shards`/`thumbs` 路径由 id 推导，不接受外部路径 |
| 内容类型 | magic bytes 复核，不接受声明即信 |
| 体积 | 流式大小上限 + 总容量上限 + 写入前淘汰；失败路径清理 `tmp/*.part` |
| 资源占用 | 流式落盘（内存与图片大小无关）；并发抓取信号量（默认 4）；缩略图生成也走信号量 |
| XSS（WebUI） | 名称/标签渲染必须转义（用户可控内容） |

> 公网部署必须：设 token + 设 WebUI 密码 + 开启 host allowlist + 反向代理限流 + HTTPS。未设 token 时后端等于公开的 SSRF 代理，README 需明确警告。
> 隐私提示：`/i/` 一旦公网可读，等于"有链接就能看图"，**QQ 私聊图片也在内**。不可猜 ID 只是缓解；画廊有密码才挡住了"翻全部"。README 需写明。

### 6.1 数据模型

### 6.3 渲染优先级（改 `get src()`，`src/resource/image.ts:106-108`）

```
hostedUrl && hostedReachable  →  hostedUrl
base64                        →  base64Url
url                           →  url
```

### 6.4 抓取时机（一跳 + 引用 + 来源上报）

```
if (图床已配置 && Image.isTemporaryUrl(url) && 无进行中请求)
    fire-and-forget  capture(url, ref, source)     // 不阻塞消息入库
```

`capture(url, ref, source)`：

1. `POST {图床}/api/upload { url, ref, source }` → `{ id, url, b64_url, reachable, dedup }`
   - `ref` = 插件的 `imageId`。**这是引用计数的钥匙**：同一张图被转发两次会有两个 `imageId`，图床侧就是一份字节 + 两条 ref，谁都不会连带删掉谁。
2. 写 `hostedUrl` / `hostedB64Url` / `hostedReachable`：
   - `reachable=true` → **不写 base64**（模型直接拿 URL）
   - `reachable=false` → 需要内联时走 `GET /i/<id>/b64`（§6.8）
3. 失败分类（用 `upstream_status`）：
   - `400 unsupported_format` / `502 + upstream_status 4xx`（非 429）→ 永久 → 复用现有规则标 `urlBroken`
   - `502 + upstream_status 429/5xx`、连接错误、`507` → 可重试 → 走现有冷却
   - 任何失败都**不改字段**，退回现状链路

**`source` 的来源字段**（需求："能看到每个图片相关的信息来源"）：

| 字段 | 取值 |
| --- | --- |
| `platform` | `getPlatform(...)` |
| `group_id` / `user_id` | `ctx` 的群 / 发送者 |
| `message_id` | 该消息的 ID |
| `session_id` | `getSessionId(ctx)`（`handleImageMessageSegment` 已在用） |
| `at` | 消息时间 |
| `raw_url` | 原始链接（图床侧排障用） |

> **实现注意**：`handleImageMessageSegment(ctx, seg)`（`src/resource/image.ts:404`）目前**只拿得到 ctx**，拿不到 msg / messageId。需要把 `msg`（或已算好的 `messageId`）从 `handleReceipt` / `deferReceipt`（`src/session/session.ts:339-360`）透传进 `transformArrayToContent`（`src/utils/string.ts:383`）。具体 ctx 字段以 SealDice `MsgContext` 为准，实现时核对。

规则：

- 只抓**会死的链接**（QQ 图床系列，`Image.isTemporaryUrl`）。稳定公网 URL 本来不会死，不复制。
- 并发上限 4；复用现有冷却 / 三次放弃机制。
- 触发条件 = "插件给它建了 Image 条目"。未入库的图片不会创建条目，天然排除。

### 6.5 组包路径改动（`src/utils/message.ts:499-536`）

```
if (image.hostedUrl && image.hostedReachable) → 直接用 hostedUrl，跳过一切转换

```

### 6.6 可达性降级：必须区分"图没了"和"够不到"

**必须做**。否则天真实现有硬 bug：模型够不到图床 → 现有降级把 URL 永久标 `urlBroken` → 这张本来能用 base64 内联的图被永久废掉。

```
模型报 Failed to download image → collectImageUrls → 逐个 URL：
  if (是 hostedUrl):
      GET {hostedUrl}（只看状态码，不读 body —— 插件读二进制会损坏）
        200 → 图还在 = 这个模型够不到
              → 不标 urlBroken
              → 把该模型记进 image_host_state.unreachableModels
              → 该图对该模型一律内联 base64（走 /i/<id>/b64）
        404 → 真没了 → urlBroken（现有行为）
  else: 现有 markUrlBrokenByUrls 行为
```

一次失败即完成自配置，不会每轮重试。

同时 `markUrlBrokenByUrls`（`src/resource/image.ts:172-184`）必须**同时匹配 `img.url` 和 `img.hostedUrl`**——否则 `hostedUrl` 匹配不上，死图标不上，会一直重发。

### 6.7 三级清理（插件侧，行使插件的删除权）

| 级 | 对象 | 规则 | 依赖 |
| --- | --- | --- | --- |
| **L1** | `urlBroken` 的图 | 清 `base64` + 清 `raw`，只留 `description` / `rawDescription` | 无（零风险，先做） |
| **L2** | 索引条目 | `lastUsedAt` 最旧 → 超上限或超期限 → 删 `image_<id>` + 从 `imageMap` 剔除 + **`POST /api/release { refs: [imageId] }`** | 索引 |
| **L3** | 有 `hostedUrl` 的图 | `base64` 随时可丢（能重取） | 图床 |

- **按 `ref` 释放，不按 blob id**（§5.9）：同一张图的另一条转发引用不会被误伤。
- 释放后**不立即**导致文件消失——图床还要看引用数、`origin`、cap 压力（§5.9）。
- 若 release 请求失败（图床不可达），**本地条目照删**，但把 ref 记进 `image_gc_state.pendingRelease`，下次对账时补发（否则会漏引用，形成泄漏）。

**删除写法**：`ext.storageSet('image_'+id, '')`。这是本仓库的删除惯例（`06-数据存储` 中 `session_sub` 即"删除时写空串"），而 `Image.get`（`src/resource/image.ts:349-350`）遇空串返回 `null`，正好是"已删除"语义。**seal 无 `storageRemove`**。

### 6.8 touch 点、`ensureBytes` 与节流

**touch 点**（都是已在跑的路径）：渲染成 `image_url` 内容块、`imageToText`、`read_raw kind=image`、`resolve_special_id`、论坛发帖、表情包、媒体任务结果发送、`Image.ensureBytes()`。

**`Image.ensureBytes(): Promise<string>`（新增统一入口）**：

```
base64                            → 直接用
hostedB64Url                      → GET {图床}/i/<id>/b64        ← 配了图床时唯一路径
hostedUrl                         → GET {图床}/i/<id>/b64（同上，URL 已含 id）
url                               → POST {i2b64}/image-to-base64  ← 未配图床时的现状路径
```

> 配了图床后 **i2b64 不再被调用**。`ensureBytes` 是唯一需要字节的入口，替换现在各处直接读 `image.base64` 的地方：`src/tool/tools/web/tool_forum.ts:108-121`、`src/tool/tools/image/tool_image.ts:30`、`tool_meme.ts` 相关分支。

**节流（必须做，否则写放大比现在更糟）**：内存里更新 `lastUsedAt`；仅当距上次落盘 > 6h 才 `save`，或搭其他 `save` 的顺风车。索引里的 `u` 跟着同一频率更新。

### 6.9 索引、trim 与对账

现成先例：`src/agent/subagent/store.ts:118-139` 的 `trim`——保留上限 + 清理最旧已结束记录，**完全不扫描上下文**，因为它维护了索引。

**分片（解决写放大）**

- 键 `image_idx:<00..3f>`，`bucket = parseInt(sha1(imageId).slice(0,2),16) % 64`。
- append：只重写所属那一片（≈ 30–50 KB），**不是重写全量索引**。
- trim（低频）：读全部 64 片 → 全局按 `u` 排序 → 淘汰 → 只重写受影响的片。

**trim 触发**：启动后延迟一次；距上次 > 1h **或** 新增 ≥ 200 张。

**对账**：启动时 + 每 6h + trim 后，`POST {图床}/api/exists { refs }` → `missing` 的标 `urlBroken` / 清条目；同时补发 `pendingRelease`。

> **为什么必须有索引**：seal 没有 `storageList`，无法枚举 `image_<id>` 键 → 不建索引就永远找不到要删的对象。

### 6.10 失败回退链（配了图床时）

```
hostedUrl(模型可达) → 图床 b64 内联 → 原始 url → 纯文本 [img:id:描述]
```

每级失败落下一级，**任何情况下不静默丢图、不整轮 400**。

## 11. 测试要点

### 插件单测

1. `src` 优先级三态；`CQCode` 优先 `hostedUrl`。
2. LRU trim 边界：等于上限 / 超上限 / 全部 `urlBroken` / 全部未超期。
3. 分片索引：写入只改所属片、trim 只重写受影响片、分布均匀。
4. touch 节流：6h 内重复使用只落盘一次。
5. `revive` 新字段不丢（回归 `validKeysMap` 遗漏）。
6. 可达性降级：`GET hostedUrl` 200 → 不标 `urlBroken` 且记模型；404 → 标 `urlBroken`。
7. `markUrlBrokenByUrls` 能匹配 `hostedUrl`。
8. `ensureBytes` 三级回退；**配了图床时断言不调用 i2b64**。
9. 失败分类：`upstream_status` 4xx → 永久；429/5xx → 可重试。
10. 交叉清理：trim 淘汰 → 触发 `release { refs }`；release 失败 → 进 `pendingRelease` 并在对账时补发；对账 `missing` → 标死。
11. 来源上报：`source` 六个字段齐全（含消息 ID 透传）。
12. **未配置图床时全链路零变化**（回归保护）。

### 后端单测（`image-host`）

1. 流式落盘：内存占用与图片大小无关；`sha256` 与实际字节一致。
2. **PNG 原样保存**；**动画 GIF 不丢帧**（帧数与上传一致）；缩略图取 GIF 首帧。
3. **哈希去重**：同字节第二次上传 → `dedup: true`、只追加一条 ref、`tmp` 无残留、**磁盘只多一份字节**。
4. **引用计数**（核心）：
   - 同一 blob 两条 ref → release 一条 → 字节仍在、`blobs_freed=0`
   - release 两条 → 归零 → 置 `orphan_at`、`blobs_freed=1`
   - **按 ref 释放不会连带删掉另一条 ref**
5. cap 淘汰顺序：零引用 `origin=plugin`（按 `orphan_at`）→ 有引用 `origin=plugin`（按 `last_access_at`）→ **`origin=manual` 跳过**。
6. 手动图占满 cap → 新上传 `507`，且手动图仍在。
7. 单文件上限 `413`（流式中断）；磁盘满 `507`。
8. 鉴权边界：`/i/*`、`/t/*`、`/api/health` 免鉴权；`/api/*` 其余、`/`、`/mcp` 需 token。
9. WebUI：未设密码时 `/` 关闭；设密码后未登录 401、登录后可浏览；"收进图库"把 `origin` 改为 manual 后不再被自动清。
10. magic bytes 与声明不符 → `400`；非白名单格式 → `400`。
11. 路径穿越与非法 id → `404`。
12. **SSRF**：`file://`、`127.0.0.1`、`10.x`、`169.254.169.254`、IPv6 回环 → `400`；**302 跳私网** → `400`；超 3 跳 → `400`。
13. host allowlist 开启时非白名单域名 → `400`。
14. 上游 4xx/5xx → `502 + upstream_status`，且**不内部重试**。
15. `/i/<id>/b64` 返回的 base64 解码后与原图字节完全一致（含 GIF）。
16. MCP：`tools/list` 恰好 3 个工具；`image_search` 能按标签/来源命中；`image_rename` / `image_tag` 落库。
17. WebUI XSS：名称/标签含 `<script>` 时被转义。
18. `ETag` / `If-None-Match` → `304`。

### 集成

1. 起图床 + 配地址 → 发 QQ 图 → 断言：`hostedUrl` 有值、`image_<id>` 里 **无 base64**、组包产生 `image_url = hostedUrl`、**全程没有调用 i2b64**、图床里能看到该图的来源。
2. 停图床 → 断言回退现状且不报错。
3. 手工删掉图床文件 → 断言走 §8 #2 并自愈。
4. `reachable=false` → 断言模型收到的是 b64 内联而非本地 URL。
5. 同一张图在群里转发两次 → 断言图床只有一份字节、两条 ref；插件淘汰其中一条 → 另一条仍可用。
6. WebUI 把一张抓来的图"收进图库"→ 断言它在 cap 压力下不被自动删。

## 14. 明确不做 / 已知取舍

| 项 | 原因 |
| --- | --- |
| 扩展 i2b64 | 它可能做成公共 API，不能持有用户数据（§5.1） |
| 主链路经 base64 中转 | 三份 base64 的搬运成本换不来对等收益（§5.2） |
| 实时转码（`?w=&h=&fmt=`） | 每次请求都转码，慢且吃 CPU；缩略图预生成已够用 |
| 语义/视觉搜索（CLIP） | 要引入本地模型、吃内存；搜索限定元数据（P7 可议） |
| `image_delete` MCP 工具 | AI 误删代价不对称；删除留在 WebUI（人的决定） |
| 插件保存名称/标签 | 元数据真相只在图床，避免双写不一致（§3 原则 3） |
| 删除宽限期 | `release` 立即生效；安全性靠引用计数 + `origin=manual`，不靠等待 |
| 引用计数 | 插件侧不维护全局引用计数（`context_edit_replace` 会改文本导致漂移）；但**图床侧的引用计数必须做**（它就是 `ref` 表） |
| 全量引用扫描 | 用 `lastUsedAt` 代理"还在被用"，O(1) 且更准 |
| URL 健康轮询 | 三种死法已有零成本判定；轮询证明不了模型侧可达 |
| 历史孤儿图片的自动回收 | seal 无 `storageList`，物理上枚举不到 |
| 手动图占满时仍接受新上传 | 宁可 `507` 也不清人放进来的东西（§5.9） |
| 图床零出网 | 与"主链路不过 base64"互斥，选择后者 + §5.10 加固 |

鉴权判定（顺序敏感）：

```python
PUBLIC_PREFIX = ("/i/", "/t/")

def auth_ok(req) -> bool:
    p = req.path
    if p == "/api/health" or p.startswith(PUBLIC_PREFIX): return True
    if p == "/login": return True
    if p == "/" or p == "/logout": return cookie_ok(req)      # WebUI
    if p.startswith("/mcp"): return token_ok(req)             # MCP 走 token
    return token_ok(req)                                      # /api/* 其余
```

- `token_ok`：`Authorization: Bearer <t>` 或 `X-Token: <t>`；`AIPLUGIN4_BACKEND_TOKEN` 为空时**拒绝一切写操作**（返回 401），而不是放行。
  > 与现有 i2b64 的差别：那边 token 为空 = 不鉴权；这里 token 为空 = 写操作全禁。因为本服务持有数据且能出网，默认拒绝比默认放行安全。
- `cookie_ok`：`ih=<hmac>`，`hmac = HMAC_SHA256(secret, "ih")`；`secret` 由 `PASSWORD` 派生（`pbkdf2` 固定盐，进程启动时算一次）。未设 `PASSWORD` → `/` 与 `/login` 直接 `404`。

### 16.5 安全抓取（`fetch.py`）——§5.10 的具体写法

```python
MAX_REDIRECTS = 3
BLOCKED = lambda ip: (ip.is_private or ip.is_loopback or ip.is_link_local
                      or ip.is_reserved or ip.is_multicast or ip.is_unspecified)

def safe_fetch(url, max_bytes, timeout, allow_hosts, tmp_dir):
    """返回 (tmp_path, sha256_hex, size, first8)；抛 BadUrl / TooLarge / FetchFailed"""
    for hop in range(MAX_REDIRECTS + 1):
        u = urlparse(url)
        if u.scheme not in ("http", "https"):        raise BadUrl("scheme")
        if not u.hostname:                            raise BadUrl("no_host")
        if allow_hosts and not host_allowed(u.hostname, allow_hosts):
                                                      raise BadUrl("host_not_allowed")
        try:
            ips = [ip_address(s[4][0]) for s in socket.getaddrinfo(u.hostname, u.port or 80)]
        except Exception:                             raise BadUrl("dns")
        if any(BLOCKED(ip) for ip in ips):            raise BadUrl("private_ip")

        r = requests.get(url, stream=True, timeout=timeout, allow_redirects=False)
        if r.is_redirect:                             # 手动跳转：每跳都重做上面全部校验
            url = urljoin(url, r.headers["Location"]); continue
        if r.status_code >= 400:
            raise FetchFailed(r.status_code)

        h, n, tmp = hashlib.sha256(), 0, tempfile.mktemp(dir=tmp_dir)
        with open(tmp, "wb") as f:
            for chunk in r.iter_content(64 * 1024):
                n += len(chunk)
                if n > max_bytes:
                    f.close(); os.remove(tmp); raise TooLarge(n)
                h.update(chunk); f.write(chunk)
        first8 = open(tmp, "rb").read(8)
        return tmp, h.hexdigest(), n, first8
    raise BadUrl("too_many_redirects")
```

要点：

- **必须 `allow_redirects=False` 手动循环**：`requests` 的自动跳转不会给你逐跳校验的机会，`302 → 127.0.0.1` 会直接绕过 IP 拦截。这是 §5.10 里最容易写错的一条。
- `socket.getaddrinfo` 取**全部** A/AAAA（`getaddrinfo` 不指定 family 就返回两者），任一命中黑名单即拒绝。
- 残留的 TOCTOU（校验用 IP 与连接用 IP 可能不同，DNS 重绑定）在"私人部署 + token"下可接受；要更严可把 URL 换成已校验 IP + `Host` 头连接，列为 P7。
- `TooLarge` 必须删掉半截临时文件；所有异常路径都要清 `tmp/*.part`。

magic bytes 判定（不引入 Pillow 依赖，纯字节）：

### 16.6 落库、去重与容量（`store.py`）

```python
def ensure_capacity(con, need: int, cap: int, watermark=0.9):
    """写入前腾地方；返回淘汰条数。manual 永不自动删。"""
    dropped = 0
    while used_bytes(con) + need > cap * watermark:
        victim = pick_victim_tier1(con) or pick_victim_tier2(con)
        if victim is None:
            raise DiskFull(used=used_bytes(con), manual=manual_bytes(con))
        delete_blob(con, victim)          # 连带 ref/tag（CASCADE）+ 删文件 + 删缩略图
        dropped += 1
    return dropped

def put_blob(con, tmp, sha, fmt, mime, size, origin, ref, source):
    row = con.execute("SELECT id FROM blob WHERE id=?", (sha,)).fetchone()
    dedup = row is not None
    if dedup:
        os.remove(tmp)                                     # 哈希命中：不写第二份字节
        con.execute("UPDATE blob SET last_access_at=? WHERE id=?", (now_ms(), sha))
    else:
        ensure_capacity(con, size, CAP)                    # 锁内
        os.replace(tmp, blob_path(sha, fmt))               # 原子落位
        thumb = make_thumb(blob_path(sha, fmt), THUMB_MAX) # 失败 → None，不阻断
        con.execute("INSERT INTO blob(id,format,mime,size,created_at,last_access_at,origin,thumb_path)"
                    " VALUES(?,?,?,?,?,?,?,?)", (sha, fmt, mime, size, now_ms(), now_ms(), origin, thumb))
    con.execute("INSERT OR REPLACE INTO ref(id,ref,platform,group_id,user_id,message_id,session_id,at,raw_url)"
                " VALUES(?,?,?,?,?,?,?,?,?)",
                (sha, ref, source.platform, source.group_id, source.user_id,
                 source.message_id, source.session_id, source.at, source.raw_url))
    return sha, dedup
```

- `INSERT OR REPLACE` on `ref`：同一个 `ref` 重复上传是幂等的（插件重试不会产生两条引用）。
- `origin`：JSON 抓取路径恒为 `plugin`；multipart（WebUI）恒为 `manual`，**不接受客户端指定**。

释放引用：

```python
def release_refs(con, refs) -> tuple[int, int]:
    released = freed = 0
    for ref in refs:
        rows = con.execute("SELECT id FROM ref WHERE ref=?", (ref,)).fetchall()
        for (bid,) in rows:
            con.execute("DELETE FROM ref WHERE id=? AND ref=?", (bid, ref))
            released += 1
            if con.execute("SELECT COUNT(*) FROM ref WHERE id=?", (bid,)).fetchone()[0] == 0:
                con.execute("UPDATE blob SET orphan_at=? WHERE id=? AND orphan_at IS NULL",
                            (now_ms(), bid))
                freed += 1
    return released, freed
```

> **必须按 `ref` 删，不能按 `id` 删**：哈希去重下同一 blob 可能有多条 ref，按 id 删会连带抹掉别人的引用（§5.9）。

### 16.7 缩略图（Pillow）

```python
def make_thumb(path, max_edge) -> str | None:
    try:
        im = Image.open(path)
        im.seek(0)                       # 动画 GIF 只取首帧
        if im.mode not in ("RGB", "RGBA"):
            im = im.convert("RGBA")
        im.thumbnail((max_edge, max_edge), Image.LANCZOS)
        out = thumb_path_for(path)
        im.save(out, "WEBP", quality=80, method=4)
        return out
    except Exception as e:
        log.warning(f"缩略图生成失败 {path}: {e}")
        return None                      # 不阻断主流程；画廊回退用原图
```

- 原图**不转码**：PNG 存 PNG、GIF 存 GIF（动画不丢帧）。

### 16.8 并发模型

| 资源 | 处理 |
| --- | --- |
| Flask | `app.run(host=..., port=..., threaded=True)` |
| SQLite | 每请求一个连接；WAL；**写操作用全局 `threading.Lock`**（容量检查+淘汰+插入必须原子） |
| 抓取 | `threading.Semaphore(FETCH_CONCURRENCY)` 包住 `safe_fetch` |
| 缩略图 | 同一把抓取信号量（CPU 密集，别和抓取抢） |
| 淘汰 | 与写操作同一把锁；不允许并发淘汰（否则可能删多） |

### 16.9 错误码总表（插件侧分类的依据）

| HTTP | `error` | 触发 | 插件侧处理 |
| --- | --- | --- | --- |
| 400 | `bad_url` | scheme 非法 / 私网 / DNS 失败 / 跳转过多 / 域名不在白名单 | **永久**，标 `urlBroken` |
| 400 | `unsupported_format` | magic bytes 不在白名单 | **永久** |
| 401 | `unauthorized` | token 缺失或错误；或 token 未配置 | 停用图床（视为未启用）+ 日志 |
| 404 | `not_found` | id / ref 不存在 | 视为已删 → `urlBroken` |
| 413 | `too_large` | 超单文件上限（流式中断） | **永久** |
| 502 | `fetch_failed` | 上游 4xx/5xx，带 `upstream_status` | 4xx(≠429) → 永久；429/5xx → 可重试 |
| 507 | `disk_full` | 淘汰后仍放不下（手动图占满） | 可重试（冷却） |
| 500 | `internal` | 其它 | 可重试 |

响应体一律 `{"error": "...", ...}`；`502` 额外带 `upstream_status`。

```ts
function classifyHostError(status, body): HostErrorKind {
  const e = (body as any)?.error;
  if (status === 401) return 'unauthorized';
  if (status === 404) return 'permanent';
  if (status === 400) return 'permanent';                       // bad_url / unsupported_format
```

### 17.3 索引结构与分片

```ts
interface ImageIdxEntry { i: string; c: number; u: number; s: string; b: 0|1; x: 0|1; h: 0|1 }
// i=imageId  c=createdAt  u=lastUsedAt  s=sourceSessionId
// b=有 base64  x=urlBroken  h=有 hostedUrl
```

分片哈希**不能用 sha1**——插件运行在 goja，没有 `crypto`，全仓库也没有哈希工具（已确认）。用纯 JS 的 FNV-1a：

```ts
const SHARDS = 64;
function fnv1a(s: string): number {
  let h = 0x811c9dc5;
  for (let i = 0; i < s.length; i++) { h ^= s.charCodeAt(i); h = Math.imul(h, 0x01000193); }
  return h >>> 0;
}
const bucketOf = (imageId: string) => fnv1a(imageId) % SHARDS;
const keyOf    = (b: number) => `image_idx:${b.toString(16).padStart(2, '0')}`;
```

读写：append 只重写 `keyOf(bucketOf(id))` 那一键；trim 读全部 64 键。

### 17.4 trim 算法（伪码）

```
trim(now):
  if (now - lastTrimAt < TRIM_INTERVAL_MS && newSinceLastTrim < TRIM_EVERY_N) return
  entries = 读 64 个分片并合并
  victims = entries
              .filter(e => now - e.u > MAX_AGE_MS)          // 期限超期
              .sort((a,b) => a.u - b.u)                      // 最久未用优先
  overflow = entries.length - MAX_ENTRIES
  if (overflow > 0) victims = victims.concat(
      entries.filter(e => !victims.includes(e)).sort((a,b)=>a.u-b.u).slice(0, overflow))
  for v of victims:
      ext.storageSet(`image_${v.i}`, '')                     // 空串 = 删除（§6.7）
      delete Image.imageMap[v.i]
      pendingRelease.push(v.i)                               // 稍后统一释放引用
  writeBackChangedShards(entries - victims)
  lastTrimAt = now; newSinceLastTrim = 0

flushPendingRelease():
  if (pendingRelease.empty) return
  try   { await releaseRefs(pendingRelease); pendingRelease.clear() }
  catch { /* 保留，等下次对账补发 */ }
```

`pendingRelease` 持久化在 `image_gc_state.pendingRelease`（**必须落盘**，否则重载后引用泄漏）。

### 17.5 touch 与节流

```ts
// 节流时间戳只放内存，不写进 Image（否则会被 Image.save 序列化进存储）
const lastFlushed = new Map<string, number>();
const TOUCH_THROTTLE_MS = 6 * 3600 * 1000;

export function touch(img: Image) {
  const now = Date.now();
  img.lastUsedAt = now;
  if (now - (lastFlushed.get(img.imageId) || 0) < TOUCH_THROTTLE_MS) return;
  lastFlushed.set(img.imageId, now);
  Image.save(img);
  updateIndexEntry(img);        // 同步分片索引里的 u
}
```

> 为什么不把 `lastFlushedAt` 放进 `Image`：`Image.save` 是 `JSON.stringify(img)`，会把它一起写进存储；而 `validKeysMap` 又不含它，读回来会被丢弃——白写一遍。放模块级 Map 更干净。

## 18. 端到端时序

### 18.1 一次带图消息（图床已配、可达）

```
协议端 ──图片段(含 rkey 直链)──► 插件
插件: createUrlImage + Image.save（现状）        [同步]
插件: captureInBackground(ref=imageId)          [异步，不阻塞]
   ├─ POST {图床}/api/upload {url, ref, source}
   │     图床: 校验→抓取→sha256→落库→缩略图→写 blob+ref
   │     图床: 200 {id, url, b64_url, reachable:true, dedup}
   └─ 插件: 写 hostedUrl/hostedB64Url/hostedReachable, 不写 base64
插件: 组包 → [img:xxx] → image_url = hostedUrl
模型: 自己拉 hostedUrl
```

### 18.2 同一张图（不可达图床 / 只吃 b64 的模型）

```
插件: 组包 → hostedReachable=false
模型: 报 Failed to download image（若走了 URL）
插件: GET hostedUrl → 200 → 记"该模型够不到"
插件: 降级重发，对该模型内联 base64：GET /i/<id>/b64
```

### 18.3 插件淘汰与交叉清理

```
插件 trim: 选中 victim → storageSet('image_x','') → pendingRelease.push('x')
插件 flushPendingRelease: POST {图床}/api/release {refs:['x']}
图床: 删 ref('x') → 该 blob 引用数=0 → orphan_at=now
图床 cap 压力: 优先淘汰零引用且 origin=plugin 的（按 orphan_at 最旧）
插件 对账: POST {图床}/api/exists {refs:[...]} → missing → 标 urlBroken / 清条目
```
