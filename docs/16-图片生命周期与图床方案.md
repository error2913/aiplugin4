# 16 - 图片生命周期与私人图床（方案 · 实现规格）

> 状态：**设计稿（未实现）**。
> 一句话目标：**图片在源链接失效前被捕获；字节不落进海豹存储；两端存储都有界且能自动回收。**
> 关联：`03-核心模块详解`、`06-数据存储`、`08-相关后端项目`、`09-注意事项与常见问题`。
> 涉及两个仓库：本仓库（插件）与 `aiplugin4-backends`（后端，源码在 `shop` 分支 `backends/` 下）。

---

## 0. 决策摘要

| # | 决策 | 理由 |
| --- | --- | --- |
| 1 | **抓取时机与存储位置解耦**：图床只解决"字节放哪儿"，不解决"什么时候抓" | 时机才是当前真正踩的坑（见 §2） |
| 2 | **另开 `image-host` 后端，不扩展 `image-url-to-base64`** | i2b64 是无状态转换器，**可能做成公共 API**；不能给它加持久化职责（见 §5.1） |
| 3 | **图床接受 URL 自己抓**（一跳），**不经 base64 中转** | base64 是纯过路费：后端多一份 +33% 字符串、插件 goja 再多一份，收益低（见 §5.2） |
| 4 | **i2b64 退出主链路**，只在"模型够不到图床、必须内联"时兜底 | 配了图床且公网可达时，主链路完全不碰 base64 |
| 5 | **两端判据同构**：图床按字节做 LRU+cap，插件按条目做 LRU+cap | 判据一致 → 不需要引用真相、不需要互相知道对方 |
| 6 | **不做引用扫描**，用 `lastUsedAt`（最近使用）代理"被引用" | O(1)；且比静态引用更准——记的是**实际使用**，不受 `context_edit_replace` 改文本影响 |
| 7 | **不做 URL 健康轮询** | 三种死法都已有零成本判定；轮询只买到"少一轮失败请求"，且证明不了模型侧可达 |
| 8 | **可达性由 `PUBLIC_BASE_URL` 决定**，不由试探决定 | 未配置 = 图床只当"稳定重取源"，**永不**把 URL 交给模型 |
| 9 | **图床盲驱逐（LRU 自洽）**，插件不通知删除 | 插件离线时通知链会断；cap 是硬约束，永远有界 |
| 10 | 插件新增 **1 项配置**：「后端 → 图床」地址（默认空 = 不启用） | 与"没配图床保持现状"直接对应 |
| 11 | **图床必须做完整 SSRF 加固**（决策 3 的代价） | 接受 URL 就等于获得出网能力，这是本方案唯一的非零攻击面（见 §5.6） |

## 1. 目标与非目标

### 目标

1. 图片在源链接失效前被捕获，AI 不再"看不见图"。
2. 字节不落进海豹 `storage.db`（当前每张转过的图会带几百 KB base64）。
3. 两端存储都有界、可自动回收。
4. 图床故障不成为硬依赖（逐级回退，最坏退回现状）。

### 非目标

- 不做通用图床/CDN：不做相册、不做分享页、不做多用户。
- 不做图片内容审核。
- 不改「识别图片时将url转换为base64」的语义（保持 永不 / 自动 / 总是 三态）。
- **不改 `image-url-to-base64` 的任何行为**（它的加固是关联但独立的事项，见 §5.1）。

## 2. 现状盘点

### 2.1 三条链路

| 链路 | 位置 | 行为 |
| --- | --- | --- |
| 收到消息 | `src/resource/image.ts:404-443` → `createUrlImage`（`:326-335`） | **只登记 URL + imageId，并立即落盘**；不转 base64。识图条件命中才走 `imageToText` |
| 识图 | `src/resource/image.ts:268-297` | 「总是」→ 先转 base64 再识图；「自动」→ **先识图，失败才转** |
| 组包给模型 | `src/utils/message.ts:499-536` | URL 型图片调 `urlToBase64()`（10s 超时），**不受「识别图片时将url转换为base64」配置控制** |

> 结论：转换点是"第一次真的把它当图片用"的那一刻，而不是"收到的那一刻"。

### 2.2 现有兜底（已实现，不要重复造）

- 永久性失败判定：`isPermanentUrlError` 命中 `4\d{2} Client Error` / `url has expired`（`src/resource/image.ts:191-195`）。
- 阻断：1 小时冷却、连续 3 次永久放弃（`src/resource/image.ts:139-144`）。
- 模型报下载失败 → 标记 + 降级重发一轮（`src/agent/agent.ts:323-360`、`markUrlBrokenByUrls` `src/resource/image.ts:172-184`）。
- 渲染期降级：上下文存的是 `[img:id]` 文本，死图自动退化为文本标签。

### 2.3 缺口

| 缺口 | 证据 |
| --- | --- |
| `image_<id>` 只增不减 | 全仓库无删除路径；`Image.save`（`src/resource/image.ts:361-363`）只有 `storageSet` |
| **无法枚举存储键** | `types/seal.d.ts:495-504` 只有 `storageInit / storageClose / storageSet / storageGet`，**没有 remove / list** |
| base64 落进 storage | `JSON.stringify(img)` 含 base64 |
| 转换时机滞后 | 见 §2.1 |
| "图已删除"与"模型够不到"被混为一谈 | 现有降级一律标 `urlBroken`，会把"模型够不到图床"误判为"图没了"（§6.6 必修） |
| 历史图片无法枚举回收 | 没有 `storageList`，只能靠 `agent_<name>` 里持久化的 `sessionService.sessionMap`（`src/agent/agent.ts:601`、`src/session/session_service.ts:26`）尽力枚举 |

### 2.4 一条硬约束：插件自己读不了二进制

海豹的 goja `fetch` 只有 `text()` / `json()`，`text()` 会按 UTF-8 解码把原始字节替换成 U+FFFD 永久损坏（`08-相关后端项目`）。**插件永远无法自己下载图片字节**。

这条约束决定了两件事：

- **抓取必须由后端完成** → 图床自己抓（决策 3），插件只发一个 `{url}`。
- **插件需要字节时也必须经后端** → 这就是 i2b64 在"内联兜底"场景里仍不可替代的原因（§6.6、§6.8）。

## 3. 设计原则

1. **职责分离**：无状态工具（i2b64）不持有数据；有状态服务（image-host）持有数据但要为自己获得的能力付安全代价。
2. **主链路不过 base64**：能不中转就不中转。
3. **增强而非硬依赖**：没配图床 = 完全现状；图床挂了 = 逐级回退。
4. **判据同构**：两端都是"最近使用 + 上限"，只是预算不同（字节 vs 条目）。
5. **删除靠 LRU，不靠引用**：不需要知道谁引用，只需要知道最近有没有人用。

## 4. 架构总览

```
QQ 消息（带 rkey 短时效直链）
   │
   ├─ 建 Image 条目 + 立即落盘（现状不变）
   │
   └─[图床已配置 且 是短时效链接]──► POST {图床}/i {url}        ← 一跳，无 base64
                                          │
                                    流式下载 + 边下边算 sha256
                                          │
                        ┌─────────────────┴─────────────────┐
                        ▼                                   ▼
              200 { id, url, reachable }            502 { upstream_status: 404 }
                        │                                   │
                        │                            标 urlBroken（现有规则）
                        ▼
        ┌───────────────┴───────────────┐
        ▼                               ▼
  reachable=true                  reachable=false
（PUBLIC_BASE_URL 已配）        （未配 = 仅本地可达）
 丢 base64，URL 直接交给模型      保留 base64 才能内联
                                        │
                              需要字节时 → POST {i2b64}/image-to-base64 {hostedUrl}
                              （从**稳定 URL** 转，无时机压力；这是 i2b64 唯一的剩余职责）
```

**主链路只有一跳**：插件把 URL 交给图床，拿回一个稳定 URL。base64 既不落盘也不中转。

## 5. 后端方案（aiplugin4-backends）

### 5.1 为什么另开 `image-host`，而不是扩展 i2b64

| 维度 | 扩展 i2b64 | 另开 image-host（**采用**） |
| --- | --- | --- |
| 公共服务可行性 | **被破坏**：无状态工具一旦落盘用户图片，就不能作为公共 API 开放（滥用、合规、责任面） | i2b64 保持纯净，随时可公开 |
| 发版节奏 | 图床改动会牵动公共 API 的版本 | 各自独立 |
| 安全面 | 抓取 + 持久化 + 对外分发耦合在一个进程 | 抓取只服务"私人图床"这一个用途，攻击面可单独评估与加固 |
| 依赖 | 需 Pillow / imageio（转换用） | 仅 Flask + requests |
| 代价 | — | 多一个端口与 registry 条目 |

> **i2b64 的加固（超时 / 大小上限 / scheme 校验 / 私网拦截）不属于本方案**，但因为"可能做成公共 API"，它的优先级反而更高——列为**关联独立事项**，单独提 PR。

### 5.2 为什么图床自己抓，而不是"i2b64 抓 → 图床存"

| 维度 | 两跳（i2b64 → 图床） | 一跳（图床自己抓，**采用**） |
| --- | --- | --- |
| base64 开销 | 后端多一份 +33% 字符串；插件 goja 里再多一份；上传 body 里第三份 | **零**：流式下载直接落盘，边下边算 sha256，全程不进内存 |
| 网络跳数 | 2 | 1 |
| 依赖数 | i2b64 与图床都必须在线 | 只有图床必须在线 |
| 插件内存 | 需在 goja 里持有大字符串（goja 内存本来就紧张） | 只发一个 URL |
| 安全面 | 图床可做到"零出网、SSRF 为零" | **图床获得出网能力 → 必须完整 SSRF 加固**（§5.6） |

> 结论：两跳省下的那点安全面，换来的是每次抓图三份 base64 的搬运成本。**采用一跳，把安全成本一次性付在 §5.6 的加固上。**

| 项 | 值 |
| --- | --- |
| 目录（`shop` 分支） | `backends/image-host/` |
| 文件 | `backend.json`、`requirements.txt`、`imagehost.py` |

### 5.4 接口契约（共 3 条路由）

**`POST /i`**（上传，需 token）

```jsonc
// req（主用形态：只给 URL，后端自己抓）
{ "url": "https://multimedia.nt.qq.com.cn/...&rkey=..." }
// req（备用形态：客户端已有字节时用；插件主链路不使用）
{ "base64": "....", "format": "png" }

// resp 200
{
  "id": "9f2c...e1",                                   // sha256(字节)
  "url": "https://img.example.com/i/9f2c...e1.png",
  "reachable": true,                                   // = 是否配置了 PUBLIC_BASE_URL
  "format": "png",
  "size": 184320,
  "dedup": false                                       // true = 同字节已存在，只刷新 mtime
}
```

错误契约（**插件靠 `upstream_status` 分类永久/可重试**）：

```jsonc
400 { "error": "bad_url" }                                  // scheme 非法 / 私网 / 域名解析失败
400 { "error": "unsupported_format" }                       // magic bytes 不在白名单
413 { "error": "too_large", "size": 20971520 }              // 超单文件上限（流式中断）
502 { "error": "fetch_failed", "upstream_status": 404 }     // 上游 4xx/5xx 原样透出
507 { "error": "disk_full" }                                // 淘汰后仍放不下
```

- **图床不重试**：一次尝试 + 超时即返回；重试策略归插件（复用现有冷却 / 退避 / 三次放弃）。
- 上游 `404` / `400` / QQ 的 `download url has expired` → 插件按现有 `isPermanentUrlError` 规则判永久 → `urlBroken`。
- 上游 `429` / `5xx` → 可重试 → 走冷却。
- 落库失败**不影响插件主功能**：插件退回现状链路（§8 #6）。

**`GET /i/<sha256>.<ext>`**（公开，只读）

- `200` + `Content-Type` + `Cache-Control: public, max-age=31536000, immutable`。
  - 内容寻址 → URL 永不变内容，可永久缓存。**副作用：即使日后被 cap 淘汰，已缓存方仍可用**，等于多一层保护。
- `404` 不存在。**插件用它来判断"图还在不在"**（§6.6）。
- 路径校验：`^[0-9a-f]{64}\.(png|jpg|jpeg|gif|webp|bmp)$`，拒绝一切其他形态（防目录穿越）。

**`GET /health`**（公开）

```json
{ "ok": true, "image_host": true, "public_base_url_set": false,
  "cap_mb": 2048, "used_mb": 137, "count": 812 }
```

- 插件启动时探一次并缓存 → 决定要不要"收到即抓"。
- 未配置图床地址 / 服务不可达 → 插件判定"图床未启用" → 完全走现状（**向后兼容**）。

**不做**：`DELETE`（插件不拥有字节）、批量 `exists`（对账通道已砍）、格式转换（GIF 原样存，转换归 i2b64）。

### 5.5 存储布局与抓取实现

```
<data_dir>/image-host/
  shards/ab/<sha256>.<ext>     # ab = sha256 前两位，分片避免单目录爆炸
  tmp/<uuid>.part              # 下载中；完成后 os.replace 进 shards（原子）
  stats.json                   # { totalBytes, count, updatedAt }；启动扫描重建
```

抓取流程（**流式，不进内存**）：

1. 校验 URL：scheme ∈ `http/https`；解析所有 A/AAAA 记录，拒绝私网 / 回环 / 链路本地（§5.6）。
2. `requests.get(url, stream=True, timeout=(5, 20), allow_redirects=True)`。
3. 边读边算 `sha256` 并写入 `tmp/<uuid>.part`；累计超过 `MAX_FILE` 立即中断 → `413`。
4. 用已读的前 8 字节判 magic bytes，决定扩展名；不在白名单 → `400`。
5. 目标文件已存在 → 删除临时文件，`utime` 刷新 mtime，返回 `dedup: true`。
6. 否则写入前检查容量 → 必要时按 mtime 升序淘汰至 `≤ CAP × 0.9` → `os.replace` 原子落位。

- `id = sha256(字节)`，64 hex。**内容寻址**：天然去重 + 不可猜（不知道图就猜不到 URL）。
- 不做任何转码，存的就是上游字节。

### 5.6 生命周期与淘汰

| 项 | 规则 |
| --- | --- |
| 总容量 | `CAP`（默认 2048 MB）；内存维护总量 + 启动扫描重建 |
| 写入前检查 | `totalBytes + newSize > CAP` → 按 **mtime 升序**淘汰至 `≤ CAP × 0.9`（留 10% 余量，避免每次写都触发淘汰） |
| 单文件上限 | `> MAX_FILE`（默认 8 MB）→ 流式中断，`413` |
| LRU 信号 | `GET` 时 `os.utime`；**仅当距上次 > 1h 才写**（防写放大） |
| 去重 | 目标文件已存在 → 只 `utime`，返回 `dedup: true` |
| 并发 | `app.run(threaded=True)`，索引与淘汰操作加锁 |

> 用 LRU 而不是 FIFO：按上传时间清会**优先删掉长期活跃上下文里的老图**，正好是最不该删的那批。

### 5.7 安全模型（决策 3 的代价，必修）

| 面 | 处理 |
| --- | --- |
| scheme | 仅 `http/https`；拒绝 `file://`、`gopher://` 等 |
| SSRF（IP） | 解析**全部** A/AAAA 记录，任一命中私网 / 回环 / 链路本地 / 保留段 → `400` |
| SSRF（重定向） | `allow_redirects` 时**每一跳都重新做 scheme + IP 校验**；重定向次数上限 3（否则可用 302 绕过） |
| SSRF（DNS 重绑定） | 私人部署 + token 下可接受；需要更强时开启 host allowlist（见下） |
| 出网范围 | 只允许"抓取用户提交的 URL"这一条路径，无其他出网调用 |
| host allowlist（可选） | 默认关闭；开启后只允许白名单域名（如 `*.qpic.cn`、`multimedia.nt.qq.com.cn`）。**这是把 SSRF 面压到零的唯一方式**，公网部署建议开启 |
| 上传鉴权 | `AIPLUGIN4_BACKEND_TOKEN`；`/i/` 与 `/health` 豁免（模型不带 header），其余需 token |
| ID 不可猜 | 内容寻址 256 bit；不知道图就猜不到 URL |
| 路径穿越 | 白名单正则，只认精确哈希文件名；不提供目录列举 |
| 内容类型 | magic bytes 复核，不接受声明即信 |
| 体积 | 流式大小上限 + 总容量上限 + 写入前淘汰；临时文件失败路径要清理 |
| 资源占用 | 流式落盘，单次抓取内存占用与图片大小无关；建议对并发抓取加信号量（如 4） |

> 公网部署必须：设 `AIPLUGIN4_BACKEND_TOKEN` + 开启 host allowlist + 反向代理限流 + HTTPS。未设 token 时后端等于公开的 SSRF 代理，README 需明确警告。
> 隐私提示：`/i/` 一旦公网可读，等于"有链接就能看图"，**QQ 私聊图片也在内**。不可猜 ID 只是缓解。README 需写明。

## 6. 插件方案

### 6.1 数据模型

```ts
// Image 新增字段
hostedUrl: string;         // 图床对外 URL（空 = 无）
hostedReachable: boolean;  // 该 URL 模型侧是否可达
lastUsedAt: number;        // 最近一次被使用（ms）
createdAt: number;         // 创建时间（ms）
```

> **必须同步加进 `validKeysMap`**（`src/resource/image.ts:34-48`），否则 `revive` 会静默丢弃（`src/utils/utils.ts:383-390` 只拷贝 `validKeysMap` 里列出的键）。

新增存储键：

| 键 | 内容 |
| --- | --- |
| `image_idx:<00..3f>` | 索引分片（64 片），每条 `{i,c,u,s,b,x,h}`（短键名省空间） |
| `image_gc_state` | `{ lastTrimAt, indexedFrom, count }` |
| `image_host_state` | `{ enabled, reachable, probedAt, unreachableModels: string[] }` |

### 6.2 新增配置项（唯一一项）

| 配置 | 分组 | 默认 | 说明 |
| --- | --- | --- | --- |
| 图床 | 后端 | 空 | 私人图床地址（aiplugin4-backends 的 `image-host`）。**留空 = 完全现状**：不做收到即抓、不写 `hostedUrl`、渲染与清理全部走旧路径 |

「后端 → 图片转base64」（`src/config/configs/backend.ts:7`）**退出主链路**，只在"模型够不到图床、必须内联 base64"时作为字节来源使用（§6.6、§6.8）。

### 6.3 渲染优先级（改 `get src()`，`src/resource/image.ts:106-108`）

```
hostedUrl && hostedReachable  →  hostedUrl
base64                        →  base64Url
url                           →  url
```

`CQCode`（`src/resource/image.ts:91-95`）同步改为 **`hostedUrl` 优先**（NapCat 是本机/局域网，取得到本地图床），其次 `url` / `path`。否则 QQ 直链过期后"把图发回去"会失败。

### 6.4 抓取时机（一跳）

```
if (图床已配置 && Image.isTemporaryUrl(url) && 无进行中请求)
    fire-and-forget  capture(url)     // 不阻塞消息入库
```

`capture(url)`：

1. `POST {图床}/i { url }` → `{ id, url, reachable, format }`
2. 写 `hostedUrl` / `hostedReachable`：
   - `reachable=true` → **不写 base64**（模型直接拿 URL，主链路零 base64）
   - `reachable=false` → 保留后续内联能力（字节按需从 `hostedUrl` 经 i2b64 取，§6.8）
3. 失败分类（用 `upstream_status`）：
   - `400 unsupported_format` / `502 + upstream_status 4xx`（非 429）→ 永久 → 复用现有规则标 `urlBroken`
   - `502 + upstream_status 429/5xx`、连接错误、`507` → 可重试 → 走现有冷却
   - 任何失败都**不改字段**，退回现状链路

规则：

- 只抓**会死的链接**（QQ 图床系列，`Image.isTemporaryUrl`）。稳定公网 URL 本来不会死，不复制。
- 并发上限 4；复用现有冷却 / 三次放弃机制（`IMAGE_BASE64_RETRY_TTL` / `IMAGE_BASE64_RETRY_MAX` 同一套语义，可另立同名常量）。
- 触发条件 = "插件给它建了 Image 条目"（即它会进上下文）。未入库的图片本来就不会创建条目，天然排除。

### 6.5 组包路径改动（`src/utils/message.ts:499-536`）

```
if (image.hostedUrl && image.hostedReachable) → 直接用 hostedUrl，跳过一切转换
else if (type==='url' && !base64 && !isBase64RetryBlocked()) → 现状
```

`imageToText`（`src/resource/image.ts:268-297`）同样加这条提前返回，避免「总是」模式下多打一次转换。

### 6.6 可达性降级：必须区分"图没了"和"够不到"

这是**必须做**的一条。否则天真实现有硬 bug：模型够不到图床 → 现有降级把 URL 永久标 `urlBroken` → 这张本来能用 base64 内联的图被永久废掉。

```
模型报 Failed to download image → collectImageUrls → 逐个 URL：
  if (是 hostedUrl):
      GET {hostedUrl}（只看状态码，不读 body —— 插件读不了二进制，读 body 会损坏）
        200 → 图还在 = 这个模型够不到
              → 不标 urlBroken
              → 把该模型记进 image_host_state.unreachableModels
              → 该图对该模型一律内联 base64（§6.8）
        404 → 真没了 → urlBroken（现有行为）
  else: 现有 markUrlBrokenByUrls 行为
```

- 用 `GET hostedUrl` 判存在性，**不再经过 i2b64**（i2b64 只在真正要字节时才用）。
- 一次失败即完成自配置，不会每轮重试。

同时 `markUrlBrokenByUrls`（`src/resource/image.ts:172-184`）必须**同时匹配 `img.url` 和 `img.hostedUrl`**——否则 `hostedUrl` 根本匹配不上，死图标不上，会一直重发。

### 6.7 三级清理

| 级 | 对象 | 规则 | 依赖 |
| --- | --- | --- | --- |
| **L1** | `urlBroken` 的图 | 清 `base64` + 清 `raw`，只留 `description` / `rawDescription` | 无（零风险，先做） |
| **L2** | 索引条目 | `lastUsedAt` 最旧 → 超上限或超期限 → 删 `image_<id>` + 从 `imageMap` 剔除 | 索引 |
| **L3** | 有 `hostedUrl` 的图 | `base64` 随时可丢（能重建） | 图床 |

**删除写法**：`ext.storageSet('image_'+id, '')`。这是本仓库的删除惯例（`06-数据存储` 中 `session_sub` 即"删除时写空串"），而 `Image.get`（`src/resource/image.ts:349-350`）遇空串返回 `null`，正好是"已删除"语义。**seal 无 `storageRemove`**。

### 6.8 touch 点、`ensureBytes` 与节流

**touch 点**（都是已在跑的路径）：渲染成 `image_url` 内容块、`imageToText`、`read_raw kind=image`、`resolve_special_id`、论坛发帖、表情包、媒体任务结果发送、`Image.ensureBytes()`。

**`Image.ensureBytes(): Promise<string>`（新增统一入口）**，优先级：

```
base64                            → 直接用
hostedUrl && 需要内联时            → POST {i2b64}/image-to-base64 {hostedUrl}   ← 从稳定 URL 转，无时机压力
url                               → 现状转换
```

替换现在各处直接读 `image.base64` 的地方：

- `src/tool/tools/web/tool_forum.ts:108-121`（论坛上传仍需要 base64，走这条）
- `src/tool/tools/image/tool_image.ts:30`
- `src/tool/tools/image/tool_meme.ts` 相关分支

> 这是 i2b64 在配了图床之后的**唯一职责**：把"稳定 URL"变成内联字节。它不再参与抓取。

**节流（必须做，否则写放大比现在更糟）**：内存里更新 `lastUsedAt`；仅当距上次落盘 > 6h 才 `save`，或搭其他 `save` 的顺风车。索引里的 `u` 跟着同一频率更新。

### 6.9 索引与 trim（照 `SubAgentStore` 抄）

现成先例：`src/agent/subagent/store.ts:118-139` 的 `trim`——保留上限 + 清理最旧已结束记录，**完全不扫描上下文**，因为它维护了索引。

**分片（解决写放大）**

- 键 `image_idx:<00..3f>`，`bucket = parseInt(sha1(imageId).slice(0,2),16) % 64`。
- append：只重写所属那一片（≈ 30–50 KB），**不是重写全量索引**。
- trim（低频）：读全部 64 片 → 全局按 `u` 排序 → 淘汰 → 只重写受影响的片。

**trim 触发**

- 启动后延迟一次（不拖慢启动）。
- 距上次 > 1h **或** 新增 ≥ 200 张。
- 判定用内存计数，不读盘。

> **为什么必须有索引**：seal 没有 `storageList`，无法枚举 `image_<id>` 键 → 不建索引就永远找不到要删的对象。

### 6.10 失败回退链（配了图床时）

```
hostedUrl(模型可达) → base64(内联) → 原始 url → 纯文本 [img:id:描述]
```

每级失败落下一级，**任何情况下不静默丢图、不整轮 400**。

## 8. 失效模式矩阵

| # | 场景 | 判定 | 表现 | 自愈 | 日志 |
| --- | --- | --- | --- | --- | --- |
| 1 | 抓取前链接已死 | `502 + upstream_status 4xx`（非 429） | 文本标签 | 永久 `urlBroken`，不再重试 | `图片x的URL已确认不可用` |
| 2 | 图床文件被 cap 清掉 | `GET hostedUrl` → 404 | 文本标签 | 标 `urlBroken`，一次 | `[image-host] 已清理` |
| 3 | 图还在但模型够不到 | `GET hostedUrl` → **200** | 首次失败一轮 | 记该模型不可达，改内联 base64 | `[image-unreachable]` |
| 4 | 图床没启动 / 不可达 | 连接错误 | 走现状链路 | 冷却后重试 | `[image-host] 不可达` |
| 5 | 上游限速 / 5xx | `502 + upstream_status 429/5xx` | 走现状链路 | 冷却后重试 | `[image-host] 上游可重试` |
| 6 | 磁盘满 / 超单文件 | `413` / `507` | 走现状链路 | cap 淘汰后恢复 | `[image-host] 落库失败` |
| 7 | 上游格式不在白名单 | `400 unsupported_format` | 走现状链路 | 不重试 | `[image-host] 格式不支持` |
| 8 | 未配置图床地址 | 启动探测跳过 | **完全现状** | — | `[image-host] 未启用` |
| 9 | 需要内联但 i2b64 不可用 | `ensureBytes` 全链失败 | 文本标签 | 冷却后重试 | `[image-host] 取字节失败` |

## 11. 测试要点

### 插件单测

1. `src` 优先级三态；`CQCode` 优先 `hostedUrl`。
2. LRU trim 边界：恰好等于上限 / 超上限 / 全部 `urlBroken` / 全部未超期。
3. 分片索引：写入只改所属片、trim 只重写受影响片、64 片分布均匀。
4. touch 节流：6h 内重复使用只落盘一次。
5. `revive` 新字段不丢（回归 `validKeysMap` 遗漏）。
6. 可达性降级：`GET hostedUrl` 200 → 不标 `urlBroken` 且记模型；404 → 标 `urlBroken`。
7. `markUrlBrokenByUrls` 能匹配 `hostedUrl`。
8. `ensureBytes` 三级回退（含"从 hostedUrl 经 i2b64 取字节"）。
9. 失败分类：`upstream_status` 4xx → 永久；429/5xx → 可重试。
10. **未配置图床时全链路零变化**（回归保护）。

### 后端单测（`image-host`）

1. 流式落盘：内存占用与图片大小无关；`sha256` 与实际字节一致。
2. cap 淘汰到 90%、按 mtime 升序。
3. 内容寻址去重（同字节同 URL，`dedup: true`，临时文件被清理）。
4. 单文件上限 `413`（流式中断）；磁盘满 `507`。
5. `/i/` 与 `/health` 豁免鉴权、其余仍需 token。
6. magic bytes 与声明不符 → `400`；非白名单格式 → `400`。
7. 路径穿越与非法文件名 → `404`。
8. **SSRF**：`file://`、`127.0.0.1`、`10.x`、`169.254.169.254`、IPv6 回环 → `400`；**302 重定向到私网** → `400`；重定向超过 3 跳 → `400`。
9. host allowlist 开启时，非白名单域名 → `400`。
10. 上游 4xx/5xx 透出为 `502 + upstream_status`，且**不做内部重试**。
11. 失败路径不残留 `tmp/*.part`。

### 集成

1. 起图床 + 配地址 → 发 QQ 图 → 断言：`hostedUrl` 有值、`image_<id>` 里 **无 base64**、组包产生 `image_url = hostedUrl`、**全程没有调用 i2b64**。
2. 停图床 → 断言回退现状且不报错。
3. 手工删掉图床文件 → 断言走 §8 #2 失效模式并自愈。
4. `reachable=false`（不配 `PUBLIC_BASE_URL`）→ 断言模型收到的是内联 base64 而非本地 URL。

## 14. 明确不做 / 已知取舍

| 项 | 原因 |
| --- | --- |
| 扩展 i2b64 | 它可能做成公共 API，不能持有用户数据（§5.1） |
| 主链路经 base64 中转 | 三份 base64 的搬运成本换不来对等收益（§5.2） |
| 图床做格式转换 | 转换归 i2b64；图床存上游原字节，避免两处转码语义分叉 |
| 引用计数 | `context_edit_replace` 能任意改文本 → 计数必然漂移 |
| 全量引用扫描 | 用 `lastUsedAt` 替代，O(1) 且更准 |
| URL 健康轮询 | 三种死法已有零成本判定；轮询证明不了模型侧可达 |
| 图床"引用消失即删除" | 插件离线时通知链会断；LRU 自洽更皮实 |
| 批量对账通道 | 收益仅"少一轮失败请求"，已有降级兜底 → 降级为 P4 可选 |
| 历史孤儿图片的自动回收 | seal 无 `storageList`，物理上枚举不到 |
| 冷会话里的图被 LRU 清掉 | 与图床 cap 同一失效模式，有降级自愈；加保护就退回扫描了 |
| 图床零出网 | 与"主链路不过 base64"互斥，选择后者 + §5.7 加固 |
