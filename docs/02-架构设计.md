# 02 - 架构设计

本章描述插件的分层、依赖规则、装配顺序与主链路；各模块的文件布局与实现细节见 [03-核心模块详解](03-核心模块详解.md)。

## 设计约束

- **单文件产物**：全部 `src/` 经 esbuild 打包为 `dist/aiplugin4.js`，头部拼 `header.txt`；运行时只有一个 IIFE，没有动态 import、没有外部依赖加载。
- **goja 沙箱**：运行在 SealDice 的 JS 扩展环境，只能通过全局 `seal.*` / 扩展实例 `ext` 与宿主交互；无 `AbortController`、无 Node API、存储为「叠加式」key-value。
- **行为可回归**：改架构不改变对外行为（配置键、存储键、模型侧工具错误文案、消息渲染格式）；验证由单测 + sim/matrix/fuzz + ob11 runtime + 冒烟共同兜底（见 [07-开发指南](07-开发指南.md)）。
- **可注入宿主**：存储/时钟/网络访问统一走宿主端口，单测与模拟器用同一套 seal 桩注入，不直接摸 `seal`。

## 分层与模块地图

纵向主链路：**入口装配 → 消息管线 → 会话 → 智能体 → 模型**；横向由配置、上下文、记忆、工具、命令、提示词、日志等模块支撑。侧挂异步任务层（媒体生成、定时器、子代理）不阻塞主请求。

```text
┌──────────────────────────────────────────────────────────────┐
│ L4 装配  src/index.ts / pipeline.ts / cmd/ / pipeline/*        │
│  绑定 SealDice 事件、装配注册表、消息/事件分发入口               │
└───────────────┬──────────────────────────────────────────────┘
                ▼
┌──────────────────────────────────────────────────────────────┐
│ L3 领域  session/ context/ agent/ tool/ prompt/                │
│  会话编排与触发、上下文与摘要、智能体循环、工具执行、提示词组装     │
└───────────────┬──────────────────────────────────────────────┘
                ▼
┌──────────────────────────────────────────────────────────────┐
│ L2 能力  model/ memory/ media/ web/ resource/ pub/             │
│          judge/ event/ utils/ config(总线与注册)/ timer/block/usage │
│  模型请求与注册表、记忆引擎、媒体任务、联网、图片与资源、判定/事件      │
└───────────────┬──────────────────────────────────────────────┘
                ▼
┌──────────────────────────────────────────────────────────────┐
│ L1 纯逻辑  config/v5|domain|hooks|regex、model 纯逻辑叶子、      │
│           memory/v2 纯逻辑叶子、各模块 types.ts、logger、token_calibration │
└───────────────┬──────────────────────────────────────────────┘
                ▼
┌──────────────────────────────────────────────────────────────┐
│ L0 基础  core/host + core/seal_host + core/ports、config/static_config、│
│          config/ext、utils 基础叶子（target_id/url/raw_marker/markdown/render_tags）│
└──────────────────────────────────────────────────────────────┘
```

分层不是目录洁癖：它决定了**依赖方向只能向下**（高层可依赖低层，低层不得反向 import 高层）。每层对应 `scripts/lib/deps.mjs` 中的 `LAYER_RULES`，由 `npm run deps:check` 校验。

## 装配与生命周期

`src/index.ts` 的 `main()` 顺序是**不可随意调整的契约**：

```text
main()
├─ setHost(createSealHost())                 # 宿主端口必须先装
├─ registerConfigAppliers()                  # 配置应用钩子先注册（warmup 会触发）
├─ installAuxLlm() / installPromptMemorySource()   # 端口实现先于配置预热安装
├─ Handlebars Helper 注册（index/json_stringify/time）
├─ Config.registerConfig()                   # 注册全部分组 + warmup()（触发 Model.bootstrap 等钩子）
├─ initAgents() / registerAgentApi() / checkUpdate()
├─ registerAllTools()                        # 内置工具 + 技能 + MCP
├─ TimerManager.init() / MediaTaskManager.init() / ImageGC.init()
├─ knowledgeService.init() / BlockManager.initBlockList()
├─ registerAllCmds() / PrivilegeManager.reviveCmdPriv()
├─ MessagePipeline.subscribeOb11Receive()    # ob11 依赖事件（若存在）
├─ storage_version 写入（结构升级时）
└─ 绑定 SealDice 事件（见下）
```

事件绑定（`ext` 上的回调）：

| 事件 | 处理 |
| --- | --- |
| `onNotCommandReceived` | `MessagePipeline.handleNonCommand` |
| `onCommandReceived` | `MessagePipeline.handleCommand` |
| `onMessageSend` | `MessagePipeline.handleBotMessage` |
| `onPoke` | 构造 `[CQ:poke,...]` 后转 `onMessageSend` / `onNotCommandReceived` |
| `onGroupMemberJoined` / `onGroupLeave` / `onMessageDeleted` / `onBecomeFriend` / `onGroupJoined` | 归一到 UNI-ID 后交 `MessagePipeline.handleNativeNoticeEvent`（与 ob11 依赖通知共用去重） |

启动/重载相关的恢复语义：

- **媒体任务**：读盘时 `running` → `failed('插件重载中断')`；`done && !notified` 且来源为工具的任务补一次通知。
- **子代理**：重载后按索引对账，`running` 标记为「已中断·可续」。
- **图片索引/GC**：启动时惰性对账，不阻塞首条消息。
- **存储版本**：`storage_version < STORAGE_VERSION` 时写入新版本并记日志；具体数据迁移按 key 惰性执行（见 [06-数据存储](06-数据存储.md)）。

## 依赖规则：单向、端口、守卫

### 运行时依赖图与守卫

`npm run deps:graph` 用 esbuild metafile 提取**运行时**边（`import type` 不计入），Tarjan 求强连通分量（SCC）。`npm run deps:check` 以 `scripts/deps-baseline.json` 为基线做 ratchet：

- 最大 SCC / 环内模块数**只能下降**；
- 基线外的文件进入环 → 拒绝；
- 新增跨层依赖（低层 import 高层）、新增动态 import → 拒绝；
- 曾经删除的耦合边（`retiredEdges`）复活 → 拒绝；
- 未分类文件（新增目录未在 `LAYER_RULES` 配层）→ 拒绝，防止绕过分层检查。

当前基线：**0 个环（最大 SCC = 1、环内模块 0）**，保留 13 条历史跨层违规（只减不增），冻结删除边 187 条。架构调整后确需放宽时用 `npm run deps:update` / `--allow-grow`，并在 PR 说明原因。

### 宿主端口（L0）

`src/core/host.ts` 定义 `HostStorage` / `HostClock` / `HostFetcher` / `HostExt` 与 `setHost/getHost`；`src/core/seal_host.ts` 是唯一直接读 `seal`/`ext` 的适配器，入口先 `setHost(createSealHost())`。

规则：业务代码读写存储/时间/网络一律 `getHost().xxx`，不直接调 `seal.*`/`ext.storage*`。好处是单测与模拟器可整体替换宿主（`scripts/test-host.ts` 复用 seal 桩）。

### 跨层端口（L0）

双向协作（A 调 B、B 又回调 A）如果直接互相 import 会形成环。约定：**双方各自在模块加载时把一半能力注册到 `src/core/ports/`，不互相 import**。

| 端口 | 提供方 → 消费方 | 作用 |
| --- | --- | --- |
| `agent_registry` | agent 注册 → 压缩/子代理等按名取 Agent | `Agent.get(name)` 的间接层，保住测试桩 |
| `aux_llm` | 组合根注入实现 → memory/media 等 | 压缩、摘要、评分等内部推理调用 |
| `session_lookup` | session 注册 → timer/media 等 | 按 id 取会话，不 import `session_service` |
| `judge_wait` | judge 评分轮末 ↔ timer 定时器双向登记 | 拆掉 judge ⇄ timer 环 |
| `media_notice` | media 注册 → session 收信/发信 | 媒体「已送达」回置，不反向 import media |

实现是**动态委派**（调用时查端口当前实现），因此测试桩（`Agent.get`、`MemoryService`/兼容 `MemoryManager.*` 等）继续生效；不要缓存函数引用。

### 配置解析与应用分离

- `src/config/configs/*` 只负责「从 SealDice 配置项解析出类型化对象」，不 import 模型/会话等实现。
- `src/config/apply/` + `src/config/hooks.ts` 负责「把解析结果应用到实现」（如 `applyModelConfig` → `Model.bootstrap`）。
- 组合根在 `Config.registerConfig()` 前 `registerConfigAppliers()`；`Config.warmup()` 通过 `getCache` 访问各分组，才会触发应用钩子。
- 需要新增「配置 → 实现」联动时：解析放 `configs/`，应用放 `apply/`，在 `hooks.ts` 注册，不要在解析函数里直接调实现。

## 核心概念

| 概念 | 说明 |
| --- | --- |
| 会话（Session） | 私聊/群聊工作单元，ID 为 `QQ:<uid>` / `QQ-Group:<gid>`；含上下文、记忆、设定、图片管理器、工具开关、流式状态等 |
| 上下文（Context） | 会话内只追加的事件账本（user/assistant/tool_call/tool_result/event），带时间、来源、消息 ID 等元数据；`compileRequest` 每次按预算选择可见单元，滚动摘要只追加记录、不删除原文 |
| 记忆（MemoryUnit） | Hindsight-like 记忆单元 = 内容 + 向量 + 标签 + 实体/关联 + 权重；另有 Observation（观察记忆）与 MentalModel（心智模型） |
| 知识库（KnowledgeBaseService） | 配置驱动的只读知识库：JSON 中 Markdown 正文按标题/段落自动分块，关键词检索 + 惰性向量重排，AI 通过 `knowledge_*` 工具读取 |
| 智能体（Agent） | 「角色配置 + 会话服务」；默认 `*`，另有 `compress_agent` / `summarize_agent` / `judge_agent` |
| 工具（Tool） | 注册到 `toolMap` 的函数，描述为 OpenAI function calling JSON Schema；分内置/技能/知识库/MCP/外部插件 |
| 媒体任务（MediaTask） | tts/tti 异步工作单元：提交即返回任务号，完成后按来源投递（命令直发 / 工具唤醒 AI） |
| MCP | Streamable HTTP + JSON-RPC 外部工具服务器，`tools/list` 结果注册为工具 |
| 技能（Skill） | 配置驱动条目，AI 通过 `use_skill` 按需获取正文，支持技能间引用 |

## 消息与事件入口

`MessagePipeline` 是唯一入口，所有路径最终复用同一套过滤/触发/待机逻辑：

- **非指令消息**：忽略私聊/忽略条件/忽略正则 → CQ 白名单 → 触发判定（正则/条件/计数器/计时器/概率/活跃时间/待机）→ `session.chat()` 或仅入库。
- **指令消息**：`.ai` 根命令分发；默认不入上下文，开启后在待机模式入库。
- **机器人自身消息**：先交给工具监听（`session.tool.listen`），再按配置决定是否入库；跳过刚发出的回复避免自问自答。
- **戳一戳**：转成 `[CQ:poke]` 后走对应消息路径。
- **通知/请求事件**（原生 + ob11 依赖双路径）：转文本提示词，仅在会话待机或全局待机时录入上下文；录制成功后按「触发 → 事件触发规则」匹配事件视图（顺序=优先级、首条命中、双路径只触发一次），命中则让会话响应——空闲直接起轮，会话运行中把触发提示挂进 `pendingQueue`，轮末由 `resumePending` 续跑；poke 走消息管线（`[CQ:poke]` → poke 内容部分 → 触发检查）。共用白名单与 3 秒事件级去重，重复到达「后到覆盖先到」；机器人自身事件由原生回调覆盖。
- **ob11 补充接收**：核心 milky 路径丢弃的文件/视频/语音/卡片/音乐/合并转发段，由 ob11 依赖事件补齐；核心优先、依赖补充，避免同一条消息重复入库。

事件原始数据不渲染给模型，挂在上下文条目 `raw` 上，由 `read_raw kind=event` 读取；事件文本以 `[system:名称]…[/system]` 边界渲染，防注入。

## 一次 AI 回复的完整链路

以非指令正则触发为例：

1. `pipeline.handleNonCommand` 命中触发条件 → `session.chat(ctx, msg, '非指令')`。
2. `Session.chat()`：令牌桶配额检查 → 重置 BLOCKED 工具状态 → 按模型 `body.stream` 决定 `chatStream` 或 `Agent.run()`。
3. `Agent.run()`：
   - 组装请求消息：system prompt（分节）+ 预设上下文作为前缀；历史由 `compileRequest` 从事件账本选择：最新单元必留、工具组整组、超预算截断并带 `read_raw` 指针、被省略区间注入滚动摘要或显式缺口提示；图片按能力转内容块或文本标签。
   - `streamService.sendChatRequest()` 请求模型（`requestModel` 统一超时/重试/用量）。
   - 工具轮：写上下文 → `ToolRunner`/`executor` 执行 → 回填 tool 结果 → 下一轮，直至最终回复；轮数受 `MAX_CALL_COUNT` 限制。
   - 复读检测，命中则重试（单轮最多 3 次）。
4. `Session.reply()`：分段发送（`replyToSender`），助手消息写回上下文。
5. run 结束触发后台滚动摘要与记忆桥消费（有水位/节流/退避）；原文始终保留在事件页，可 `read_raw`/`grep_raw` 回查。

异常路径：`ApiError` 分类后按配置自动处理（上下文超长按模型窗口重算预算后重发、余额不足切备用模型）；`.ai stop` 通过 `stopVersion`/`StopEvent` 中止并在检查点丢弃结果。

## Prompt 组装与上下文构建

`prompt/builder.ts` 的 `buildPromptParts` 构造 `PromptContext` 后交给 `prompt/assemble.ts` 按**段注册表**组装（4.29.0 起不再使用大模板；内置文案全英文）：

```text
system 通道（稳定段，段级缓存 30s）
├── core:identity      身份总述
├── core:role          角色设定（用户内容，保持原语言）
├── core:language      Response language：按对话语言回复
├── core:session       平台/类型/名称/ID/BotID
├── core:markers       消息标记约定 + 英文压缩/截断标记说明
├── core:images        图片与图库（仅图床/MCP 启用）
├── core:reply         回复方式
├── core:direction     工作方向（DIRECTION_PROMPT）
├── core:tool-access   工具获取（原生模式）/ core:tool-call-format（提示词工程模式）
├── tool:image / ob11 / read-raw / resources / commands   按工具可见性门控的指导段
├── core:skills        Available skills（1500 字符 / ≤100 条）
├── core:knowledge     Knowledge bases（ID/名称/描述索引）
└── core:delegation    Sub-agent delegation（仅委派工具开启）
runtime 通道（每轮以 user 消息注入，不污染 system 前缀）
├── core:time          当前时间
├── core:memory-hint   memory_recall 提示
├── core:memory        长期记忆/心智模型（10s 缓存）
└── tool:mcp-instructions  MCP 服务器 instructions（可选、默认关）
```

段来源：内置模块在 `index.ts` 启动时 `registerBuiltinSections()`；外部插件可 `registerPromptSection` 注册 `ext:*` 段，或 `onPromptAssemble` 整体改写。协议文本（标记/包装/`[system:<name>]`）统一由 `src/utils/protocol.ts` 产出。上下文侧的窗口选择、摘要注入与工具组对齐统一在 `view/compile.ts`（见 [03-核心模块详解](03-核心模块详解.md) 的上下文与记忆章节）。

## 异步任务与唤醒

侧挂层不进主请求链路，但「结果必须送达」是硬约束：

- **媒体任务**：`submit()` 入队即返回 → 并发上限内后台执行 → 结算分流：命令来源直接 `replyToSender`；工具来源写入会话 `noticeQueue` 并尽力触发一轮对话（`skipBucket`）。三段式：**入队（置 taskId，不置 notified）→ 判定（忙则 defer）→ 轮末补触发（`wakePendingNotices`）**，任何一步失败都不能让结果丢失。工具侧另有同步等待窗口，窗口内完成则当场返回、不进唤醒链路。
- **定时器**：`TimerManager` 每 5 秒扫一轮，到点注入系统用户消息并 `session.chat()`。
- **子代理**：子会话 headless 运行，完成后写父会话 `noticeQueue`，由 `flushNotices()` 在每轮请求前注入。
